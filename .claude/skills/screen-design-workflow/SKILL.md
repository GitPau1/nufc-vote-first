# 화면 설계 워크플로우

기존 서비스에 새 화면·기능을 추가할 때, 요구사항 파악부터 개발 핸드오프 직전 QA까지 6단계로 진행한다. 목표는 "그럴듯한 화면"이 아니라 "왜 이렇게 만들었는지 설명 가능하고, 기존 서비스와 이질감 없는 화면"이다.

## 최초 1회 세팅 확인

스킬을 처음 실행할 때, 아래 항목의 위치를 사용자에게 확인하고 이후에는 고정 참조한다. 매 실행마다 다시 묻지 않는다.

- 디자인 시스템 스펙 문서 위치 (컴포넌트 목록, props, 사용법)
- 판단 원칙 문서 위치 (언제 어떤 컴포넌트를 쓰는가 — 없으면 "없음, 기존 화면에서 역추출" 로 기록)
- foundation 토큰 목록 (컬러, 간격, 라운드, 타이포 스케일)
- 작업 대상 레포 경로

이 문서들이 스킬 실행 중간에 안 나오면 반드시 3단계 진입 전에 확보한다. 없으면 진행을 멈추고 요청한다.

---

## 1단계. 요구사항 파악

**목적**: 무엇을, 왜 만드는지, 핵심 액션이 무엇인지 확정한다.

**질문 우선순위 템플릿** (순서대로, 답변에 따라 다음 질문을 좁혀감):
1. 목적 — 무엇을 만들려 하고, 어떤 문제를 해결하려 하는가
2. 사용자 — 누가, 어떤 환경에서 쓰는가
3. 플로우 — 이 화면 전후로 어떤 화면이 이어지는가 (최소 1단계 앞뒤)
4. 핵심 액션 — 이 화면에서 사용자가 반드시 해내야 하는 행동 1가지 (2개 이상 나오면 우선순위를 되물어서 하나로 좁힌다)

**종료 조건**: 위 4개 항목이 모두 채워지면, 그 즉시 "확인됐다"고 명시적으로 선언한다.
> 예: "핵심 액션을 '관리자가 나중에 볼 응답을 개인적으로 마킹한다'로 확정했습니다. 다음 단계(레퍼런스 탐색)로 넘어갈까요?"

임의로 다음 단계를 시작하지 않는다. 사용자가 진행을 명시적으로 확인해야 2단계로 넘어간다. 항목이 다 안 채워졌으면 계속 질문한다.

---

## 2단계. 로파이 와이어프레임

**목적**: 저비용으로 여러 구조를 넓게 탐색한 뒤, 3개로 좁혀 실제로 눈에 보이는 와이어프레임을 만들고, 그중 무엇을 진행할지는 사용자가 고른다. 정확한 컴포넌트명이나 픽셀 값은 아직 참조하지 않는다 — 조기에 하나의 구현 방식으로 사고가 고정되는 걸 막기 위해서다.

### 레퍼런스 조사 (2트랙)

**비주얼 트랙**
1. `web_search`로 이 화면 유형을 실제로 제공하는 서비스명을 최소 2~3개 확보한다 (쿼리 예: `"[화면 유형] app 실제 사례"`).
2. 서비스명 + "google play store"로 검색해 플레이스토어 URL을 찾고, `web_fetch`로 공식 스크린샷 원본과 다운로드 수·평점을 확인한다. 다운로드 수가 1만 미만이거나 리뷰가 적으면 후순위로 둔다.
3. 플레이스토어에 없는 서비스는 `image_search`를 보조로 쓰되, 서비스명을 포함해 검색한다. 결과가 UI킷/Figma/Dribbble 같은 컨셉성 소스면 실제 서비스로 오인시키지 않고 "컨셉 참고용"이라고 표기한다.
4. 요청받은 화면과 정확히 일치하는지 앱 설명·리뷰 문구로 재확인하고, 인접하지만 다른 화면이면 배제한다.

**맥락 트랙**
- Growth.Design, NN/g(Nielsen Norman Group), Baymard Institute, 기업 디자인 블로그에서 "왜 이렇게 설계했는가, 어떤 행동을 유도하려 했는가"를 조사한다.
- 15단어 이상 직접 인용 금지 — 반드시 자기 언어로 요약한다.
- 근거를 못 찾으면 추측으로 채우지 말고 "관련 케이스 스터디를 찾지 못함"이라고 명시한다.

### 발산-수렴

- **발산에는 제한이 없다.** 레퍼런스가 뒷받침하는 만큼 구조 후보를 계속 뽑는다.
- **수렴은 정확히 3개.** 2개 이하나 4개 이상으로 마무리하지 않는다 — 너무 적으면 비교가 안 되고, 너무 많으면 사용자의 선택 비용이 커진다.

### 와이어프레임 산출 (필수 — 표만 제시하고 넘어가지 않는다)

표는 각 구조안의 요약일 뿐, 실제 산출물이 아니다. 3개 구조안마다 **눈에 보이는 와이어프레임을 반드시 만들어서 보여준다.**

- **형식**: ASCII 아트가 아니라, 실제 렌더링되는 HTML(Artifact)로 만든다. 박스·영역·라벨 정도의 로파이 해상도로 — 실제 색상 토큰, 정확한 간격 값, 실제 카피는 아직 넣지 않는다 (그건 4단계 몫이다). 회색조 박스 + 텍스트 라벨(예: "헤더", "카드 썸네일", "CTA 버튼") 정도의 충실도가 기준선이다.
- **베이스라인**: 화면을 완전히 새로 상상하지 않는다. 대상 화면들의 **현재 실제 구조를 단순화한 것**을 각 구조안의 출발점으로 삼는다 — 그래야 "무엇이 유지되고 무엇이 바뀌는지"가 한눈에 비교된다.
- **비교 가능성**: 3개 안을 한 페이지(또는 나란히 배치된 섹션)에서 같이 볼 수 있게 만들어, 사용자가 스크롤/탭 전환 없이 바로 비교하게 한다.

### 결정 기록 (표 형식, 파일로 저장하지 않고 대화 중 표로 제시 — 와이어프레임 산출 다음에 온다)

| 아이디어 | 한계점 |
|---|---|
| (구조안 1 한 줄 설명) | (이 안이 가진 약점) |
| (구조안 2 한 줄 설명) | (이 안이 가진 약점) |
| (구조안 3 한 줄 설명) | (이 안이 가진 약점) |

**채택은 사용자가 한다.** 스킬이 임의로 "채택: N안"을 선언하지 않는다. 표와 와이어프레임을 제시한 뒤 "어떤 안으로 진행할지" 사용자에게 명시적으로 묻고, 답을 받은 다음에만 3단계로 넘어간다.

---

## 3단계. 컨텍스트 확보 + 패턴 매칭

**목적**: 2단계에서 채택한 로파이 구조를, 실제 서비스의 규칙과 컴포넌트에 매칭한다. 이 작업은 격리된 작업 공간에서 진행한다.

**진행 순서**:
1. 최초 1회 세팅에서 확인한 레포를 스캔해서, 이 화면이 상속받는 레이아웃(GNB, 배경, 페이지네이션 등)과 이미 쓰이고 있는 컴포넌트를 목록화한다. 이 목록을 **"건드리면 안 되는 것"** 기준선으로 저장한다.
2. 로파이 구조의 각 요소를 실제 컴포넌트/패턴에 하나씩 매칭한다.
3. 매칭이 애매한 회색지대는 판단 원칙 문서에서 근거를 찾는다. 원칙 문서가 없으면 1번에서 스캔한 기존 화면들에서 반복되는 패턴을 역으로 추출해 임시 원칙으로 쓴다.
4. 이 모든 작업은 격리 폴더(예: `src/prototype/{화면명}/`) 안에서만 진행한다.
   - 새 코드가 기존 코드를 읽는 것(단방향 참조)만 허용, 기존 코드가 새 코드를 불러오는 역참조는 금지.
   - fetch·API 실호출 금지, 모든 데이터는 더미로 처리.
   - 검증이 끝나면 이 폴더만 삭제하면 원복되게 유지한다.
5. 가능하면 실제로 로컬 서버를 띄우고 임시 라우트로 연결해 스크린샷으로 눈으로 확인한다. 코드만 읽고 "맞겠지"로 넘어가면 실제로 자주 놓치는 문제들이다.

레포 경로나 스펙/원칙 문서 위치가 아직 없으면, 이 단계 진입 전에 반드시 확보하고 없으면 요청한다.

### 프리뷰 시 자주 겪는 문제 (먼저 의심할 것)

격리 폴더를 실제로 띄워봤을 때 스타일이 안 먹거나 레이아웃이 이상하면, 새 버그를 의심하기 전에 먼저 이 두 가지를 확인한다 — 실제로 반복해서 겪는 문제다.

1. **빌드 설정이 격리 폴더를 스캔하지 않는다.** Tailwind 등 유틸리티 CSS는 보통 `content`/스캔 경로가 정해져 있고, 격리 폴더(`src/prototype/` 등)가 거기 빠져 있으면 에러 없이 조용히 스타일이 안 먹는다. 확인 후 임시로 스캔 경로에 추가해서 확인하고, **확인이 끝나면 반드시 원복한다.**
2. **상위 레이아웃과 이중으로 겹친다.** 임시 라우트가 실제 루트 레이아웃(전역 셸 컨테이너 등)을 그대로 상속하면, 그 레이아웃이 이미 걸어둔 폭 제한·배경이 프로토타입 자체의 폭 제한과 겹쳐 의도한 폭이 안 나온다. 상위 레이아웃을 임시로 우회해서 확인하고, **확인이 끝나면 반드시 원복한다.**

---

## 4단계. 컴포넌트 기반 구현

**목적**: 실제 시안을 만든다. 기존 것으로 되는 건 최대한 재사용하고, 안 되는 것만 서비스의 foundation 규칙에서 파생시킨다.

**4단계는 한 라운드로 안 끝나는 게 정상이다.** 범위가 넓은 변경(여러 화면에 걸친 구조 변경, 전역 컴포넌트 수정 등)을 처음부터 한 번에 다 하려 하지 않는다. 좁은 범위로 먼저 반영하고 사용자 확인을 받은 뒤, "다른 화면도", "이것도 마저" 식으로 반복 확장하는 것을 이탈로 보지 않는다 — 4단계 내부의 정상적인 반복이다. 매 확장 라운드마다 3단계 매칭을 가볍게 다시 거쳐도 된다.

**진행 순서**:
1. 3단계에서 매칭된 기존 컴포넌트를 그대로 조립한다.
2. 매칭되지 않은 신규 요소는, foundation 토큰(컬러, 간격, 라운드값, 타이포 스케일)을 재료로 2~3개의 후보 변형을 생성한다. 완전히 새로운 임의의 값을 쓰지 않는다.
3. 후보들 중 1단계 핵심 액션과 3단계 매칭 원칙에 가장 부합하는 것을 선택하고 다듬는다. (판단 기준 우선순위: 핵심 액션 부합도 > foundation 준수도 > 구현 복잡도)
4. 공유·전역 컴포넌트(헤더, 셸 컨테이너, 네비게이션 등)를 고칠 때는 짐작으로 사용처를 판단하지 않는다 — grep 등으로 실제 사용처를 전부 찾아 하나씩 확인한다. 빠뜨리면 나중에야, 대개 사용자 피드백으로 발견된다.
5. 실제 레포에 반영한 뒤 가능하면 로컬 서버로 최소 1회 스크린샷 검증한다 — 특히 모바일/데스크탑처럼 여러 breakpoint와, 로그인/비로그인처럼 여러 상태를 확인한다.
6. 변경 후 관련 테스트만이 아니라 프로젝트 전체 테스트 스위트를 최소 1회 실행해 회귀를 확인한다. 기존 테스트가 실패하면, 이번 변경으로 생긴 회귀인지 원래부터 있던 문제인지부터 구분한다(예: 마지막 커밋 시점의 파일과 비교). **이번 변경으로 생긴 회귀**면 새 의도에 맞게 테스트를 업데이트하고 왜 바뀌었는지 주석으로 남긴다. **무관한 기존 실패**면 고치려 하지 말고 그 사실만 사용자에게 보고한다.
7. 완료 후 "재사용한 패턴 / 새로 만든 요소"를 구분해서 기록해둔다 — 6단계 QA에서 대조 대상이 된다.

---

## 5단계. 승인 게이트

**목적**: 방향이 맞는지 사람이 확인한다. 이 게이트는 **디테일 조정 피드백만** 다룬다 — 근본적인 방향 재검토는 이 스킬의 범위 밖이며, 그런 피드백이 오면 1단계부터 별도로 다시 시작할 것을 제안한다.

**진행 순서**:
1. 결과물을 제시하면서, 1단계 핵심 액션·3단계 매칭 원칙과 어떻게 부합하는지 근거를 함께 요약해서 보여준다. (근거 없이 결과물만 보여주지 않는다 — 근거가 있어야 사용자가 정확한 피드백을 줄 수 있다.)
2. 피드백을 받으면 4단계로 돌아가 반영한다. 반복될 수 있다.
3. 승인되면 6단계로 진행한다.

---

## 6단계. 일관성 자가검증 (QA)

**목적**: 승인된 결과물이 실제로 빠짐없이 규칙을 지켰는지, 스킬 스스로 기계적으로 대조한다. 5단계가 "방향이 맞는지"를 사람이 판단하는 단계라면, 6단계는 "맞다고 확인된 것이 정말 다 지켜졌는지"를 검증하는 단계다.

**체크리스트** (실무 디자인 QA에서 쓰이는 7개 기준):
1. **디자인 시스템 준수** — 컬러·타이포·간격·컴포넌트가 스펙과 일치하는가 (토큰 값을 임의로 쓰지 않았는가)
2. **상태 커버리지** — default, hover, focus, disabled, loading, empty, error 상태가 모두 정의됐는가
3. **콘텐츠 극단값 대응** — 텍스트가 매우 길거나 짧을 때, 리스트가 0개이거나 아주 많을 때 깨지지 않는가
4. **반응형/다크모드 대응** — 정해진 breakpoint와 테마에서 모두 확인됐는가
5. **접근성** — 색 대비, 포커스 순서, 터치 타겟 크기
6. **플로우 정합성** — 연결된 다른 화면과 상태 값(필터 조건 등)이 끊기지 않고 이어지는가
7. **핸드오프 스펙 정확성** — 실제 구현물과 전달되는 스펙(간격 값 등)이 일치하는가

**진행 순서**:
1. 3단계에서 저장한 "건드리면 안 되는 것" 목록과 4단계 최종 결과물을 항목별로 1:1 대조한다.
2. 불일치가 나오면 "의도된 변경(3단계 매칭이나 4단계 판단에 근거가 있음)"인지 "실수로 인한 이탈"인지 구분한다. 실수면 스스로 고치고, 애매하면 사용자에게 보고한다.
3. 위 7개 체크리스트를 확인한다. `seed-design-qa` 스킬이 사용 가능하면 이 단계를 그 스킬에 위임해도 된다.
4. 최종적으로 "유지된 것 / 의도적으로 바뀐 것 / 개발 시 주의할 점"을 요약해서 전달한다. 필요하면 `design-handoff` 스킬 포맷에 맞춰 정리한다.

---

## 단계 간 이동 규칙 요약

- 1→2→3→4→5→6은 기본 순서이며, 각 단계 종료 조건이 충족되고 사용자가 진행을 확인해야 다음 단계로 넘어간다.
- 4단계는 "다른 화면도", "이것도 마저" 식으로 여러 라운드에 걸쳐 반복 확장되는 게 흔하다 — 이건 순서 이탈이 아니라 4단계 안에서의 정상적인 반복이다(자세한 기준은 4단계 참고).
- 5단계에서 디테일 피드백이 오면 **4단계로만** 돌아간다. 2단계나 3단계로 되돌아가지 않는다.
- 6단계는 5단계 승인 이후 한 번만 실행한다. 6단계에서 발견된 실수성 이탈은 스킬이 직접 수정하고, 의도가 불분명하면 사용자에게 확인한다.
