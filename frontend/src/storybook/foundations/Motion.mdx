# Motion

duration은 **네 개**뿐이다. 역할로 고른다.

이 토큰은 `transition-*`과 `animate-in`/`animate-out` 양쪽에 적용된다 — `tailwindcss-animate`의 `animationDuration`이 `transitionDuration`을 상속하기 때문이다. 그래서 하나만 외우면 된다.

| 토큰 | 값 | 언제 쓰는가 |
|---|---|---|
| `duration-micro` | 150ms | hover·pressed·focus 피드백, 작은 인디케이터(캐러셀 dot) |
| `duration-enter` | 300ms | 나타나거나 새 위치로 자리잡는 전환. 시트·모달 등장, 캐러셀 카드 이동, 페이드 인 |
| `duration-exit` | 200ms | 사라지는 전환. 시트·모달 퇴장 |
| `duration-slow` | 700ms | 화면을 크게 차지하는 카드·배너 전환 |

## 규칙 — 나가는 건 들어오는 것보다 빠르게

`enter`(300ms) > `exit`(200ms)다. 사용자가 이미 본 것을 치우는 데는 시간을 덜 쓴다. 이 관계를 뒤집지 않는다.

## 마이크로/매크로 경계는 쓰지 않는다

일부 디자인시스템은 "0.2초 이하는 마이크로, 초과는 매크로"로 나눈다. **우리는 이 기준을 채택하지 않았다.** `duration-exit`이 정확히 200ms여서 경계에 걸리고, 우리 토큰은 이미 역할 이름으로 구분되기 때문에 시간 기준이 추가 정보를 주지 않는다.

"이건 마이크로인가 매크로인가"를 묻지 말고 "이건 피드백인가, 등장인가, 퇴장인가, 큰 전환인가"를 묻는다.

## 현행 값이 어떻게 수렴했는가

이 4개 토큰은 흩어져 있던 7종(100·150·200·300·500·700·1000ms)을 정리한 결과다.

| 새 토큰 | 흡수한 값 | 영향 |
|---|---|---|
| `micro` 150 | 100, 200 | hover 피드백이 약간 느려지고, 캐러셀 dot은 약간 빨라졌다 |
| `enter` 300 | 500(시트 열림), 200(선수 선택 모달 열림), 300(캐러셀 카드) | **시트는 빨라지고 모달은 느려져서, 두 모달의 속도가 같아졌다** |
| `exit` 200 | 300(시트 닫힘), 150(모달 닫힘) | 위와 같은 이유로 통일 |
| `slow` 700 | 700, 1000 | Pick One 카드가 흐려질 때가 조금 빨라졌다 |

수렴 전에는 같은 "아래에서 올라오는 모달"인데 시트는 500ms, 선수 선택 모달은 200ms로 **2.5배 차이**가 났다. 그게 이 정리의 이유다.

## 예외 — CSS 클래스가 아닌 JS 타이머

위 검사는 Tailwind 클래스 문자열(`duration-숫자`)만 본다. 애니메이션 종료 시점에 state를 정리해야 하는 곳은 `setTimeout`으로 같은 시간을 다시 재는데, 이건 클래스가 아니라 숫자 인자라 검사가 못 잡는다. `PlayersPageClient.tsx`의 Pick One 카드가 이 경우다.

| 상수 | 값 | 토큰과의 관계 |
|---|---|---|
| `PICK_ONE_EXIT_FADE_MS` | 700 | `duration-slow`와 같은 값 — 카드가 실제로 사라지는 CSS 전환 시간과 맞춰야 하므로, 둘 중 하나만 바꾸면 어긋난다 |
| `PICK_ONE_EXIT_STAGGER_MS` | 120 | 4개 토큰 중 어디에도 안 맞는 stagger 값. "진입 애니메이션이 자리잡을 시간을 준 뒤 퇴장을 시작"하는 용도라 등장/퇴장 전환 자체와는 다른 역할 — `opacity-[0.34]`(State.mdx)와 같은 성격의 예외로 다룬다 |
| `PICK_ONE_CONFIRM_HOLD_MS` | 1000 | 애니메이션 전환이 아니라 "승자를 보여준 채로 대기"하는 UX 타이밍. 4개 토큰과 원래 무관 |

이 셋은 이름과 주석으로만 추적되고 있고, `design-foundation.test.mjs`는 이 파일의 숫자 인자를 검사하지 않는다 — JS 타이머는 Tailwind 클래스 문자열이 아니라 숫자 인자라 자동 검사 대상이 아니다.

## Easing — 현재 일관되지 않다

**의도한 규칙**은 이렇다.

| 상황 | 쓸 것 | 이유 |
|---|---|---|
| 등장 | `ease-out` | 빠르게 들어와서 부드럽게 멈춘다 |
| 퇴장 | `ease-in` | 부드럽게 시작해서 빠르게 빠진다 |
| 마이크로 피드백 | 지정하지 않음 (기본값) | 150ms에서는 이징 차이가 인지되지 않는다 |

**실제 코드는 아직 여기에 맞지 않는다.** `ui/sheet.tsx`는 양방향 모두 `ease-in-out`을 쓰고, `PlayerPickModal`은 열림에만 `ease-out`을 지정하고 닫힘은 기본값이다. `PlayersPageClient`의 카드는 `ease-in-out`이다.

이 불일치를 알고 쓴다 — 새로 만드는 것은 위 규칙을 따르고, 기존 코드를 맞추는 작업은 별건이다. duration과 달리 easing은 아직 토큰화하지 않았고 검사도 없다.

## 정의된 keyframe

| 이름 | 무엇 |
|---|---|
| `animate-enter` | 페이지 진입 (8px 아래에서 페이드 인, 0.2s ease-out) |
| `animate-skeleton` | 로딩 shimmer (1.15s ease-in-out 무한 반복) |
| `loading-bar` | 상단 로딩 바 이동 |
| `accordion-down` / `accordion-up` | 아코디언 펼침·접힘 (0.2s ease-out) |

새 keyframe을 추가할 때는 duration을 하드코딩하지 말고 위 토큰 값과 맞춘다.

## 하지 말 것

- 숫자 duration(`duration-300`, `duration-500`)을 쓰지 않는다. `design-foundation.test.mjs`가 **src 전체를 훑어서** 막는다 — 파일 목록에 등록하지 않은 새 파일도 걸린다.
- 같은 종류의 UI에 다른 속도를 주지 않는다. 시트와 모달이 다르게 움직이면 같은 앱처럼 느껴지지 않는다.
- `framer-motion`은 제거했다. 애니메이션은 Tailwind + `tailwindcss-animate`로 처리한다. 드래그 제스처처럼 이것만으로 안 되는 요구가 생기면 그때 다시 논의한다.
