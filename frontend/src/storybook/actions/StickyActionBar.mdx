# StickyActionBar

화면 하단 제출 버튼 바. 투표 상세(`/polls/[id]`)의 세 화면(`TypeAPollClient`·`TypeBPollClient`·`OverallRatingPollClient`)과 승부예측 제출(`/predictions/[weekKey]`의 `PredictionFlowClient`)에 거의 동일하게 복붙돼 있던 마크업을 하나로 합친 것이다.

코드: `src/components/primitives/sticky-action-bar.tsx`. props는 `children`과 `className`뿐이다. **공유하는 건 "모바일 fixed → 데스크탑 static" 전환 로직**이고, 화면마다 다른 부분(폭·데스크탑 정렬)은 `className`으로 넘긴다 — `cn()`이 `twMerge`라 `max-w-*` 같은 충돌 유틸리티는 넘긴 쪽이 이긴다. 예측 플로우는 `max-w-shell sm:max-w-[560px] sm:flex sm:justify-center`로 더 좁은 폭 + 가운데 고정폭 버튼을 만든다. 새 화면에서 하단 고정 CTA가 필요하면 `fixed bottom-0`를 직접 쓰지 말고 이걸 쓴다.

위 3개 스토리는 375px 폭 iframe에 담아 모바일 분기를 보여준다(자세한 이유는 아래 "문서상의 제약"). 스크롤되는 본문은 실제 화면 구조를 축약한 더미다.

## 모바일과 데스크탑이 완전히 다르게 놓인다

| | 모바일(`<640px`) | 데스크탑(≥640px) |
|---|---|---|
| 위치 | `fixed bottom-0`, `left-1/2 -translate-x-1/2`로 중앙 정렬 | `sm:static` — 컨텐츠 흐름 맨 아래 |
| 폭 | `w-full max-w-detail`(680px) | 동일 + `sm:mx-auto` |
| 배경 | `bg-surface-translucent`(뒤가 비치는 흰색) + `backdrop-blur` + `border-t` | 전부 제거(투명, 보더 없음) |
| 여백 | `p-4` | `sm:p-0 sm:pb-10` |
| z-index | `z-30` | `sm:z-auto` |

데스크탑에서 fixed를 푸는 건 의도된 결정이다 — `max-w-detail`로 폭이 잘린 흰 카드가 화면 하단 가운데 떠 있는 게 어색하다는 피드백 때문이고, 지금은 일반 웹 폼의 "맨 아래 제출 버튼"과 같은 자리에 놓인다.

## 안에 들어가는 버튼

투표 3곳은 [Button](?path=/docs/primitives-button--docs)의 **`variant="default"`(1차 CTA) 1개**를 `size="lg" className="w-full"`로 꽉 채워 넣는다. 높이(48px)는 `size` 토큰이 주는 값이라 `className`에 `h-12`를 직접 박지 않는다 — 그러면 `size=default`의 좌우 패딩(`px-4`)이 남아 토큰과 어긋난다. 예측 플로우는 같은 버튼을 모바일에선 `w-full`, 데스크탑에선 `sm:w-[200px]` 고정폭으로 두는 차이만 있다. 버튼 2개를 나란히 두거나 부가 텍스트를 함께 넣는 사용처는 현재 없다 — 새로 그런 형태가 필요하면 이 문서에 형태를 추가하고 나서 쓴다.

`OverallRatingPollClient`는 스텝형이라 같은 바에 마지막 스텝에서는 `전체 평가 제출`, 그 전에는 `다음 포지션 평가`가 들어간다. 조건이 안 찼을 때는 버튼만 `disabled`가 되고 바 자체(배경·상단 보더)는 그대로 보인다.

## 하단 여백은 호출부가 직접 준다

컴포넌트는 자기 높이만큼의 spacer를 만들어주지 않는다. 그래서 스크롤 영역에 하단 패딩을 직접 넣어야 마지막 콘텐츠가 바 밑에 가린다:

- `pb-[88px] sm:pb-0` — `TypeAPollClient`, `TypeBPollClient`
- `pb-[92px] sm:pb-0` — `OverallRatingPollClient`

`sm:pb-0`을 빼먹으면 데스크탑에서 바가 흐름 안으로 들어온 뒤에도 빈 여백이 88px 남는다.

## BottomNav와는 동시에 뜨지 않는다

[BottomNav](?path=/docs/composition-common-bottomnav--docs)는 `/`, `/polls`, `/predictions`, `/players`, `/menu` 5개 경로에서만 렌더되고(그 외에는 `return null`), StickyActionBar는 투표 상세(`/polls/[id]`)와 예측 제출(`/predictions/[weekKey]`)에서만 쓰인다 — 둘 다 BottomNav가 `return null`인 경로라 실제로 겹치는 화면이 없다.

겹칠 경우 BottomNav가 위에 온다 — `z-40` 대 액션바 `z-30`이고 둘 다 `bottom-0`이라 액션바가 가려진다. 폭도 달라서(`max-w-shell` 480px 대 `max-w-detail` 680px) 어긋난 두 겹으로 보인다. **BottomNav가 보이는 5개 경로에는 StickyActionBar를 쓰지 않는다.** 참고로 `NavigationLoading` 오버레이는 `z-[100]`이라 로딩 중에는 둘 다 덮는다.

## PageContainer가 세로 마진을 안 주는 이유

`src/components/primitives/page-container.tsx`는 셸에 `top`/`bottom` 마진을 의도적으로 주지 않는다 — 이 컴포넌트의 모바일 `fixed`는 뷰포트 기준이라, 셸에 세로 마진이 생기면 액션바가 셸 카드 밖으로 삐져나온다. PageContainer 쪽을 고칠 때 이 제약을 깨지 않도록 주의한다. (코드 의존은 없고 주석으로만 연결된 관계다.)

## 문서상의 제약

- 실제 화면에서 버튼 `onClick`은 서버 액션(`lib/actions/*`)을 호출한다. 여기 스토리의 버튼은 아무 동작도 하지 않는다 — 배치와 상태 확인용이다.
- 모바일 분기 스토리 3개는 `docs.story.inline: false`로 iframe에 담고, `src/storybook/_internal/mobile-only-docs-fix.css`에서 그 iframe 폭을 375px로 강제한다. 인라인으로 그리면 `fixed`가 문서 전체 뷰포트 기준으로 빠지고, 문서 폭(≥640px) 때문에 `sm:static` 분기만 보인다.
- 스토리의 프레임은 데스크탑에서 `sm:min-h-0`으로 높이를 푼다(실제 화면은 `min-h-screen`). Docs 페이지에 100vh 빈 컬럼이 늘어지는 걸 막기 위한 문서용 조정이다.
