# AI 제품 개발 자동화 프레임워크 — 에이전트 시스템 설계서

---

## 1. 작업 컨텍스트

### 배경 및 목적
반복되는 **기획 → 컨펌 → 개발** 사이클을 에이전트 협업으로 자동화한다.
기획/UX 에이전트가 PRD와 디자인 시스템을 해석해 명세를 생성하고, 사용자가 승인한 후 개발 에이전트가 코드를 구현하는 구조다.
**어떤 프로젝트에도 복사해 쓸 수 있는 범용 프레임워크**가 목표다.

### 입력
| 입력 | 형태 | 시점 |
|------|------|------|
| PRD | Markdown 파일 (1개 이상) | 프로젝트 초기화 |
| 디자인 시스템 | 폴더 (토큰, 컴포넌트, 가이드라인 등) | 프로젝트 초기화 |
| 기술 스택 명세 | 사용자가 대화로 제공 → SSOT에 기록 | 프로젝트 초기화 |
| 사용자 컨펌/선택 | 기획 에이전트가 제시한 옵션 중 선택 | 기획 단계마다 |
| 역질문 응답 | 사용자가 로그 파일을 읽고 답변 | 개발 중 수시 |

### 출력
| 출력 | 형태 | 경로 |
|------|------|------|
| 프로젝트 중심 파일 | Markdown | `/context/project.md` |
| 디자인 시스템 인덱스 | Markdown | `/context/design-system-index.md` |
| 기능별 명세서 | Markdown + 선택적 JSON | `/specs/<feature-name>.md` |
| 기획 사이클 로그 | Markdown 추가형 로그 (사용자용) | `/context/decisions.md` |
| 역질문 로그 | Markdown 추가형 로그 | `/output/questions.md` |
| 구현 코드 | 기술 스택에 따라 다름 (풀스택) | `/output/<feature-name>/` |

### 제약조건
- 개발 에이전트는 명세의 논리적 빈틈을 발견해도 **독단 판단 금지** → 역질문 로그 기록 후 건너뜀
- 기획 에이전트는 결과물을 제시하기 전 **엣지 케이스·기술 제약 자기 검증** 필수
- 에이전트 간 직접 호출 금지 → 메인 오케스트레이터를 통해서만 조율
- 기술 스택은 프로젝트마다 다를 수 있어, **SSOT(project.md)에 명시된 가이드**를 따름

### 용어 정의
| 용어 | 정의 |
|------|------|
| SSOT | Single Source of Truth. `/context/project.md`가 중심 파일 |
| 기획 사이클 | 기능 하나에 대한 기획 에이전트 실행 → 사용자 컨펌까지 |
| 개발 사이클 | 컨펌된 명세를 받아 개발 에이전트가 코드 구현까지 |
| 역질문 로그 | 개발 에이전트가 발견한 불확실한 항목을 기록하는 파일 |
| 디자인 토큰 | 색상, 타이포그래피, 간격 등 디자인 시스템의 최소 단위 값 |

## 2. 워크플로우 정의

### 2-1. 전체 흐름도

```
[프로젝트 초기화]
  사용자: PRD 파일 경로 + 디자인 시스템 폴더 + 기술 스택 제공
  메인 에이전트 → project.md + design-system-index.md 생성
        ↓
[기능 선택]
  메인 에이전트: 구현할 기능 목록 제시 또는 사용자가 지정
        ↓
[기획 사이클] ─────────────────────────────────────────┐
  기획/UX 에이전트:                                      │
    1. project.md + design-system-index.md 로드          │
       (필요 시 특정 컴포넌트 파일만 추가 조회)          │
    2. 화면/기능 명세 초안 생성                          │
    3. 자기 검증 (엣지 케이스, 기술 제약)                │
    4. 시각적 선택지 + 기능 명세 사용자에게 제시          │
  사용자: 옵션 선택 + 시각적 레이아웃 컨펌               │
  메인 에이전트:                                         │
    - /specs/<feature>.md 저장                           │
    - decisions.md에 사이클 로그 기록 (사용자용)         │
        ↓                                                │
  [컨펌 검증]                                            │
    성공 → 개발 사이클 진행                              │
    실패(명세 불완전) → 최대 2회 재시도 ─────────────────┘
        ↓
[개발 사이클]
  개발 에이전트:
    1. /specs/<feature>.md + project.md 로드
    2. [FE 단계] FE 레퍼런스 로드 → UI 컴포넌트·페이지 구현
    3. [BE 단계] BE 레퍼런스 로드 → API 라우터·DB 스키마 구현
    4. 논리적 빈틈 발견 시 → questions.md 기록, 해당 항목 건너뜀
    5. 구현 완료 코드 /output/<feature>/ 저장
        ↓
  [역질문 처리 루프]
    questions.md에 미답변 항목 있음?
      YES → 사용자에게 알림, 답변 수집 → 미완성 항목 재개발
      NO  → 사이클 종료
        ↓
[다음 기능 선택 or 종료]
```

### 2-2. LLM 판단 vs 코드 처리 구분

| LLM (에이전트가 직접 수행) | 스크립트/도구로 처리 |
|--------------------------|---------------------|
| PRD 해석 및 기능 분류 | 파일 읽기/쓰기 (Read/Write 도구) |
| 시각적 선택지 생성 | Markdown → JSON 변환 |
| 엣지 케이스 자기 검증 | 폴더 구조 스캔 |
| 컨펌 내용을 구조화된 명세로 변환 | 코드 파일 저장 |
| 역질문 작성 및 분류 | decisions.md 추가 기록 |
| 기술 스택에 맞는 코드 구현 | (없음 — 코드는 에이전트가 직접 작성) |

### 2-3. 단계별 성공 기준 및 검증

| 단계 | 성공 기준 | 검증 방법 | 실패 시 처리 |
|------|----------|----------|------------|
| 프로젝트 초기화 | project.md에 필수 섹션 존재 (서비스 목적, 기술 스택, 디자인 시스템 경로) | 스키마 검증 (필드 존재 여부) | 자동 재시도 1회 후 사용자에게 누락 항목 확인 |
| 기획 사이클 | 명세서에 화면 목적/컴포넌트 목록/분기 조건/엣지 케이스 항목 포함 | 규칙 기반 + LLM 자기 검증 | 최대 2회 재시도, 이후 에스컬레이션 |
| 사용자 컨펌 | 사용자가 시각적 선택지 중 하나를 명시적으로 선택 | 사람 검토 (필수 게이트) | 선택 없으면 사이클 진행 불가 |
| 개발 사이클 | 명세서의 모든 항목에 대응하는 코드 파일 존재 (역질문 항목 제외) | 규칙 기반 (파일 체크) | 역질문 로그 작성 후 스킵 + 사용자 알림 |
| 역질문 처리 | questions.md의 미답변 항목 = 0 | 규칙 기반 | 에스컬레이션 (사용자에게 답변 요청) |

## 3. 구현 스펙 (구조 개요)

### 3-1. 폴더 구조

```
/project-root
  ├── CLAUDE.md                              # 메인 오케스트레이터 지침
  ├── /.claude
  │   ├── /skills
  │   │   ├── /project-init                  # 프로젝트 초기화 스킬
  │   │   │   ├── SKILL.md
  │   │   │   └── /scripts                   # project.md + design-system-index.md 생성 스크립트
  │   │   ├── /spec-validator                # 명세서 검증 스킬
  │   │   │   ├── SKILL.md
  │   │   │   └── /scripts                   # 필수 필드 체크 스크립트
  │   │   └── /decision-logger               # 기획 사이클 로그 스킬
  │   │       ├── SKILL.md
  │   │       └── /scripts                   # decisions.md 추가 기록 스크립트
  │   └── /agents
  │       ├── /planning-agent
  │       │   ├── AGENT.md
  │       │   └── /references                # 기획 도메인 지식, 명세 템플릿
  │       └── /dev-agent
  │           ├── AGENT.md
  │           └── /references
  │               ├── fe-guide.md            # FE 단계에서만 로드
  │               └── be-guide.md            # BE 단계에서만 로드
  ├── /context
  │   ├── project.md                         # SSOT 중심 파일 (초기화 후 생성)
  │   ├── /design-system                     # 사용자가 복사해 넣는 디자인 폴더
  │   ├── design-system-index.md             # 초기화 시 자동 생성되는 디자인 시스템 요약 (에이전트용)
  │   └── decisions.md                       # 기획 사이클별 진행 로그 (사용자 열람용, 에이전트 비참조)
  ├── /specs
  │   └── <feature-name>.md                  # 기능별 컨펌된 명세 (사이클마다 생성)
  └── /output
      ├── questions.md                       # 역질문 누적 로그
      └── /<feature-name>                    # 기능별 구현 코드
```

### 3-2. CLAUDE.md 핵심 섹션 목록

- 역할: 메인 오케스트레이터 (기획/개발 에이전트 호출 조율)
- 프로젝트 초기화 절차
- 기능 목록 관리 방식
- 기획 사이클 트리거 조건 및 완료 기준
- 개발 사이클 트리거 조건 및 완료 기준
- 역질문 로그 처리 규칙
- 에이전트 호출 형식 (인라인 vs 파일 전달)

### 3-3. 에이전트 구조

**메인 에이전트 (CLAUDE.md)** — 오케스트레이터
- 전체 상태 추적 (어느 기능, 어느 단계)
- planning-agent, dev-agent 순차 호출
- 사용자와의 모든 인터페이스 담당

**기획/UX 에이전트 (planning-agent/AGENT.md)** — 명세 생성 전문
- 트리거: 메인이 기능명 + 컨텍스트 파일 경로를 전달할 때
- 입력: `project.md`, `design-system-index.md`, 대상 기능명
- 출력: `/specs/<feature>.md` (시각적 선택지 포함 명세 초안)
- 참조 스킬: spec-validator (자기 검증), decision-logger (컨펌 후 기록)

**개발 에이전트 (dev-agent/AGENT.md)** — 코드 구현 전문 (FE→BE 순차)
- 트리거: 메인이 컨펌된 `/specs/<feature>.md` 경로를 전달할 때
- 입력: `/specs/<feature>.md`, `project.md` (기술 스택 가이드 포함)
- FE 단계: `/references/fe-guide.md` 로드 → UI 구현
- BE 단계: `/references/be-guide.md` 로드 → API·DB 구현
- 출력: `/output/<feature>/` 코드 파일들, `questions.md` 업데이트
- 참조 스킬: spec-validator (완료 확인)

### 3-4. 스킬 목록

| 스킬 | 역할 | 트리거 조건 |
|------|------|------------|
| `project-init` | PRD + 디자인 시스템 + 기술 스택을 읽어 `project.md` 및 `design-system-index.md` 생성 | 프로젝트 최초 실행 시 |
| `spec-validator` | 명세서 필수 필드 존재 여부 검증 | 기획 에이전트가 명세 초안 완성 후 / 개발 에이전트 완료 확인 시 |
| `decision-logger` | 기획 사이클 전체 진행 내용을 `decisions.md`에 사이클 단위로 추가 기록 | 사용자 컨펌 직후 |

### 3-5. 데이터 전달 방식

| 구간 | 방식 | 형태 |
|------|------|------|
| 메인 → 기획 에이전트 | 파일 경로 전달 | `project.md`, `design-system-index.md` 경로 + 기능명 |
| 기획 에이전트 → 메인 → 사용자 | 파일 + 인라인 요약 | `/specs/<feature>.md` 저장 후 핵심 선택지만 인라인 제시 |
| 사용자 컨펌 → 메인 → 기록 | 인라인 | 선택 내용 + 이유를 decision-logger로 기록 |
| 메인 → 개발 에이전트 | 파일 경로 전달 | `/specs/<feature>.md`, `project.md` 경로 |
| 개발 에이전트 → 메인 | 파일 저장 | `/output/<feature>/`, `questions.md` 업데이트 |

### 3-6. 주요 산출물 파일 형식

**`/context/project.md`** (SSOT 중심 파일)
```markdown
# 서비스 개요
## 목적
## 핵심 원칙
# 기술 스택
## 프론트엔드
## 백엔드
## DB / 인프라
# 디자인 시스템
## 경로: /context/design-system/
## 인덱스: /context/design-system-index.md
# 기능 목록
## [ ] 기능명 — 상태(미착수/기획중/개발중/완료)
```

**`/specs/<feature>.md`** (기능 명세서)
```markdown
# 기능명
## 화면 목적
## 컴포넌트 목록 (디자인 토큰 참조)
## 기능 흐름 / 분기 조건
## 엣지 케이스
## API 엔드포인트 (풀스택)
## 시각적 선택지 → [컨펌된 옵션: X]
## 기술 제약 사항
```

**`/context/decisions.md`** (기획 사이클 로그)
```markdown
## [기능명] — [날짜]
### 제안된 선택지
- 옵션 A: ...
- 옵션 B: ...
### 컨펌된 선택
- 선택: 옵션 A
- 이유: ...
### 수정 사항
- ...
```

**`/output/questions.md`** (역질문 로그)
```markdown
## [기능명] — [날짜]
### 미결 항목
- [ ] Q: ... | 관련 파일: ... | 건너뛴 항목: ...
### 완료된 항목
- [x] Q: ... | A: ...
```

## 4. 검증 방법 (End-to-End)

1. **초기화 검증**: 샘플 PRD.md + 디자인 시스템 폴더를 준비 → 메인 에이전트 실행 → `project.md` 및 `design-system-index.md` 내 필수 섹션 존재 확인
2. **기획 사이클 검증**: 기능 하나를 지정 → 기획 에이전트 실행 → `/specs/<feature>.md` 생성 확인, 필수 필드(목적/컴포넌트/분기/엣지케이스) 포함 여부 체크
3. **컨펌 게이트 검증**: 명세서의 시각적 선택지가 명확히 제시되는지 확인, 선택 없이 개발 사이클 진행 불가한지 확인
4. **개발 사이클 검증**: 컨펌된 명세 기반 코드 생성 확인, 의도적 빈틈이 있는 명세로 역질문 로그 생성 여부 테스트
5. **재사용성 검증**: 새 프로젝트 폴더에 복사 후, 다른 PRD + 기술 스택으로 동일 워크플로우 정상 동작 확인
