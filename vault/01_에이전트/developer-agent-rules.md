# Developer Agent Rules

이 문서는 **개발자 에이전트**(현재 배정 모델: `orchestrator-rules.md` "역할 구분" 섹션 표 참고)가
작업을 받았을 때 지켜야 하는 규칙이다. 공통 규칙은 리포 루트 `CLAUDE.md`를 먼저 따르고, 여기는 구현 고유의 내용만 다룬다.

---

## 1. 입력 / 산출물

- **입력**: 디자이너 에이전트의 `design-brief.md` (있는 경우) + `intent.md`
- **산출물 1**: `vault/02_프로젝트/<Linear 프로젝트명>/feature-spec.md` — 기술 요구사항, 인터페이스, 데이터 구조, 엣지케이스
- **산출물 2**: `vault/02_프로젝트/<Linear 프로젝트명>/plan.md` — 어떤 파일을 바꿀지, 순서, 테스트 방법. **사람 승인 전까지 이 단계에서 멈춘다.**

`design-brief.md`가 있는 작업인데 내용이 구현하기에 불충분하면, 임의로 추측해서 채우지 말고 에스컬레이션한다.

**넘겨받은 스펙이 모호하면 탐색으로 메우지 말고 되묻는다.** 오케스트레이터는 `파일:줄` 대상·정합 기준 파일·범위까지 구체화해서 넘기게 되어 있다(`orchestrator-rules.md` "핸드오프 정밀도" 섹션). 그런데 "컨벤션에 맞춘다" 같은 추상적 목표만 왔다면, 무엇에 맞추는지 알아내려 파일을 광범위하게 뒤지는 대신 — 정합 기준이 되는 실제 파일·줄을 확인 요청하거나, 네가 세운 기준(어느 파일을 근거로 삼았는지)을 보고에 명시한다. (회고: 서술형 목표가 정밀 목표보다 도구 호출 2배 이상을 썼고 차이는 대부분 탐색이었다.)

## 2. 작업 순서 (CLAUDE.md 작업 순서의 개발 버전)

```
feature-spec.md 작성 → plan.md 작성 → (사람 승인 대기) → 구현 → 검증 명령어로 직접 확인 → PR 생성
```

- plan mode에서 계획만 세우고, 사람이 승인하기 전에는 코드를 수정하지 않는다.
- 구현 후 CLAUDE.md에 정의된 검증 명령어(빌드/테스트/린트)를 반드시 직접 실행하고 결과를 그대로 보고한다.

**검증 시점 (2026-09-01 회고): 매 편집마다 무거운 검증을 돌리지 않는다.**
- **빠른 테스트**(`npm test` — 문자열 정규식 검사라 빠르다)는 편집 중에도 자유롭게 돌린다.
- **무거운 검증**(`npm run build` ~30~60초, `npm run lint`, dev 서버 실렌더 확인)은 **작업이 끝났다고 판단한 시점에 한 번** 돌린다 — 중간 편집마다 반복하지 않는다.
- 이유: 회고에서 같은 163개 테스트+빌드가 세션 전체에서 15~20번 반복 실행됐다. 검증을 생략하라는 게 아니라, 완료 게이트에 모으라는 것이다. (사소한 지적 수정을 여러 번 반복할 땐 모아서 마지막에 한 번 검증한다 — `orchestrator-rules.md` "검수 깊이 조절" 섹션과 짝을 이룬다.)

## 3. 구현 시 체크리스트 (2026-08-31 결과 페이지 리뉴얼 회고에서 추가)

실제로 검수에서 반복 지적됐던 패턴이다. 구현을 마치기 전에 스스로 확인한다.

1. **문서 drift 방지**: 변경한 컴포넌트명·클래스 리터럴·폭 수치를 `storybook/`과 주변 파일 주석에서
   grep해, 이번 변경으로 거짓이 된 서술(스토리 데코레이터 폭, mdx 실사용처 목록, 옆 화면 주석 등)을
   **같은 커밋에서** 갱신한다. (같은 유형이 한 브랜치에서 4번 지적됨)
2. **짝 화면 정합**: 같은 플로우의 짝 화면(투표↔결과, 제출↔결과)과 커버·셸·토큰 처리가
   어긋나지 않는지 확인한다. 스코프 밖이면 고치지 말고 보고에 남긴다. (통합 리뷰에서야 발견되면
   막판 추가 커밋이 됨)
3. **주석에 티켓 번호 금지**: 코드 주석은 현재 규칙만 말한다. 어느 티켓에서 왔는지는 커밋 메시지 몫이다.
4. **검수 반영 커밋**: 리뷰 지적 반영은 기존 커밋 amend 대신 fixup 커밋으로 쌓고, 태스크 마감 시
   squash한다. (amend는 매번 보안 경고를 유발해 판별 소음이 됨)

## 4. 에스컬레이션 (개발 특화)

`orchestrator-rules.md`의 공통 기준 외에, 개발자 에이전트는 특히 아래 상황에서 반드시 사람에게 확인한다.

- 기존 데이터베이스 스키마, 프로덕션 데이터에 영향을 주는 변경
- 새로운 외부 라이브러리/패키지/서비스를 추가해야 하는 경우
- `feature-spec.md`/`plan.md` 범위 밖의 작업이 구현 중 필요하다고 판단될 때
- 보안, 인증/인가, 개인정보 처리 관련 로직 변경

질문 형식은 `orchestrator-rules.md`의 "질문 형식" 섹션을 그대로 따른다.

## 5. Sonnet에게 위임하는 기준

아래 조건을 **모두** 만족하는 작업만 Sonnet에게 위임한다.

- 병렬로 처리 가능 (다른 파일/모듈과 의존관계 없음)
- 스코프가 작음 (지정된 파일/디렉토리 범위 내에서 끝남)
- 판단이 거의 없음 (정해진 패턴을 반복 적용하는 수준)

**위임 가능한 예**: 보일러플레이트 코드 생성, 반복적인 타입/인터페이스 정의, 단순 포맷 변환, 이미 정해진 패턴으로 테스트 케이스 여러 개 작성

**위임하면 안 되는 예**: 아키텍처 결정이 필요한 작업, 여러 모듈에 걸친 리팩터링, 순서 조율이 필요한 작업

위임할 때는 Sonnet에게 `sonnet-subtask-scope.md`와 함께, 건드려도 되는 파일/디렉토리 범위를 명시해서 준다.

---

## 6. 하지 말아야 할 것

- plan.md 승인 없이 구현에 들어가지 않는다.
- 검증(빌드/테스트)을 생략하고 완료 보고하지 않는다.
- `feature-spec.md`에 없는 기능을 임의로 추가하지 않는다 (스코프 확장은 에스컬레이션 대상).
- main 브랜치에 직접 push하지 않는다 (`CLAUDE.md` Git/PR 규칙 참고).
