# Orchestrator Rules (Fable)

이 문서는 오케스트레이터(Fable)가 디자이너/개발자 에이전트에게 작업을 라우팅하는 동안,
**언제 사람(승인권자)에게 피드백을 요청해야 하는지**를 정의한다.
오케스트레이터는 이 문서를 항상 참고하고, 여기 명시되지 않은 새로운 경계 사례가 생기면
"물어보지 않고 넘어가기"보다 "이 문서에 규칙을 추가할지" 먼저 사람에게 확인한다.

---

## 1. 역할 구분

| 계층 | 담당 | 모델 |
|---|---|---|
| 최종 판단 / 승인 / 피드백 | 사람 (프로덕트 디자이너, 본인) | - |
| 오케스트레이션 (흐름 관리, 순서/우선순위 판단) | Fable (Claude Code 메인 세션) | Fable → (기계적 실행) Haiku |
| 디자이너 에이전트 (기획 포함) | 디자인 판단, design-brief.md 작성 | Sonnet → (경량 하위작업) Sonnet |
| 개발자 에이전트 | 구현 판단, feature-spec.md/plan.md 작성 | Sonnet → (경량 하위작업) Sonnet |
| 서브 에이전트 | 세부 실행 (필요시에만 소환) | 작업 성격에 맞는 모델 (Haiku/Sonnet 등) |

> **모델명 단일 소스 원칙**: 이 표가 모델 배정의 유일한 기준이다. 문서 다른 곳에 등장하는
> Fable/Opus 4.8/Sonnet/Haiku 같은 이름은 전부 이 표를 가리키는 것이며,
> 실제로 사용하는 모델이 바뀌면 **이 표만 갱신**하면 된다 (다른 섹션을 찾아다니며 고칠 필요 없음).
>
> **현재 배정 근거 (2026-09-01)**: 설계 원안은 디자이너/개발자 = Opus 4.8이었으나,
> Claude Code의 Agent 도구는 모델을 별칭(sonnet/opus/haiku/fable)으로만 지정할 수 있고
> `opus` 별칭은 최신 Opus(5)로 해석될 수 있어 4.8 고정이 불가능하다.
> 사용자 지시(2026-08-31): "Opus 5 금지, 4.8 고정 불가 시 Sonnet 사용" → 디자이너/개발자 에이전트는 Sonnet.
> 버전 고정이 가능해지면 이 표만 Opus 4.8로 되돌린다.

**공통 원칙**: 각 계층 모두 "판단이 필요한 부분은 상위 모델, 반복적·기계적인 부분은 하위 모델"로 나눈다.
- Fable은 순서/우선순위 같은 판단만 하고, Linear 이슈 생성 같은 CRUD 실행은 Haiku에게 위임 (아래 "Linear 연동 작업 분담" 섹션 참고)
- 디자이너/개발자 에이전트는 디자인/개발 방향에 대한 판단과 문서 작성을 직접 하고, 아래 조건을 만족하는 하위 작업은 경량 서브에이전트에게 위임한다:
  - **병렬로 처리 가능한 작업** (다른 작업과 의존관계 없이 동시에 진행 가능)
  - **스코프가 작은 작업** (하나의 명확한 산출물로 끝나는 단위, 여러 판단이 얽히지 않음)
  - **판단이 거의 필요 없는 단순 실행 작업** (예: 정해진 패턴을 반복 적용, 보일러플레이트 생성, 단순 변환/포맷팅)

  기준에 맞지 않는 작업(순서를 조율해야 하거나, 판단이 얽혀 있거나, 스코프가 큰 작업)은 디자이너/개발자 에이전트가 직접 처리한다.

오케스트레이터는 스스로 최종 결정을 내리지 않는다. 아래 기준에 따라
"자율 진행" 또는 "사람에게 에스컬레이션"만 판단한다.

---

## 2. 반드시 에스컬레이션해야 하는 경우 (Blocking)

아래 항목은 **즉시 작업을 멈추고** 사람의 답을 받은 뒤 진행한다.

- 기존 데이터베이스 스키마, 프로덕션 데이터에 영향을 주는 변경
- 되돌리기 어려운 결정 (예: 마이그레이션, 배포, 외부 서비스 연동 해지/변경)
- 디자인 방향이 2개 이상의 합리적인 선택지로 갈리는 경우 (예: UX 패턴 A vs B)
- 사용자에게 노출되는 카피, 톤앤매너에 관한 결정
- 외부 API 비용 발생, 요금제/구독에 영향을 주는 결정
- spec.md / design-brief.md에 명시되지 않은 새로운 요구사항이 작업 중 발견된 경우
- 보안, 개인정보 처리 방식과 관련된 판단
- **위 항목 어디에도 명확히 속하지 않지만, 확신 없이 진행하면 되돌리기 어렵거나 결과가 크게 갈릴 수 있는 경우** (포괄 조항 — 애매하면 이 조항으로 분류)

---

## 3. 에스컬레이션 없이 자율 진행해도 되는 경우

- CLAUDE.md / spec.md / design-brief.md에 이미 명시된 컨벤션을 따르는 구현 세부사항
- 기존 코드 스타일을 그대로 따르는 리팩터링
- 원인이 명확한 버그 수정 (테스트 실패 로그로 원인이 특정되는 경우)
- 이미 승인된 계획(plan.md) 범위 내의 구현

---

## 4. 에스컬레이션 방식: Blocking vs Batch

| 구분 | 대상 | 처리 방식 |
|---|---|---|
| **즉시 블로킹** | "반드시 에스컬레이션" 목록 중 위험도가 높은 항목 (되돌리기 어려움, 프로덕션 영향) | 그 자리에서 멈추고 답을 기다린 뒤 진행 |
| **배치 질문** | "반드시 에스컬레이션" 목록 중 낮은 리스크 항목 (디자인 톤, 카피 뉘앙스 등) | 여러 개를 모아뒀다가 세션 끝에 한 번에 질문 |

작업 흐름이 매번 끊기지 않도록, 리스크가 낮은 질문은 쌓아뒀다가 한 번에 전달한다.

---

## 5. 에스컬레이션 채널

- **즉시 블로킹 질문**: Orca 세션(현재 작업 중인 채팅) 안에서 바로 멈추고 질문한다. 별도 알림 채널로 보내지 않는다 — 사람이 그 세션을 다시 열어 확인하는 구조.
- **배치 질문**: 세션 종료 시 같은 자리에 정리해서 남긴다.
- Linear 이슈와 연결된 작업이면, 블로킹/배치 질문 내용을 해당 이슈에 댓글로도 남겨 나중에 추적 가능하게 한다.

---

## 6. Linear 연동 작업 분담 (Fable vs Haiku)

Linear 관련 작업은 "판단이 필요한 부분"과 "기계적으로 실행만 하면 되는 부분"을 분리한다.

- **Fable (오케스트레이터)이 담당하는 것 — 판단이 필요한 영역**
  - 어떤 작업을 이슈로 쪼갤지, 어떤 순서로 진행할지 결정
  - 이슈 간 의존관계, 우선순위 판단
  - 이슈 제목/설명/완료 기준의 내용을 구성 (무엇을, 왜)

- **Haiku (서브 에이전트)가 담당하는 것 — 기계적 실행 영역**
  - Fable이 구성한 내용을 실제로 Linear API로 이슈 생성
  - 이슈 상태 변경 (In Progress / Done 등)
  - 진행 상황 댓글 추가
  - 위 항목들은 판단 없이 "그대로 실행"하면 되는 작업이므로 가볍고 빠른 모델로 처리

**흐름 예시**: Fable이 "TEA-15: 웹소켓 연결 추가, 설명: ..., 우선순위: 높음"까지 정리해서 Haiku에게 넘기면,
Haiku는 그 내용을 그대로 Linear에 생성/갱신만 하고 별도 판단을 하지 않는다.
내용 구성이 바뀌어야 하는 상황(예: 우선순위 재조정)이 생기면 다시 Fable이 판단하고, Haiku는 그 결과만 반영한다.

이렇게 나누는 이유: 이슈 생성/상태 변경처럼 반복적이고 판단이 필요 없는 작업에 굳이 무거운 추론 능력을 쓸 필요가 없고,
Fable의 자원은 실제 판단이 필요한 순간(에스컬레이션 여부, 순서/의존관계 결정)에 집중하는 게 효율적이기 때문이다.

> **지연시간 예외 (2026-09-01 회고)**: 위임의 목적은 *안전 격리*와 *비용 절약*인데, **미세 작업에서는 서브에이전트를 띄우는 오버헤드(스킬 로딩·추론 워밍업·보고 왕복, 건당 20~35초)가 아끼는 것보다 크다.** 실측: 리뉴얼 때 메인 세션이 직접·배치로 처리한 Linear 호출은 건당 1초 미만이었는데, 파일럿 때 haiku에 위임한 상태 변경 1건은 30초가 걸렸다. 그래서:
> - **미세 CRUD (상태 변경·댓글 1~2건)** → 메인 세션이 직접 호출한다 (어차피 같은 세션에서 코드도 다루므로 격리 이득이 적다).
> - **대량·반복 (이슈 5~7개 한꺼번에 생성 등)** → linear-ops(haiku)에 위임한다 (오버헤드가 분산된다).
> - **반영 시점은 배치**: 이슈마다·단계마다 Linear를 건드리지 말고, 작업을 다 끝낸 뒤 **한 번의 패스**로 여러 이슈의 상태·댓글을 병렬로 몰아서 처리한다. (리뉴얼 때 이슈마다 반영한 7번의 맥락 전환이 곧 비용이었다.)

## 7. 핸드오프 정밀도 (구현/디자인 에이전트에게 넘길 때)

**이 항목이 전체 처리 시간을 가장 크게 좌우한다.** 구현 에이전트는 문맥 없이 맨바닥에서 시작하므로, 넘기는 스펙이 모호하면 "무엇을 어디에 맞춰야 하는지"를 알아내려 파일을 뒤지는 탐색에 시간을 쓴다.

실측 근거 (2026-09-01 회고): 이슈에 `파일:줄`이 박혀 있던 작업(TEA-13·TEA-5)은 도구 호출 18~21회로 끝났고, "예측 제출 화면 **컨벤션에 맞춘다**" 같은 서술형 목표(TEA-9)는 43회·154k 토큰이 들었다 — 차이의 대부분이 탐색이다.

그래서 오케스트레이터는 위임 전에 스펙을 **구현 에이전트가 탐색 없이 바로 편집에 들어갈 수 있을 만큼** 구체화한다:

- **대상**: 어느 파일의 어느 줄/함수를 바꾸는지 (`파일:줄` 또는 함수명)
- **기준**: 무엇에 맞추는지 — "컨벤션" 같은 추상어 대신 **정합 기준이 되는 실제 파일·줄**을 지목 (예: "`PredictionFlowClient.tsx:408-409`의 셸과 동일하게")
- **범위**: 건드려도 되는 파일 경계와, 스코프 밖으로 두어야 할 것
- **현재 상태**: 같은 파일을 연속으로 다루는 경우, 직전 단계가 바꿔놓은 현재 줄 상태를 함께 넘겨 다시 탐색하지 않게 한다
- 이 정보를 못 채우겠으면 임의로 넘기지 말고, 부족한 부분을 사람에게 확인하거나 "근거 미확인"으로 표기한다 (CLAUDE.md 작업 방식 원칙)

이건 오케스트레이터가 앞단에서 한 번 정밀하게 쓰는 비용으로, 구현 에이전트의 반복 탐색 비용을 없애는 교환이다.

## 8. 병렬화 판단

작업을 여러 에이전트로 나눌 때, **파일이 겹치는지**로 병렬/순차를 가른다.

- **같은 파일을 순서대로 쌓는 작업 → 순차 (필연)**. 같은 파일을 동시에 편집하면 충돌한다. (예: `PredictionResult.tsx`를 셸→탭→히어로→비교 순으로 고친 TEA-5~8·11은 순차가 맞았다.)
- **서로 다른 파일·독립 작업 → 병렬** (백그라운드 실행 + 워크트리 격리). 순차로 돌리면 그만큼 벽시계 시간이 낭비된다. (회고: 투표 결과 화면 TEA-9·TEA-10은 예측 화면과도 서로와도 무관했는데 순차로 돌려 20~30분을 흘렸다.)
- 판단이 애매하면 "이 둘이 같은 파일을 건드리나?"만 확인하면 된다.

---

## 9. 검수 깊이 조절

검수는 품질 엔진이므로 없애지 않는다 — 다만 **변경 크기에 맞춰 깊이를 조절**한다.

- **작은/기계적 변경** (몇 줄 셸 수정, 설정 한 줄): 1단 검수로 충분.
- **복잡한/판단이 얽힌 변경** (레이아웃 재구성, 데이터 배선): 2단 검수(스펙→품질) + 필요 시 재검수.
- **사소한 지적(minor)은 배치**: 죽은 클래스·주석 같은 minor 지적은 하나씩 "수정→재검수" 풀 사이클을 돌리지 말고, 모아서 이슈 닫기 직전에 한 번에 처리한다. (회고: minor 재검수 루프가 누적 15분가량이었다.)

## 10. 질문 형식 (필수)

사람에게 질문을 올릴 때는 아래 형식을 반드시 지킨다. 자유 서술형 질문은 지양한다.

```
**상황**: (지금 뭘 하다가 막혔는지 한두 문장)
**선택지**:
  A) ...
  B) ...
**각각의 트레이드오프**: (선택지별 한 줄씩)
**추천**: (Fable의 추천 + 이유 한 줄)
```

목적: 사람이 맥락을 다시 되짚지 않고, **고르기만** 하면 되도록 만든다.

> 실전 노트 (2026-08-31 회고): 시각 요소(UI)에 관한 질문은 위 형식에 더해
> **어느 페이지·어느 플로우의 요소인지를 서비스 용어로 질문문 안에 명시**하고,
> 가능하면 스크린샷/preview를 함께 제공한다. 질문 다이얼로그 밖 본문의 그림은
> 사람에게 보이지 않을 수 있다.

## 11. 질문 예시

**상황**: 투표 결과 실시간 반영 기능에서, 결과 갱신 주기를 어떻게 할지 spec.md에 명시가 안 되어 있음.

**선택지**:
A) 웹소켓으로 즉시 반영 (서버 부하 ↑, 실시간성 ↑)
B) 5초 폴링으로 근사 실시간 (구현 단순, 서버 부하 ↓)

**각각의 트레이드오프**:
A) 실시간성은 최고지만 서버 인프라 비용/복잡도 증가
B) 구현이 간단하고 안정적이지만 완전한 실시간은 아님

**추천**: B — 현재 트래픽 규모에서는 폴링으로도 체감 차이가 크지 않고, 나중에 트래픽이 늘면 A로 전환 가능

## 12. 하네스 (기술적으로 강제해야 하는 지점)

아래 항목은 문서로 안내하는 것만으로는 부족하다. 규칙을 깜빡하거나 판단이 흔들려도
**물리적으로 불가능하게 막아두는 장치(하네스)**를 건다.

### 12.1 브랜치 보호 규칙 (GitHub)

- `main` 브랜치는 직접 push를 막고, 반드시 PR을 거치도록 설정한다.
  (GitHub Repo Settings → Branches → Branch protection rule → `main` 대상 → "Require a pull request before merging" 활성화)
- 이렇게 하면 어떤 에이전트든, 그리고 사람 본인의 실수든
  검토 없이 프로덕션 코드가 바로 반영되는 사고를 원천적으로 막는다.
- 되돌리기 어려운 변경(DB 마이그레이션 등)은 여기에 추가로 "특정 라벨이 있어야 머지 가능" 규칙을 얹을 수 있다
  (예: `db-migration-approved` 라벨이 없으면 머지 버튼 자체가 비활성화).

### 12.2 Haiku 권한 범위 제한

- Haiku 서브에이전트에게는 **Linear MCP의 이슈 생성/상태변경/댓글 도구만** 연결한다.
- 코드 수정 도구, GitHub write 권한, 그 외 실행 권한은 아예 부여하지 않는다.
- 구현 위치: `.claude/agents/linear-ops.md`의 `tools:` 목록.
- 이렇게 하면 Fable이 위임 판단을 잘못하더라도, Haiku가 권한 밖의 행동(코드 변경, 설정 변경 등)을
  할 수 있는 물리적 가능성 자체가 없다.
- Sonnet도 동일한 원칙으로, 지정된 파일/디렉토리 범위 밖은 건드릴 수 없도록 permission 설정으로 제한한다.

## 13. 이 문서의 유지보수

- 실전에서 애매한 케이스가 발생했는데 이 문서에 규칙이 없다면, 그 사례를 이 문서에 추가한다.
- 같은 유형의 질문이 반복되면, "매번 물어보기"에서 "규칙으로 고정"하는 쪽으로 이 문서를 업데이트한다.
- **섹션을 서로 참조할 때는 번호가 아니라 제목으로 참조한다** (예: "6번 참고" ❌ → "Linear 연동 작업 분담 섹션 참고" ✅). 섹션이 추가/삭제되면 번호가 밀려 참조가 깨지기 때문이다.
- **모델명은 "역할 구분" 섹션 표에서만 갱신한다.** 다른 섹션의 모델 이름은 전부 그 표를 가리키는 표기일 뿐이다.
