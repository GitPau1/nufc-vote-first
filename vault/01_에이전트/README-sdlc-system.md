# nufc-vote SDLC 시스템 개요

이 문서는 왜 이런 구조를 만들었는지, 그리고 실제로 어떻게 작동하는지를 설명한다.
개별 규칙 파일(리포 루트 `CLAUDE.md`, 이 폴더의 `orchestrator-rules.md`, `designer-agent-rules.md`,
`developer-agent-rules.md`, `marketing-agent-rules.md`, `haiku-linear-ops.md`, `sonnet-subtask-scope.md`)을 처음 보거나,
시간이 지나 왜 이렇게 구성했는지 기억이 흐려졌을 때 이 문서로 돌아와서 맥락을 복구한다.

> 안착 노트 (2026-09-01): 원문의 독립 `CLAUDE.md` 템플릿은 별도 파일로 두지 않고
> **리포 루트의 기존 CLAUDE.md에 병합**했다 (기존 실사고 기반 규칙을 유지하기 위함).
> 규칙 파일들은 `vault/01_에이전트/`에, 작업별 동적 문서는 `vault/02_프로젝트/<Linear 프로젝트명>/`에 둔다.

---

## 1. 어떤 문제에서 시작했는가

nufc-vote는 기획-디자인-개발을 혼자 다 맡아서 운영하는 서비스다.
혼자 여러 역할을 겸하다 보니 실제로 겪은 문제는 세 가지였다.

- **다 처리할 수 없음**: 할 일이 쌓이는 속도를 혼자서 따라가지 못함
- **까먹음**: 왜 이 작업을 시작했는지, 어떤 제약이 있었는지가 시간이 지나면 사라짐
- **컨텍스트 소실**: 여러 작업을 동시에 진행하다 보면 작업 사이의 맥락이 서로 섞이거나 유실됨

AI 코딩 도구(Claude Code 등)는 "코드를 짜는 속도"는 크게 높여줬지만, 계획·리뷰·테스트·배포처럼
그 앞뒤를 감싸는 과정은 그대로 사람 손에 남아 있어서, 병목이 코드 작성에서 그 주변 과정으로 옮겨갈 뿐이었다.
이 구조는 그 병목을 다시 줄이기 위해, **AI에게 흐름 관리와 실행을, 사람에게는 최종 판단만** 남기는 방식으로 설계했다.

---

## 2. 전체 아키텍처

### 2.1 세 개의 축 (도구 레벨)

```
GitHub  ── source of truth (코드, intent/spec/plan 문서, PR 히스토리)
Linear  ── 진행상황 대시보드 (이슈/프로젝트 상태)
Orca    ── 실행 공간 (여러 에이전트를 격리된 워크트리에서 병렬 구동)
```

GitHub이 "진짜 기록"이고, Linear는 그 기록을 보기 좋게 보여주는 파생 뷰다. 어긋났을 때는
항상 GitHub 쪽을 기준으로 삼는다. Orca는 이 둘을 넘나들며 실제로 에이전트가 작업을 수행하는 공간이다.

### 2.2 네 개의 계층 (에이전트 레벨)

```
사람 (최종 판단 / 승인 / 피드백)
 └─ Fable (오케스트레이션: 흐름 관리, 순서/우선순위 판단)
     └─ Haiku (Linear 이슈 생성/상태변경 등 기계적 실행)
 └─ 디자이너 에이전트 / 개발자 에이전트 / 마케팅 에이전트 (판단 + 산출물 작성 — 배정 모델은 orchestrator-rules.md 표 참고)
     └─ Sonnet (병렬·저판단·소규모 하위 작업 실행)
```

각 계층은 같은 원칙을 반복한다: **판단이 필요한 부분은 상위 모델이 직접 하고,
반복적이고 기계적인 부분은 하위 모델에게 위임한다.** 이렇게 하면 상위 모델의 자원이
실제 판단이 필요한 순간에 집중되고, 반복 작업에 낭비되지 않는다.

## 3. 왜 문서를 이렇게 나눴는가

문서는 크게 두 종류로 나뉜다.

- **정적 문서** (역할이 유지되는 동안 계속 재사용) — 리포 루트 `CLAUDE.md`와 이 폴더의 역할별 규칙 파일들
- **동적 문서** (작업마다 새로 생성) — `intent.md` → `spec.md`(또는 `design-brief.md`/`feature-spec.md`) → `plan.md`
  - 위치: `vault/02_프로젝트/<Linear 프로젝트명>/` (프로젝트별 폴더)
  - **간소 사이클** (2026-09-01 확정): 소속 Linear 프로젝트가 없는 단발 이슈는 intent/spec/plan 파일을
    만들지 않는다 — Linear 이슈 본문을 spec으로 삼고, plan 승인 게이트만 거친다 (plan은 이슈 댓글/세션 보고로 남김).
  - **마케팅 상시 문서** (2026-09-04 추가): 신규 유저 확보 전략·브랜드 보이스·콘텐츠 캘린더처럼 특정
    기능/프로젝트에 안 걸리고 계속 갱신되는 마케팅 문서는 `vault/03_마케팅/`에 둔다 — Linear 이슈로 만들지
    않고 문서로만 관리한다. 기능에 딸린 홍보 문구(`marketing-brief.md`)는 기존 방식대로
    `vault/02_프로젝트/<프로젝트명>/`에 둔다. 상세 기준은 `marketing-agent-rules.md` 참고.

이 구분은 SDLC 플레이북 원문이 이미 쓰던 개념(정적 인프라 vs 작업별 산출물)을 그대로 따른 것이다.
정적 문서를 다시 역할별로 쪼갠 이유는, 디자이너와 개발자가 필요로 하는 정보 자체가 다르기 때문이다
— 개발자에게는 인터페이스·데이터 구조 같은 구체적 지시가 필요하지만, 디자이너에게는 그런 게 필요 없고
대신 톤·사용자 흐름·근거가 필요하다. 하나의 문서에 다 담으면 누구에게도 딱 맞지 않는 문서가 된다.

**공통 규칙(모두가 지켜야 할 것)은 리포 루트 `CLAUDE.md` 하나에만 적는다.** 역할별 파일에는
그 역할에서 공통 규칙이 어떻게 구체적으로 적용되는지만 적어서, 같은 내용이 여러 곳에
중복·모순되게 적히는 걸 막는다.

## 4. 실제로 어떻게 작동하는가 (한 사이클 예시)

예: "투표 결과 실시간 반영" 기능을 추가한다고 가정하면.

1. **Plan**: 사람이 Claude와 대화하며 아이디어를 `intent.md`로 정리하고 커밋. Fable이 Linear에
   프로젝트/이슈를 만들도록 판단하고, 실제 생성은 Haiku가 `haiku-linear-ops.md`의 입력 형식대로 실행한다.
2. **Design**: 필요하면 디자이너 에이전트가 `design-brief.md`를 작성한다. 톤이나
   UX 패턴이 애매하면 `orchestrator-rules.md`의 질문 형식대로 사람에게 확인한다. 간단한 카피 배리에이션
   같은 저판단 작업은 Sonnet에게 위임한다 (`sonnet-subtask-scope.md` 규칙 적용).
3. **Build**: 개발자 에이전트가 `feature-spec.md`와 `plan.md`를 작성한다. plan.md는
   사람이 승인하기 전까지 구현에 들어가지 않는다 (브랜치 보호 규칙과 별개로, 이건 워크플로우 규칙이다).
   승인 후 구현하고, 보일러플레이트 같은 반복 작업은 Sonnet에게 위임한다.
4. **Test**: 개발자 에이전트가 `CLAUDE.md`에 정의된 검증 명령어(빌드/테스트)로 스스로 확인한 뒤 보고한다.
5. **Deploy**: PR을 생성하고 `Fixes TEA-XX` 매직 워드를 포함시킨다. `main`은 브랜치 보호 규칙으로
   직접 push가 막혀 있어 반드시 PR을 거친다. 자동 상태 전환이 요금제 제약으로 막혀 있는 동안은
   머지 후 Linear 상태를 사람이 직접(또는 Fable→Haiku 경로로) Done으로 바꾼다.
6. **Maintain**: 반복되는 버그나 이상 징후를 발견하면, 사람이 트리거해서 새 `intent.md`를 만들고
   같은 사이클을 다시 시작한다.

이 흐름에서 사람이 실제로 개입하는 지점은 (a) 처음 아이디어를 던질 때, (b) plan.md 승인,
(c) 에스컬레이션된 질문에 답할 때, (d) 최종 PR/결과 확인 정도로 좁혀진다.

## 5. 안전장치: 문서만으로 안 되는 것

일부 규칙은 "지켜주길 바라는 것"만으로는 부족해서, 기술적으로 강제한다 (하네스).

- **브랜치 보호 규칙**: main 직접 push 자체를 막아, 검토 없는 반영 사고를 원천 차단
- **Haiku 권한 제한**: Linear 도구만 연결하고 코드/GitHub write 권한은 아예 안 줘서, 위임 판단이
  잘못되더라도 사고가 물리적으로 불가능하게 함
  - 구현 위치: `.claude/agents/linear-ops.md`의 `tools:` 목록 (Linear MCP 도구만 허용)

문서(규칙)로 충분한 영역과, 하네스(강제)가 필요한 영역을 구분하는 기준은 **"되돌리기 어려운가"**와
**"권한 남용이 가능한가"** 두 가지다. 둘 중 하나라도 해당하면 하네스를 건다.

## 6. 이 구조의 전제와 한계

- **오케스트레이터(Fable)는 최종 결정권이 없다.** 흐름과 우선순위만 판단하고, 애매하거나
  위험하거나 확신 없는 판단은 전부 사람에게 올린다. 이 경계가 `orchestrator-rules.md`의 핵심이다.
- **모델 이름은 시간이 지나면 바뀐다.** 그래서 `orchestrator-rules.md` 1번 섹션 표를 유일한
  기준으로 삼고, 다른 문서에서는 그 표를 참조하는 것으로 취급한다.
- **이 구조는 완성본이 아니라 계속 고쳐지는 문서 묶음이다.** 실전에서 애매한 케이스가 나오면
  해당 규칙 파일에 그 사례를 추가하고, 같은 유형이 반복되면 "매번 물어보기"에서 "규칙으로 고정"으로 옮긴다.
