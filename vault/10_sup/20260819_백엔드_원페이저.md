# NUFC Fan Poll
뉴캐슬 팬 대상 시즌 예측+포인트 도메인을 기존 Supabase 백엔드 안에 신규 구축

## 배경
NUFC Fan Poll은 뉴캐슬 유나이티드 팬을 위한 웹페이지로, 지금까지는 투표 기능만 제공해왔다. 투표만으로는 사용자 유입과 재방문을 늘리는 데 한계가 있어, 이번 개편에서 승부예측+포인트 도메인을 새로 추가한다.

## 문제 정의
- 사용자: 뉴캐슬 팬(1차), 축구 팬덤 커뮤니티(2차)
- 상황: 기존 투표 서비스는 참여 후 재방문 유인이 약해 D1 13.9% / D7 2.0%, 76%가 단일 방문 후 이탈. 예측+포인트 콘텐츠로 재방문 동기를 만들려는 것
- 한계: 신규 도메인은 아직 실사용 트래픽이 0명이라, 착수 시점엔 실제 데이터로 동작을 증명할 대상이 없음

## 범위
- 신규 도메인 테이블(경기·예측·포인트 원장) 설계 + RLS 정책
- 경기 CRUD(관리자 수동 입력)
- 예측 제출 API + 마감 시각 이중 차단(서버 검증 + DB 제약)
- 정산 배치(Vercel Scheduled Function) 및 포인트 원장 반영

## 완성 기준
- **검증 데이터**: 실제 프리미어리그 경기 일정·결과를 관리자가 수동 입력, 지인/테스터가 실제 계정으로 예측 제출
- **완료 판정**: 실제 경기 1라운드 이상에 대해 등록→예측 제출→마감 잠금→정산까지 오류 없이 완료되고, 정산 후 포인트 원장이 실제 경기 결과와 일치함을 수동 검증

## 안정성
- 마감 이후 예측 제출 → 서버 측(Route Handler/Server Action) 마감 시각 검증 + DB 제약으로 이중 차단
- 스키마 위반 입력 → 요청 payload 검증 + 구조화된 에러 응답
- 인증되지 않은 요청 → Supabase Auth 세션 검증 + RLS 정책으로 본인 데이터만 접근 허용
- 정산 중복 실행 → 이미 정산된 경기는 재실행되지 않도록 DB UNIQUE 제약 + 멱등 설계

## 재현성
- 정산 결과가 실행 시점에 따라 달라짐 → 경기 결과 confirm 이후에만 실행되는 고정 트리거로 통제
- 테스트마다 데이터가 달라짐 → 고정 픽스처(경기 결과·예측 세트)로 회귀 테스트 구성
- AI 기능 없음 — 비결정성 통제 해당 없음

## 설계 판단
- 기존 Supabase(Postgres+RLS)+Vercel 스택 재사용 — 별도 EC2/RDS 인프라 없이 신규 도메인 테이블만 추가, 기존 투표 서비스와 동일한 운영·배포 파이프라인 사용
- 인증은 Supabase Auth 그대로 — 별도 JWT 미들웨어 대신 RLS 정책으로 접근 제어
