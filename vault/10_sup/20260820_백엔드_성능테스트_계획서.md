## 1. 목표

평가 기준(백엔드) 중 성능 테스트가 직접 담당하는 배점:

| 배점 | 항목 | 성능 테스트와의 관계 |
|---|---|---|
| 20 | 성능 지표 | **p95 응답시간 · 처리량(RPS) · 에러율** 측정 |
| 15 | 재현성 | 고정 시드 데이터로 반복 측정 가능하게 |
| 15 | 문서·회고 | 병목 진단 근거와 한계 기술 |

> 상위 조건: **"병목을 찾아 개선 전후 수치를 제시"**

`p95 = 800ms` 하나로는 부족하고, **`810ms → 210ms (왕복 3회 → 1회)`** 형태여야 배점을 받는다.

## 2. 현재 상태 진단

### 2.1 코드로 확인한 실제 구성

| 항목 | 실제 |
|---|---|
| 백엔드 | Vercel 위 Next.js Server Action / Route Handler |

- 경기 · 예측 · 포인트 원장 **테이블 없음**
- 예측 제출 **엔드포인트 없음**

8/20 범위(테이블+RLS, 경기 CRUD, 예측 제출 API)가 착수 전이라 없는 API에 부하를 걸 수 없다.

## 3. 전제 정리 (검토 과정에서 확정된 판단)

### 3.1 측정 대상은 Supabase가 아니라 우리 코드다

응답시간의 구성:

```
사용자 -> Vercel 함수 (우리 코드)
           |- DB 왕복 1  <- 왕복 횟수: 우리가 결정
           |- DB 왕복 2  <- 인덱스 유무: 우리가 결정
           |- DB 왕복 3  <- 전송 행 수: 우리가 결정
        -> 응답
```

| Supabase 책임 | 우리 책임 |
|---|---|
| 서버 하드웨어, Postgres 패치, 가용성 | 왕복 횟수, 쿼리 모양, 인덱스, RLS, 전송량, 캐시, 리전 |

### 3.2 mock 모드로는 측정 불가

mock 모드는 DB를 호출하지 않는다.

- `queries/polls.ts:185` — `if (IS_MOCK) return mockGetPollList(page)`
- `actions/vote.ts:26` — 쿠키에 저장하고 즉시 반환

Postgres · PostgREST · RLS · 네트워크 왕복 전부가 실행되지 않으므로, 측정값은 "Node가 배열을 map 하는 속도"에 불과하다.

### 3.3 로컬 Docker Supabase는 불필요

- 현재 환경: docker 없음, supabase CLI 없음 (둘 다 설치 필요)
- `EXPLAIN ANALYZE`는 **네트워크를 포함하지 않으므로** 원격 Studio에서 실행해도 같은 값이 나온다
- 반대로 로컬은 왕복 지연이 0에 가까워 **왕복 병목이 보이지 않는다** — 틀린 결론으로 이어진다

→ staging Supabase 프로젝트를 새로 만드는 편이 싸고 정확하다.

### 3.4 Express 도입하지 않음

원페이저의 "기존 스택 재사용, 별도 EC2/RDS 없이" 판단을 유지한다. 평가 기준의 API 항목은 Route Handler로 충족된다.

## 4. 조회 API 흐름과 이 스택의 결정적 성질

```
1  클라이언트 (DNS + TLS)
2  Vercel Edge (CDN)
3  middleware.ts — 세션 갱신
4  Next.js 서버 함수 — 콜드스타트
   +- unstable_cache 히트? -> YES면 DB 미접근 (polls.ts:257, revalidate 30s)
5  supabase-js 호출   ★ DB 커넥션이 아니라 HTTPS 요청
6  PostgREST — URL -> SQL 변환, JWT 검증
7  PostgreSQL — RLS 평가 -> 실행계획 -> 인덱스/정렬
8  JSON 직렬화 -> 응답            (5~8이 왕복 1회)
9  Node에서 JS 가공
10 HTML 렌더
```

`supabase-js`는 Postgres에 직접 연결하지 않고 **PostgREST로 HTTPS 요청**을 보낸다.

| | Express + `pg` 직결 | Supabase JS (현재) |
|---|---|---|
| 왕복 1회 비용 | TCP 재사용, 순수 SQL | HTTPS + JSON 직렬화 + SQL 변환 |
| 왕복 추가 비용 | 싸다 | **비싸다** |
| 여러 쿼리 트랜잭션 묶기 | 가능 | 불가 (RPC로 감싸야 함) |
| 커넥션 고갈 | 위험 (풀 필수) | PostgREST가 자체 풀 관리 |

> **이 스택의 최적화 1순위는 쿼리 튜닝이 아니라 왕복 합치기다.**

## 5. 병목 후보 (코드 근거)

| 순위 | 위치 | 문제 | 부하 시 거동 |
|---|---|---|---|
| 1 | `queries/polls.ts:335` `getVoteCounts` | `votes`의 `option_id` **전량 조회 후 JS로 count** | 행 수에 선형. 1만 표 = 1만 행 전송 |
| 1 | `queries/polls.ts:93` | `rating_votes` 전량 조회 후 JS `Set`으로 중복 제거 | 동일 |
| 2 | `initial_schema.sql` 12곳 | `auth.uid()`가 `(select auth.uid())`로 감싸지지 않음 | RLS가 행마다 재평가 |
| 2 | `initial_schema.sql:169` | RLS 정책 내 `EXISTS` 서브쿼리 | 행마다 실행 (현재는 인덱스로 커버) |
| 3 | `polls` 테이블 | `polls(created_at DESC)` 인덱스 없음 (`created_by` 선행 인덱스만 존재) | `ORDER BY created_at DESC` 매번 전체 정렬 |
| 4 | `queries/polls.ts:201` fallback | 컬럼 에러 시 축소 쿼리 재시도 | 해당 경로 진입 시 왕복 2배 |
| 5 | `actions/vote.ts` | polls 조회 -> poll_options 조회 -> insert = 왕복 3회 | HTTP 왕복이라 비용 큼 |
| 6 | 리전 / 콜드스타트 | Vercel-Supabase 거리, 함수 첫 기동 | 워밍업 구간이 p95 오염 |

`getPollListUncached`는 왕복 3회지만 `Promise.all`로 2개가 병렬이라 실효 2홉 — 이 부분은 문제 없음.

## 6. 개선 후보 우선순위

| 순위  | 대상               | 방법                                                            | 효과             | 난이도 |
| --- | ---------------- | ------------------------------------------------------------- | -------------- | --- |
| 1   | RLS `auth.uid()` | 12곳 전부 `(select auth.uid())`로 래핑                              | 대량 스캔 시 배수     | 5분  |
| 2   | 정렬 인덱스           | `CREATE INDEX polls_created_at_idx ON polls(created_at DESC)` | Sort 제거        | 5분  |
| 3   | `getVoteCounts`  | RPC로 `GROUP BY` 이동 (N행 -> 5행)                                 | 데이터 늘수록 극적     | 낮음  |
| 4   | 왕복 합치기           | 검증+조회를 RPC 하나로                                                | 왕복당 수십 ms x 횟수 | 중간  |
| 5   | 캐시 확대            | `unstable_cache` 적용 범위 확대                                     | 히트 시 DB 홉 0회   | 낮음  |
| 6   | 집계 테이블           | 카운터 컬럼 + 트리거, 또는 Materialized View                            | 3번으로 부족할 때     | 중간  |
| 7   | 리전 정렬            | Vercel 함수 리전 = Supabase 리전                                    | 왕복당 수십 ms      | 낮음  |

1·2번은 각각 5분이며 측정에 잡힌다. 여기서 시작한다.

## 8. 시드 데이터 — 목데이터가 아니라 대량 데이터

데이터가 적으면 병목이 드러나지 않는다.

| 표 수 | 전송 행 | 결과 |
|---|---|---|
| 100 | 100 | 빠름 — "문제 없음" 오진 |
| 10,000 | 10,000 | 느려짐 |
| 100,000 | 100,000 | 확실히 드러남 |

실제 스키마(`initial_schema.sql`) 기준 시드:

```sql
-- 유저 10만 명
INSERT INTO public.users (id, email, display_name)
SELECT gen_random_uuid(), 'load' || i || '@test.local', 'tester' || i
FROM generate_series(1, 100000) AS i;

-- 부하 테스트용 투표 1건 + 선택지 5개
INSERT INTO public.polls (id, type, title, closes_at)
VALUES ('00000000-0000-0000-0000-000000000001', 'selection',
        '[LOAD TEST] 최우수 선수', now() + interval '30 days');

INSERT INTO public.poll_options (poll_id, label, display_order)
SELECT '00000000-0000-0000-0000-000000000001', '선수 ' || i, i
FROM generate_series(1, 5) AS i;

-- 표 10만 개 (UNIQUE(poll_id, user_id) 이므로 유저당 1표)
INSERT INTO public.votes (poll_id, user_id, option_id)
SELECT '00000000-0000-0000-0000-000000000001',
       u.id,
       (SELECT id FROM public.poll_options
        WHERE poll_id = '00000000-0000-0000-0000-000000000001'
        ORDER BY random() LIMIT 1)
FROM public.users u
WHERE u.email LIKE 'load%@test.local';
```

- 제목에 `[LOAD TEST]` 접두사를 붙여 정리 가능하게 한다.
- 이 스크립트를 파일로 유지하는 것 자체가 평가 기준 "재현성" 항목의 산출물이다.
- 주의: `users`는 `auth.users` 트리거로 동기화되는 테이블(`20260528_fix_user_trigger.sql`)이다. 직접 INSERT한 행은 로그인 가능한 계정이 아니다. **인증 API 측정용으로는 Auth에 실제 테스트 계정 10~20개를 별도 생성**해 토큰을 순환 사용한다.

## 9. 측정 항목별 도구와 실행 위치

| 측정 항목 | 도구 | 실행 위치 | 산출물 |
|---|---|---|---|
| SQL 실행시간, 인덱스 효과 | `EXPLAIN ANALYZE` | staging Studio SQL Editor | "Seq Scan+Sort 400ms -> Index Scan 3ms" |
| RLS 정책 비용 | `EXPLAIN ANALYZE` (테스트 유저 세션) | 동일 | `(select auth.uid())` 전후 비교 |
| **p95 / RPS / 에러율** | **k6** | 내 PC -> Vercel preview 배포 | 리포트 메인 수치 |
| 테스트 커버리지 | `node --test` | 로컬 (DB 무관) | 커버리지 % |

k6 쏘는 위치:

| 방식 | p95에 포함되는 것 | 용도 |
|---|---|---|
| 내 PC -> localhost (`next start` + staging DB) | 내 PC 성능 + 인터넷-Supabase 왕복 | 개선 전후 상대 비교 |
| 내 PC -> **Vercel preview 배포** | 실제 사용자가 겪는 전 구간 | **리포트용 메인 수치** |

### 측정 시 주의

- **워밍업 구간 버리기** — 콜드스타트가 p95를 오염시킨다.
- **fallback 경로 확인** — `polls.ts:201`이 타면 왕복이 2배가 되어 엉뚱한 병목을 잡게 된다.

## 13. 실행 순서

1. k6 설치 — `winget install k6`
2. staging 프로젝트 생성 + 마이그레이션 push + 시드 SQL 작성
3. **기존 투표 조회 경로로 베이스라인 측정** — 측정 파이프라인을 먼저 검증 (신규 API를 기다리지 않음)
4. 5분짜리 개선 2개 적용 (RLS 래핑 + 인덱스) → 재측정 → 첫 전후 수치 확보
5. 예측 제출 API를 Route Handler로 구현 → 왕복 3회 측정 → RPC 1회로 개선 → 재측정

3번을 선행하면 "측정 대상 부재" 문제와 무관하게 측정 체계를 먼저 세울 수 있다.

## 14. 기존 개선 방향 보고서 검토 결과

`Supabase 기반 백엔드 성능 개선 방향 보고서.md` 총평: **일반론으로는 정확, 이 프로젝트 문서로는 부적합.**

| 판정 | 내용 |
|---|---|
| 유지 | 4~5장 Round Trip / Batch UPSERT 원칙, 6장 우선순위(캐시는 마지막) |
| 수정 1 | "Edge Function" 전제 → 미사용 기술. Route Handler / Server Action으로 치환 |
| 수정 2 | 예시가 뉴스 수집 서비스 → 이 프로젝트의 정산 배치로 교체 (논리는 그대로) |
| 수정 3 | "단순 조회는 프론트가 DB 직접" → 방향 반전 필요 |
| 누락 1 | RLS 정책 비용 · 커넥션 풀링 · 리전 (Supabase 특화 병목 3개) |
| 누락 2 | 측정 방법 전체 — EXPLAIN ANALYZE, k6, 전후 비교표, 재시도/멱등성 |
| 누락 3 | 우리 코드의 실제 병목 인용 |

### 수정 3의 근거

1. **캐시가 사라진다** — `unstable_cache(revalidate:30)`는 30초에 1회만 DB를 친다. 프론트 직접 조회는 사용자 수만큼 요청이 늘어 역효과.
2. **3대 제약이 깨진다** — "결과는 참여 후 공개" 로직이 서버 쿼리 계층에 있다(`getRatingResults(poll, userId)`). 클라 조회로 옮기면 전부 RLS로 재구현해야 하고 하나만 빠져도 결과가 사전 노출된다.
3. **프론트엔드 원페이저와 충돌** — 서버 렌더를 걷어내면 Lighthouse 점수가 하락한다.
4. **평가 대상을 스스로 지운다** — API 레이어를 없애면 입력 검증·구조화된 에러·요청 한도·요청 로깅을 넣을 자리가 사라진다.

## 부록 A. 이 계획서를 읽기 위한 CS 개념

★ = 없으면 문서가 읽히지 않는 것.

### A.1 네트워크
- ★ RTT(왕복 시간) — "왕복 3번이면 150ms"의 근거
- ★ 지연(latency) vs 처리량(throughput) — p95와 RPS를 따로 재는 이유
- ★ 네트워크 지연은 거리에 비례 — 리전 정렬이 개선 항목인 이유
- TCP 3-way / TLS handshake — HTTP 왕복이 `pg` 직결보다 비싼 이유
- 커넥션 재사용(keep-alive, 커넥션 풀)
- DNS 조회, HTTP 상태코드(429), JSON 직렬화 비용

### A.2 통계·측정
- ★ 백분위(p95/p99), 평균의 함정, 롱테일
- ★ 워밍업 구간 / 이상치 제거 — 콜드스타트 오염 방지
- ★ 베이스라인, 통제 변수 — 개선 전후 비교의 전제

### A.3 DB 쿼리 실행
- ★ 실행 계획, `EXPLAIN ANALYZE` (네트워크 미포함)
- ★ Seq Scan vs Index Scan, B-tree 인덱스
- ★ **복합 인덱스의 선행 컬럼(leftmost prefix)** — `(created_by, created_at)`이 `ORDER BY created_at`에 쓰이지 않는 이유
- 인덱스의 쓰기 비용, 정렬(Sort) 연산, 카디널리티/선택도, JOIN 전략
- ★ 집계(`GROUP BY`, `COUNT`)

### A.4 DB 구조·무결성
- ★ 제약조건(UNIQUE/FK/CHECK), UPSERT(`ON CONFLICT`)
- ★ 멱등성(idempotency), 트랜잭션/ACID
- 정규화/비정규화, Materialized View, 트리거, DB 함수(RPC), 페이지네이션

### A.5 알고리즘·복잡도
- ★ O(n) vs O(log n) vs O(1) — "행 수에 선형"
- ★ 데이터가 적으면 복잡도 차이가 보이지 않는다 — 100행 목데이터 오진의 원인
- ★ N+1 문제, Amdahl의 법칙(병목의 정의)
- 연산을 데이터 쪽으로 옮기기(push computation down), 배치 처리

### A.6 캐시
- ★ 캐시 히트/미스, TTL(revalidate)
- stale 허용(정합성-성능 트레이드오프), 캐시 무효화, 캐시 계층, CDN

### A.7 동시성·부하
- ★ VU(가상 사용자), 부하 테스트 유형(load/stress/spike/soak)
- ★ 커넥션 풀 / 커넥션 고갈 — 부하 시 에러율이 급증하는 주원인
- 큐잉 이론(포화점에서 대기가 비선형 증가), 백프레셔/레이트 리미팅, 경쟁 조건, 낙관적/비관적 락

### A.8 서버 아키텍처
- ★ 서버리스 vs 상주 프로세스, 콜드 스타트, stateless
- BaaS, 관리형 서비스의 책임 경계, SSR/CSR/서버 컴포넌트, 미들웨어

### A.9 API 설계
- ★ REST, RPC, PostgREST
- 입력 검증/신뢰 경계, 구조화된 에러, 재시도와 지수 백오프(멱등성이 전제)

### A.10 인증·인가
- ★ 인증 vs 인가
- ★ RLS(행 단위 인가)와 **행마다 실행된다**는 성질
- 상수 폴딩/표현식 캐싱 — `(select auth.uid())`가 빠른 원리
- JWT, 세션 쿠키 vs Bearer 토큰, service role

### A.11 실험 설계·관측성
- ★ 재현성, 고정 시드 데이터(fixture), 환경 분리(dev/staging/prod)
- 관측성 3요소(로그/메트릭/트레이스), 테스트 커버리지, 회귀 테스트

### A.12 학습 순서

### A.13 판단이 갈린 세 개념

이 문서의 결론 세 개가 정확히 이 개념들에 걸려 있다.

1. **`EXPLAIN ANALYZE`는 네트워크를 포함하지 않는다** → 로컬 Docker 스택 불필요 (7장)
2. **복합 인덱스는 선행 컬럼 조건에만 쓰인다** → `polls(created_at DESC)` 인덱스 필요 (5장)
3. **RLS 정책은 행마다 실행된다** → `(select auth.uid())` 래핑이 배수 차이를 만든다 (6장)
