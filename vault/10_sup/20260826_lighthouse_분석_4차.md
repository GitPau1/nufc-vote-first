## 2. [중요] Best Practices 회복은 hydration 수정이 아니다

3차의 최우선 과제였던 hydration mismatch는 **전혀 손대지 않은 상태**다. 근거:

| 확인 항목 | 3차 | 4차 |
|---|---|---|
| `errors-in-console` score | 0 | **0 (그대로 실패)** |
| 콘솔 에러 | React #418 / #423 / #425 ×4 = 6건 | **동일한 6건** |
| 에러가 난 청크 | `fd9d1056-96ce47984f4dfdd7.js` | **동일 해시** |

에러 스택의 청크 해시가 같다는 것은 그 번들이 재빌드조차 되지 않았다는 뜻이다(같은 배포에서 CSS 청크는 `bed0387d…` → `c9b7fede…`로 바뀌었으므로, 배포 자체는 있었다). **SSR HTML을 버리고 root 전체를 클라이언트에서 다시 그리는 상태(#423)가 유지되고 있다.**

### 그럼 23점은 어디서 왔나

`inspector-issues`(0 → 1)와 `third-party-cookies`(0 → 1)가 통과했다. 3차에서 이 두 항목을 실패시킨 원인은 두 가지였다:

| 원인 | 3차 | 4차 |
|---|---|---|
| `images.fotmob.com`이 심는 Hotjar 쿠키 (`_hjSessionUser_*`, `_hjSession_*`) | 이미지 5건 | **fotmob 요청 0건** — Supabase Storage로 이전됨 |
| Mixpanel `track`/`engage`의 `_gd_visitor`, `mp_user` 등 | 요청 3건 | **요청 0건** |

fotmob 제거는 3차 리포트 4번에서 예측한 부수효과("fotmob 이미지를 프록시하면 서드파티 쿠키 문제도 절반 자동 해결")가 그대로 실현된 것이다. **Mixpanel 요청이 이번 측정에서 아예 안 뜬 이유는 근거 미확인** — 두 측정 모두 구글 아바타(`lh3.googleusercontent.com`)를 받았으므로 로그인 상태는 같다. 제거된 건지, 측정 시간 안에 안 발사된 건지 확인이 필요하다. **Mixpanel이 다시 발사되면 Best Practices는 다시 내려간다.**

> **결론: BP 96은 안정적으로 확보한 점수가 아니다.** 남은 4점(`errors-in-console`)이 3차에서 지목한 진짜 문제이고, 통과한 부분은 분석 도구 재활성화 시 되돌아온다.

## 3. [새 회귀] team-logos의 Cache-Control이 0이다

이미지 호스트 이전의 대가로 **캐시 수명이 사라졌다.**

| URL | 3차 (fotmob) | 4차 (Supabase) |
|---|---|---|
| 팀 로고 10261 (17KB) | TTL **7일** | TTL **0** |
| 팀 로고 8659 (13KB) | TTL **7일** | TTL **0** |

`cache-insight`가 0.5 → **0**으로 떨어진 직접 원인이다. 히어로 최상단 이미지 30KB를 **재방문 때마다 다시 받는다.** fotmob에서는 공짜로 얻던 캐시를 잃은 것이므로, 이전 작업 자체는 옳아도 이 한 줄은 회귀다.

`3798a6a`에서 업로드 시 `cacheControl: '31536000'`을 추가했는데, **team-logos 버킷 파일들은 그 경로를 타지 않고 올라간 것으로 보인다.** poll-thumbnails 3건은 여전히 TTL 1시간(3차와 동일, 기존 파일 미적용분)이다.

**조치**: team-logos 파일 재업로드 또는 Storage 객체 메타데이터 일괄 갱신. 3차 4번의 "기존 Supabase 썸네일 Cache-Control 재설정"과 같은 작업이므로 **한 번에 처리하면 된다.** 규모: 일회성 스크립트 하나.

## 4. LCP 요소가 텍스트 → 이미지로 바뀌었다 (콘텐츠 변화)

두 측정의 홈 첫 화면이 다르다.

| | 3차 (08-25 20:16) | 4차 (08-26 09:31) |
|---|---|---|
| 히어로 | 지난 경기 **평점 결과** (2-2 리버풀, 선수 사진 3장) | 다음 경기 **승부예측 카운트다운** (EFL Cup, 팀 로고 2장) |
| 히어로 높이 | 큼 (선수 카드 3개) | 작음 (카운트다운 + 버튼) |
| LCP 요소 | 텍스트 (breakdown에 TTFB + renderDelay만) | **투표 카드 썸네일 IMG** (`top:448`) |
| 이미지 요청 | 13건 / 206KB | 8건 / 159KB |

히어로가 짧아지면서 투표 카드 썸네일이 첫 화면 안으로 올라왔고, 그게 LCP 요소가 됐다. 그래서 이번에 `lcp-discovery-insight`가 처음 등장하면서 **실패(score 0)**했다:

```
priorityHinted     : false   ← fetchpriority=high 프리로드 없음
requestDiscoverable: true
eagerlyLoaded      : true
```

LCP 이미지가 CSS/JS 파싱 뒤에야 발견되므로 시작이 늦다(관측 breakdown: 로드 지연 33ms + 로드 45ms + **elementRenderDelay 291ms**). renderDelay가 여전히 지배적이고, 이건 2번의 root 재렌더 비용이다.

**조치**: 3차 4번의 `next/image` 전환(PollCard부터)이 그대로 답이다. `priority` 지정으로 `fetchpriority=high`가 자동으로 붙는다. 별도 작업이 필요한 게 아니다.

> **측정 방법 경고**: 홈 히어로가 경기 일정에 따라 매일 바뀌므로 **회차 간 성능 점수 비교가 흔들린다.** 이번 Performance 3점 하락도 상당 부분 여기서 온다. 개선 전후를 비교하려면 콘텐츠가 고정된 페이지(예: 특정 투표 상세 URL)를 **보조 기준선**으로 함께 측정해야 한다.

## 5. 폰트 — 오히려 늘었다 (262KB → 282KB, 조각 10 → 11)
