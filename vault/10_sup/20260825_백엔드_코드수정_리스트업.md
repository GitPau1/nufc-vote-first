### A-2 — ⏸ 보류: 기획·화면 변경 후 착수 (2026-08-25 결정)

**결정**: 평점 결과 화면의 기획·화면이 변경될 예정이라, **변경이 끝난 뒤에 착수한다.**

지금 멈추는 이유는 측정 데이터 부재가 아니라 **대상이 움직이기 때문**이다. 필요한 쿼리 형태가 화면에 직접 매여 있다:

| 현재 화면이 요구하는 것 | 대응 코드 |
|---|---|
| 선수별 평균·건수 | `polls.ts:502~505` JS 집계 |
| 선수별 코멘트 **상위 3개** | `OverallRatingResultView.tsx:81` `slice(0, 3)` |
| "전체보기"로 **전량 펼침** | 같은 파일 `expandedPlayerId` 분기 |
| 정렬 = 좋아요순 → 최신순 | `polls.ts:522` JS `sort` |

이 넷 중 무엇이 남는지에 따라 해법이 달라진다 — 특히 "전체보기 전량 펼침"이 유지되는지가 `limit` 상한을 정할 수 있는지를 가른다. 화면 확정 전에 뷰를 짜면 그 뷰를 다시 짜게 된다.

#### 화면이 바뀌어도 유지될 설계 방향 (합의됨)

**점수와 코멘트를 분리한다.** 둘은 저장 성질부터 다르다(`actions/ratings.ts:75~85`):

| | 점수 | 코멘트 |
|---|---|---|
| 필수 여부 | **전원 필수** (`hasEveryTarget` 검사) | **선택** — 비면 `null` |
| 1인당 행 | 14 (선수 수) | 0 ~ 14, 보통 0~2 |
| 필요한 연산 | **집계** (평균·건수) | **목록** (본문·작성자·좋아요) |

- 평균·건수 → **뷰에서 `avg(score)`, `count(*)`** (A-1의 `rating_poll_participants`와 같은 패턴). poll×선수 = 14행 응답이라 캡과 무관해진다
- 코멘트 → **`.not('comment','is',null)`**로 실제 쓴 것만. 대부분이 `null`이라 행 수가 급감한다

이 분해는 화면이 어떻게 바뀌든 유효하다. 화면에 따라 달라지는 건 **코멘트 쪽 상한을 어떻게 잡느냐**뿐이다.

#### 착수 시 남아 있을 결정 하나 — 코멘트 정렬

`like_count`가 임베디드 집계(`rating_vote_likes(count)`)라 **PostgREST에서 그걸로 `order`를 못 건다.** 코멘트에 `limit`을 걸면 "좋아요 상위 N"이 아니라 "아무거나 N개"가 온다.

| 안 | 내용 | 천장 |
|---|---|---|
| 가벼운 안 | 코멘트 필터 + 넉넉한 `limit`(예: 500), JS 정렬 유지 | 코멘트 500개 초과 시 상위권이 틀어짐 |
| 정확한 안 | 뷰에 `like_count`까지 넣고 `row_number() over (partition by target_player_id ...)` | 없음. 단 "전체보기"가 상위 N까지만 |

새 화면이 "전체보기"를 유지하지 않으면 **정확한 안이 오히려 자연스러워진다** — 이것도 화면 확정을 기다리는 이유다.

#### 발현 임계 — 급하지 않다

```
1,000행 ÷ 14선수 = poll당 참여자 71명부터
```

캡은 요청 하나(= poll 하나)에 걸리므로 DAU가 아니라 **한 투표의 참여자 수**가 기준이다. prod 현재 참여자 2명. A-1(임계 14명)과 달리 여유가 있다.

### A-2 원 실측 — 캡 재현 완료 (2026-08-25)

staging 실측(2026-08-25). `getRatingResults`와 같은 형태의 select를 평점 poll 1개에 날렸다:

```
GET /rest/v1/rating_votes?select=id,target_player_id,user_id,score,comment&poll_id=eq.02102b1c…
HTTP/1.1 206 Partial Content
Content-Range: 0-999/1400
```

| 항목 | 받은 값 | 실제 |
|---|---|---|
| 행 수 | 1,000 | 1,400 |
| 선수별 건수 | 8명이 71건, 6명이 72건 | 전원 100건 |

에러 없이 206 + 정상 JSON이라 코드 어디서도 잡히지 않는다.

**범위 결정에 필요한 값은 아직 못 얻었다.** UI(`OverallRatingResultView.tsx:81`)는 선수별 상위 3개만 쓰고 정렬이 JS라 단순 `limit`으로는 상위 3개가 틀려진다. 어느 해법을 쓸지는 "코멘트 달린 행의 비율"에 달렸는데,

- staging 시드는 `comment`를 넣지 않는다(`seed-target-scale.mjs`의 rating_votes payload에 필드 없음) → 코멘트 0건
- prod는 참여자 2명이라 표본이 안 된다

즉 **실측할 데이터가 아직 어디에도 없다.** 시드에 코멘트를 섞도록 고치거나, prod에 실사용이 쌓일 때까지 기다려야 한다.

### A-1·A-2 최초 분석 (2026-08-25 기록, 이후 갱신됨)

> A-1은 뷰로 해결됐고, A-2의 방향은 위 "화면이 바뀌어도 유지될 설계 방향"으로 정해졌다. 아래는 당시 판단 근거로 남긴다.

임베디드 집계(`votes(count)`)로 안 풀린다. 성격이 다르다.

| 함수                           | 필요한 연산                | 왜 임베디드 집계로 안 되나              | 필요한 접근                               |
| ---------------------------- | --------------------- | ---------------------------- | ------------------------------------ |
| `getRatingParticipantCounts` | **중복 제거된 참여자 수**      | `count()`는 행 수라 선수 수만큼 과다 집계 | `COUNT(DISTINCT user_id)` → RPC 또는 뷰 |
| `getRatingResults`           | 표시용 평점 목록(작성자·코멘트 포함) | 집계가 아니라 목록이다                 | 페이지네이션 또는 명시적 `limit` 정책             |

당시 판단 포인트는 "새 개념(`.rpc()`) 도입 여부"였다. 결론은 **뷰** — `week_leaderboard` 등 기존 개념이라 `.rpc()`(리포 내 사용처 0건)를 새로 들이지 않았다. A-2도 같은 방식으로 간다.

#### `createPublicClient`를 쓴 이유

#### 캐시 오염이 구조적으로 불가능한 이유

캐시되는 함수의 반환값에 사용자별 필드가 **아예 들어가지 않는다.** `isMe`는 캐시 밖에서 붙는다. 캐시 안에 `isMe`를 넣었다면 남의 하이라이트가 보였을 자리다.

### B-2 — ⏸ 보류: 탈퇴 사용자 정책 확정 후 착수 여부 결정 (2026-08-25) + ⚠️ 원 서술 정정

**결정 (2026-08-25)**: 이 항목은 **탈퇴한 사용자를 화면에 어떻게 다룰지가 기획에서 정해져야 진행할 수 있다.** 정책이 나온 뒤 **착수 여부 자체를 다시 결정한다** — 정책에 따라 3안(폐기)이 답일 수도 있다.

기술적 준비는 끝나 있다: 해법은 아래 "정정 ③"의 클라이언트 교체 5줄이고, migration도 FK도 필요 없다. 막고 있는 것은 코드가 아니라 **"탈퇴자가 만든 투표를 화면에 뭐라고 표시할 것인가"**라는 기획 결정 하나다(아래 "착수 전 결정 필요" 표).

성능 관점의 시급성은 없다 — `unstable_cache(30)` 안이라 30초에 1회 실행되고 이미 `Promise.all`로 병렬이다.

---

#### 원 서술 정정 (2026-08-25 실측). 근거도 해법도 원 서술과 다르다

> 원 서술: *"`queries/comments.ts`가 쓰는 `public_profiles` FK 조인 패턴으로 본 쿼리에 합치면 세 문제(인스턴스 생성·왕복·RLS 우회)가 같이 사라진다."*
>
> **근거 하나가 틀렸고, 제시한 해법은 실제보다 비싸다.** 아래로 대체한다.

#### 이 코드가 하는 일

투표 목록/상세에 **작성자 이름**(`creator_name`)을 붙인다. `polls.created_by`(uuid)만으로는 이름을 모르니 목록을 읽은 뒤 그 uuid들로 `users`를 한 번 더 조회한다.

```
polls 조회 (anon, createPublicClient)
   └─ getCreatorNamesById(uuid[])   ← 여기서 service-role 클라이언트를 새로 만들어 users 조회
```

호출부 2곳: `polls.ts:203`(목록 `mapPollRows`), `polls.ts:387`(상세 `getPollById`).

#### 정정 ① — "RLS를 통째로 우회한다"는 과장이다

`20260821092457_remote_schema.sql:1123`에 이미 공개 읽기 정책이 있다:

```sql
create policy "users: public read profile" on "public"."users"
  for select to public using ((deleted_at IS NULL));
```

**anon 키 실측 (prod `xrvz…`, 2026-08-25):**

| 쿼리 | 결과 |
|---|---|
| `users?select=id,display_name,deleted_at` | **200** — `display_name`까지 그대로 읽힘 |
| `public_profiles?select=id,display_name` | **200** |

service-role로 추가로 얻는 것은 사실상 **하나뿐** — `deleted_at`이 찍힌 **탈퇴 사용자의 이름**이다.

#### 정정 ② — 실제 가치는 성능·보안이 아니라 정확성이다

| 원 문서의 근거 | 실측 후 |
|---|---|
| RLS 통째로 우회 (보안) | ❌ 과장. anon과 읽히는 행이 거의 동일 |
| 왕복 ≈28ms (성능) | ⚠️ 미미. `unstable_cache(30)` 안이라 30초에 1회, 그마저 `Promise.all`로 이미 병렬 |
| — (원 문서에 없음) | ✅ **탈퇴 사용자 이름이 투표 목록에 계속 노출된다** ← 이게 진짜 결함 |
| — (원 문서에 없음) | ✅ 공개 목록 경로에서 service-role 키를 쓰는 표면 축소 |

#### 정정 ③ — `public_profiles` FK 조인은 **지금 불가능**하고, 필요하지도 않다

`public_profiles` FK는 `comments`·`rating_votes`·`player_comments`에만 있다. **`polls.created_by`에는 없다**(`grep` 확인). 원 문서의 해법을 그대로 하려면 **새 migration으로 FK 추가** + `POLL_LIST_SELECT` 2종(본/fallback) 수정 + 상세 경로 수정이 필요하다.

필요한 건 그게 아니다. **클라이언트만 교체하면 된다:**

```
AS-IS  동적 import + createServiceClient(...)                      (5줄)
TO-BE  호출부가 이미 들고 있는 anon 클라이언트를 인자로 받아 사용
```

`users: public read profile` 정책이 있어 anon으로 읽히고(위 실측 200), `deleted_at IS NULL` 필터가 **정책 쪽에서 자동 적용**된다. **migration 0건, FK 0건, `public_profiles` 등장 0건.**

#### 착수 전 결정 필요 — 탈퇴자 표시 방식 ← **기획 대기 중인 항목**

고치면 탈퇴 사용자가 만든 투표의 `creator_name`이 `null`이 된다. 그런데 현재 UI는 `created_by`가 있어도 `creator_name`이 없으면 **관리자 투표로 판정**한다:

```tsx
// PollCard.tsx:76, PollHeroCard.tsx:23, ResultView.tsx:70,149, TypeAPollClient.tsx:52, TypeBPollClient.tsx:65
creator_type: poll.created_by && poll.creator_name ? 'user' : 'admin'
// ResultView.tsx:104
<span>{poll.creator_name ?? 'Admin'}</span>
```

→ **탈퇴자가 만든 투표가 "Admin"으로 표시된다.** 지금(탈퇴자 실명 노출)보다 나은지는 기획 판단이라 코드에서 정하지 않는다.

| 안 | 내용 | 비용 |
|---|---|---|
| 1 | 그대로 `Admin` 표시 | 쿼리 5줄만. UI 변경 0 |
| 2 | `탈퇴한 사용자` 등 별도 표시 | UI 6곳 수정. **새 개념이라 사용자 확인 필요** |
| 3 | 탈퇴자 이름 노출이 문제가 아니라고 보면 **B-2 폐기** | 남는 이득은 service-role 표면 축소뿐 |

**결론: 진행할 가치는 있으나 원 문서에 적힌 이유 때문이 아니다.** 성능 개선으로는 가치 없고, **탈퇴 사용자 이름 노출을 막는 정확성·프라이버시 수정**으로 가치가 있다. diff가 한 함수 5줄이고 migration이 없어 비용은 거의 0.

**다만 그 가치가 성립하는지 자체가 탈퇴 사용자 정책에 달려 있다** — 그래서 위와 같이 기획 확정까지 보류한다.

### B-3 — ✅ 완료 (2026-08-25). 지적은 유효했으나 **성능 항목이 아니다**

착수 전 코드베이스로 검증했고, **처음 세운 주장 중 2건이 틀려서 여기 정정해 둔다.** 착수 시 같은 오판을 반복하지 않기 위한 기록이다.

#### 이 함수가 하는 일

투표 상세의 **댓글 목록**을 만든다. 댓글 한 건에 붙는 정보가 넷이라 쿼리가 여러 개다.

| 붙이는 것 | 어디서 |
|---|---|
| 본문·작성자·좋아요 수 | `comments` (FK 조인 + 임베디드 집계) |
| "이 사람이 뭘 뽑았는지" 라벨 | `votes` → `poll_options` (2단 체인) |
| "내가 좋아요 눌렀는지" | `comment_likes` |

#### 현재 실행 순서 — 직선이다

```
① comments 조회                     (필수 선행)
      ↓
② votes 조회        (①의 user_id 필요)
      ↓
③ poll_options 조회 (②의 option_id 필요)   ← 진짜 의존
      ↓
④ comment_likes 조회 (①의 comment_id 필요) ← ②③과 무관한데 기다린다
```

#### ✅ 검증됨 — ④가 ②③과 독립이라는 핵심 지적

`comments.ts:88~97`. ④가 쓰는 입력은 `userId`(인자)와 `commentIds`(①의 결과)뿐이다.

```ts
const commentIds = data.map(row => row.id)             // ① 결과만 사용
.eq('user_id', userId).in('comment_id', commentIds)    // ②③ 결과 참조 0건
```

②③의 산출물(`voteMap`, `optionLabelMap`)을 **어디서도 읽지 않는다.** 독립·순차 대기 모두 사실.

②→③은 **진짜 의존이라 못 푼다** — `comments.ts:74` `.in('id', optionIds)`가 ②의 `voteData`에서 나온다.

#### ✅ 검증됨 — 캐시 밖이라 요청마다 탄다

| 확인 | 결과 |
|---|---|
| `comments.ts` 안 `unstable_cache` | **0건** |
| `cache-policy.test.mjs` 검사 대상 | **아님** |
| 호출부 `app/polls/[id]/page.tsx:67` | `ƒ Dynamic` 라우트 |

사용자별(`userId`) 결과라 캐시가 원천적으로 불가능하다. B-2(`unstable_cache(30)` 안, 30초에 1회)와 다른 점이다.

#### ❌ 정정 ① — "왕복 3회"는 단정할 수 없다. **비로그인은 개선 0**

셋 다 조건부다:

| 쿼리 | 실행 조건 | 안 도는 경우 |
|---|---|---|
| ② `votes` | `commenterIds.length > 0` (`:65`) | 댓글 0건 |
| ③ `poll_options` | `voteData && voteData.length > 0` (`:72`) | 댓글 작성자가 아무도 투표 안 함 |
| ④ `comment_likes` | `if (userId)` (`:90`) | **비로그인** |

**비로그인 사용자에겐 ④가 아예 안 돌아 개선 효과가 0이다.** 결과 화면은 마감된 투표면 비로그인도 본다(`page.tsx:61` `isClosed || hasVoted`). 즉 혜택 대상은 **로그인 사용자로 한정**된다.

#### ❌ 정정 ② — "20~30ms"는 근거 없는 수치였다

B-2의 `≈28ms`를 그대로 옮겨 쓴 것인데, 그건 **`getCreatorNamesById`의 `users` 조회** 수치다. `comment_likes` 조회의 실측치가 아니다. 다른 테이블·다른 인덱스·다른 행 수에 같은 숫자를 붙인 것이라 **철회한다. 근거 미확인.**

#### ⚠️ 검증 중 발견 — 호출부가 **이미 병렬**이다

`app/polls/[id]/page.tsx:64`:

```ts
const [voteCounts, comments] = await Promise.all([
  getVoteCounts(id),
  getComments(id, user?.id ?? null),
])
```

`getComments`는 이미 `getVoteCounts`와 나란히 돈다. 내부에서 왕복 1회를 줄여도 그 시점에 `getVoteCounts`가 안 끝났으면 **페이지 전체 응답 시간은 안 줄어든다.** 어느 쪽이 임계 경로인지는 **측정 안 했다**.

#### 완료 내역

②③ 체인과 ④를 `Promise.all`로 나란히 보냈다. `comments.ts:63~110`.

```
① comments
      ↓
   ┌──────────────┬──────────────┐
   ② votes → ③ options      ④ comment_likes     ← 동시 출발
```

두 IIFE가 **각자의 조건 분기를 그대로 들고 있다** — 조기 반환으로 옮겼을 뿐 조건은 하나도 안 잃었다:

| 기존 | 변경 후 |
|---|---|
| `if (commenterIds.length > 0)` | `if (commenterIds.length === 0) return map` |
| 중첩 `if (voteData && voteData.length > 0)` | `if (!voteData \|\| voteData.length === 0) return map` |
| **`if (userId)`** ← 잃으면 안 되는 조건 | **`if (!userId) return set`** |

②→③은 `option_id` 의존이라 IIFE **안에서 순차 유지**. 반환 변수명(`voteMap`, `likedSet`)을 그대로 둬서 아래 `data.map(...)` 매핑부는 안 건드렸다.

검증: `tsc --noEmit` 클린 / `npm run lint` 에러 0(기존 `<img>` 경고만) / `npm test` **151/151**(이 작업 직후 아래 E 항목의 Windows 경로 버그를 고쳐 전건 통과가 됐다).

**측정 안 함**: 실제 응답 시간 변화는 재지 않았다. 위 검증대로 비로그인은 개선 0이고 호출부가 이미 병렬이라, 성능이 아니라 구조 정정으로 남긴다.

#### 결론 — 진행 가치는 있으나 성격이 다르다

| 주장 | 판정 |
|---|---|
| ④가 ②③과 독립인데 순차 대기 | ✅ 확인됨 (`comments.ts:88~97`) |
| 캐시 밖이라 요청마다 실행 | ✅ 확인됨 |
| 왕복 3회 → 2회 | ⚠️ 조건부. 비로그인은 개선 0 |
| 20~30ms 개선 | ❌ 근거 없음. B-2 수치 오용 |
| 페이지 응답이 그만큼 빨라짐 | ❌ 불확실. 호출부가 이미 병렬, 임계 경로 미측정 |

**구조가 틀렸다는 지적 자체는 유효했고**(독립 작업 둘을 순차 대기), 고치는 비용은 한 함수 안이었다. 하지만 **성능 개선이 아니라 구조 정정이다.** 목표 규모 실측에서 여유 77배가 확인된 상태라 이게 병목이라는 근거는 없다.

#### 배포 방식 — npm 의존성이 아니라 **리포 복사**를 택한 이유

`pretendard` npm 패키지를 설치해 CSS만 import하는 방법도 있었다. 두 방법의 **브라우저 산출물은 완전히 동일**하다 — 어느 쪽이든 같은 92개 woff2가 `.next/static/media/`로 emit되고, 브라우저는 `unicode-range`에 맞는 조각만 받는다. 차이는 **92개 파일이 빌드 머신에 어떻게 도착하느냐**뿐이다.

| | 리포 복사 (**채택**) | npm 의존성 |
|---|---|---|
| git에 들어가는 것 | woff2 92개 + CSS = **2.82MB** | 없음 (`package.json` 1줄) |
| Vercel이 빌드마다 받는 것 | 없음 (clone에 포함) | **99MB** 설치·압축해제 |
| 그중 실제 쓰는 양 | 2.82MB 전부 | 2.82MB (**나머지 96MB는 static 웨이트별·미사용 서브셋**) |
| 폰트 버전 올릴 때 | 수동 재복사 | `npm update pretendard` |
| 브라우저 다운로드 | **동일** | **동일** |

**채택 근거**: 교환 조건은 "2.82MB를 git에 한 번 넣기 ↔ 99MB를 빌드마다 받기"다. 폰트는 1년에 한 번 바뀔까 말까 한 정적 자산이라 **버전 관리 편의보다 빌드가 가벼운 쪽의 값어치가 크다.** 패키지 99MB 중 실제 쓰는 건 2.82MB(variable dynamic-subset)뿐이고 나머지는 static 웨이트별·일본어 등 이 프로젝트가 안 쓰는 것들이다.

경량 대안(`pretendard-dynamic-subset`, `pretendard-variable`)을 npm에서 찾았으나 **둘 다 404 — 존재하지 않는다.**

`npm i pretendard` → 필요한 파일 복사 → `npm rm pretendard` 순서로 진행해서 **`package.json`은 변화 없다.**

## E. 작업 중 발견해 고친 것 (원 문서에 없던 항목)

### E-1 — foundation 검사의 예외가 Windows에서 무력화되고 있었다 ✅ 완료 (2026-08-25)

`npm test`가 **로컬에서 항상 150/151**이었고, 이 문서 여러 곳에 *"실패 1건은 무관한 기존 Storybook 색 토큰 건"*으로 반복 기록돼 있었다. **무관한 건 맞았지만 "기존"이 아니라 고칠 수 있는 버그였다.**

#### 원인 — `readdirSync`가 주는 경로 구분자

`src/components/design-foundation.test.mjs`의 `retired legacy color class names are gone repo-wide` 검사에는 **이 파일을 봐주는 예외가 원래 있었다**:

```js
// 이 페이지의 존재 이유가 "무엇을 왜 걷어냈는지" 설명하는 것이라, 폐기된 이름을
// 본문에서 인용하는 게 정상이다. 유일한 예외.
if (entry.endsWith('foundations/DesignToken.mdx')) continue
```

`fs.readdirSync(root, { recursive: true })`는 **플랫폼 구분자**로 경로를 준다. 비교 문자열만 `/`로 하드코딩돼 있어 Windows에서 예외가 빗나갔다:

```
readdirSync가 주는 경로: "storybook\foundations\DesignToken.mdx"   ← 역슬래시
endsWith('foundations/DesignToken.mdx')  →  false
path.sep = "\"
```

예외 대상 파일이 그대로 위반 목록에 올라 검사가 실패했다.

| 플랫폼 | 결과 |
|---|---|
| **Windows** | 항상 실패. `npm test`가 영구히 150/151 |
| **macOS / Linux** | 통과. `path.sep === '/'`라 예외가 정상 작동 |

같은 파일 내 슬래시 경로 비교는 **이 1줄뿐**(`grep` 확인). 다른 두 검사(`legacy flat…`, `prediction screens…`)는 `.mdx`를 스캔 범위에서 아예 빼서 영향이 없었다.

#### 수정

```js
// AS-IS
if (entry.endsWith('foundations/DesignToken.mdx')) continue
// TO-BE  (path는 같은 파일 :4에서 이미 import 중)
if (entry.split(path.sep).join('/').endsWith('foundations/DesignToken.mdx')) continue
```

정규식 이스케이프(`entry.replace(/\\/g, '/')`) 대신 `path.sep`을 쓴 건 의도가 그대로 읽히기 때문이다. **검사 강도는 그대로다** — 예외 대상은 여전히 `foundations/DesignToken.mdx` 하나뿐이고 봐주는 범위를 넓히지 않았다.

**결과: `npm test` 151/151, 실패 0건.**

#### 왜 이게 실해였나

- Windows에서 **`npm test`가 절대 초록이 안 됐다** → *"1건은 원래 빨간 거"*가 기본값이 된다
- 새 실패가 1건 더 생겨도 149/151과 150/151을 눈으로 구분해야 한다
- CLAUDE.md가 경고한 바로 그 상황이다 — *"2026-08-24에 이 script가 없어서 화면 구조가 바뀐 뒤에도 4건이 깨진 채 방치돼 있었다"*

#### ⚠️ 같은 계열 버그의 **재발**이다

`20260823_프로젝트_전체점검.md`의 **"1. 테스트 스위트 전멸 (Windows 경로 버그) — ✅ 해결 (2026-08-23)"**과 같은 계열이다. 그때는 `.pathname`이 `/C:/Users/...`를 주고 `path.join`이 드라이브를 또 붙여 `C:\C:\...`가 됐다.

**2주 만에 다른 형태로 재발했다.** 그 문서가 "해결"로 닫혀 있어 이 함정이 반복된다는 신호가 남지 않았다. 앞으로 `src`를 훑는 검사를 쓸 때는 **경로 비교 전에 구분자를 정규화**하는 것을 기본으로 본다.
