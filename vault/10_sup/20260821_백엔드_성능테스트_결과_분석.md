> **요약**
> 1. 엔드포인트별 유효 베이스라인을 확보했다 (2·3장).
> 2. **정확성 버그 발견** — PostgREST가 1,000행에서 응답을 자르므로 `getVoteCounts` 등 3개 함수가 **1,000행을 넘으면 에러 없이 틀린 집계를 반환한다** (4장). prod는 현재 최대 52건이라 미발현 상태지만(4.5), 성장하면 예고 없이 넘는다. 성능이 아니라 정확성 문제이며, 이번 테스트의 가장 중요한 산출물이다.

> 4. 병목의 정체가 계획서 예상과 다르다: "10만 행 전송"은 애초에 발생할 수 없고, 실제 비용은 **왕복 1회당 ~28ms**와 **1,000행 페이로드**다 (6장).
> 5. 계획서 2순위 개선(`polls` 정렬 인덱스)은 실효성이 없다 (6.3). 우선순위 조정이 필요하다.

### 2.1 엔드포인트 분리가 필수였음이 증명됐다

**80배 차이**(1.65ms vs 143.20ms)다. 두 경로를 합친 값(p95 148.7ms)은 어느 쪽도 대표하지 못한다.

- `/polls`는 `getPollList`가 `unstable_cache(revalidate:30)`로 감싸져 있어(`queries/polls.ts:257`) 3분간 DB를 치는 건 약 6회뿐이다. 1.65ms는 캐시 히트 비용이다.
- `/polls/{id}`는 캐시가 없어 매 요청 DB를 친다.

→ **최적화 대상은 상세 페이지 단독이다. 목록은 이미 캐시로 해결돼 있다.**

### 2.2 꼬리가 무거워지는 것이 특징이다

RLS 정책 적용 전후 비교 (같은 조건, `votes` 조회가 0행 → 1,000행으로 바뀐 것만 차이):

|---|---|---|---|
| 중앙값 | 93.07 ms | 95.72 ms | +2.7 ms |
| 평균 | 100.30 ms | 143.20 ms | +42.9 ms |
| p95 | 147.50 ms | 290.75 ms | **+143.3 ms (약 2배)** |
| 최대 | 479 ms | 3,260 ms | **+2,781 ms** |

**중앙값은 거의 그대로인데 p95는 2배, 최대값은 7배가 됐다.** 평균만 봤다면 "40ms 정도 느려졌네"로 넘어갔을 변화다. 계획서 A.2(백분위·롱테일·평균의 함정)가 실측으로 확인된 사례다.

## 3. 포화점 측정 (처리량)

| 지표 | 정책 전 (0행) | 정책 후 (1,000행) |
|---|---|---|
| 목표 도착률 | 400 iter/s (800 req/s) | 동일 |
| **달성 처리량** | 68.06 iter/s (136.1 req/s) | **54.46 iter/s (108.9 req/s)** |
| 미발사 iteration | 8,428 | 10,050 |
| 상세 p95 | 6.91 s | **13.51 s** |
| 상세 평균 / 중앙값 | 3.05 s / 1.84 s | 4.37 s / 3.51 s |
| 상세 최대 | 7.50 s | 19.94 s |
| **에러율** | 0.00% | **0.00%** |

### 3.1 실패가 아니라 큐잉으로 무너진다

에러율 0%인데 p95가 13.5초, 최대 19.9초다. 서버가 요청을 거절하지 않고 **전부 받아 줄을 세운다**. 계획서 A.7(포화점에서 대기가 비선형 증가)의 전형이다.

부하에 따른 상세 페이지 지연: **143ms → 4,370ms (약 30배)**.

> **운영 함의**: 에러율·5xx만 모니터링하면 이 상태를 탐지할 수 없다. 사용자는 20초를 기다리는데 알람은 울리지 않는다. 요청 로깅과 지연 기반 알람이 필요하다 (계획서 2.3의 "요청 로깅 없음" 항목과 연결).

### 3.2 1,000행 페이로드의 비용

정책 적용만으로 처리량 **20% 감소**(68.06 → 54.46 iter/s), p95 **95% 증가**(6.91 → 13.51s). 응답 하나에 1,000행(약 56KB)이 추가된 것만으로 발생한 차이다.

### 3.3 이 수치의 신뢰도 한계

- k6(최대 500 VU)와 Next.js 서버가 **같은 머신**에서 실행됐다 — 부하 생성기와 측정 대상이 CPU를 다툰다.
- `Insufficient VUs, reached 500 active VUs` 경고 — VU 상한 도달.

따라서 54 iter/s는 **상한이 아니라 하한 추정치**다.

## 4. 정확성 버그 — 투표 결과가 1,000표에서 잘린다 ★

### 4.1 확인 방법과 결과

PostgREST에 직접 질의:

```
GET /rest/v1/votes?select=option_id&poll_id=eq.<LOAD TEST poll>
Prefer: count=exact

→ HTTP 200
   Content-Range: 0-999/100000      ← 10만 행 중 1,000행만 반환
   응답 본문 55,998 바이트, option_id 1,000개
```

Supabase PostgREST의 `db-max-rows` 기본값(1,000)이 적용된다. **범위를 지정하지 않은 `select()`는 조용히 1,000행에서 잘린다.**

### 4.2 영향받는 코드

세 곳 모두 `.range()`/`.limit()` 없이 전량을 가정하고 JS에서 집계한다:

| 위치 | 함수 | 증상 |
|---|---|---|
| `queries/polls.ts:340` | `getVoteCounts` | 1,000표 초과 투표의 **득표수가 틀리게 표시**된다. 총합이 항상 1,000에서 멈춘다 |
| `queries/polls.ts:93` | `getRatingParticipantCounts` | 목록 페이지의 참여자 수 과소 집계. `.in(poll_id, [...])`이라 **여러 poll이 1,000행 한도를 나눠 쓴다** — 더 빨리 잘린다 |
| `queries/polls.ts:393` | `getRatingResults` | 평점 결과가 1,000건에서 잘림 |

`getVoteCounts`의 실제 코드:
```ts
const { data, error } = await supabase
  .from('votes')
  .select('option_id')
  .eq('poll_id', pollId)        // ← range/limit 없음 → 1,000행 캡
if (error || !data) return {}
return data.reduce(...)          // ← 1,000개만 세고 그것을 전체로 보고
```

### 4.3 왜 지금까지 발견되지 않았나

- **에러가 아니다.** HTTP 200, `error` 필드 없음, 정상 배열 반환. 예외도 로그도 없다.
- **작은 데이터에서는 정상 동작한다.** 1,000표 미만에서는 정확하다. 계획서 8장이 지적한 "목데이터 100건으로는 병목이 안 보인다"가 성능뿐 아니라 **정확성에도 적용된 사례**다.
- 부하 테스트를 위해 10만 표를 넣지 않았다면 발견되지 않았을 것이다.

### 4.4 수정 방향

집계를 DB로 내리면 성능과 정확성이 **동시에** 해결된다 (계획서 6장 3순위):

```sql
-- RPC: 5행만 반환, 캡과 무관, 전송량 1/200
SELECT option_id, count(*) FROM votes WHERE poll_id = $1 GROUP BY option_id;
```

리포에 이미 올바른 관용구가 있다 — `getMyRatingVoteCount`(`polls.ts:374`)는 `.select('id', { count: 'exact', head: true })`로 행을 전송하지 않고 개수만 받는다. 단순 개수만 필요한 곳은 이 패턴으로 충분하다.

### 4.5 prod 영향 — 현재 없음 (잠재 상태)

2026-08-21 prod 실측:

| 확인 항목 | 쿼리 | 결과 | 판정 |
|---|---|---|---|
| 1,000표 초과 투표 | `SELECT poll_id, count(*) FROM votes GROUP BY poll_id HAVING count(*) > 1000` | 0건 | 여유 |
| poll별 최대 평점 수 | `SELECT poll_id, count(*) FROM rating_votes GROUP BY poll_id ORDER BY count(*) DESC` | 최대 52건 | 여유 |
| 평점 전체 합계 | `SELECT count(*) FROM rating_votes` | 52건 | 여유 |

**세 함수 모두 현재는 정확한 값을 반환하고 있다.** 버그는 발현되지 않은 잠재 상태다.

다만 임계값이 절대적이라 **성장하면 예고 없이 넘는다.** 특히 `getRatingParticipantCounts`는 poll별이 아니라 목록 한 페이지의 합계에 한도가 걸리므로 개별 poll이 작아도 누적으로 도달할 수 있다.

> **판단**: 장애 대응이 아니라 계획된 개선으로 처리할 수 있는 지금이 수정 적기다. 수정 자체가 성능 개선(6장)과 동일한 작업이므로, 개선 전후 수치가 그대로 평가 산출물이 된다.

## 5. prod 스키마 drift (운영 리스크)

### 5.1 내용

`votes: public read` (SELECT, `USING (true)`) 정책이 **prod에만 있고 어떤 마이그레이션에도 없다.** 대시보드에서 직접 추가된 것으로 보인다.

| 환경 | `votes` SELECT 정책 |
|---|---|
| prod | `votes: public read` + `votes: select own` |
| staging (마이그레이션만으로 구축) | `votes: select own` 만 |

### 5.2 왜 위험한가

이 정책이 없으면 `votes: select own`(`auth.uid() = user_id`)만 남아 익명 사용자는 0행을 받는다. `getVoteCounts`는 에러 없이 빈 객체를 반환하므로 **투표 결과가 전부 0표로 조용히 표시된다.**

prod를 마이그레이션으로 재구축하거나 새 환경(재해 복구, 신규 리전, 리뷰 앱)을 만들면 재현된다. 즉 **현재 마이그레이션 집합은 prod를 재현하지 못했다.**

### 5.3 조치

`supabase/migrations/20260821000000_capture_votes_public_read.sql`로 편입했다. prod에 이미 존재하므로 `DROP POLICY IF EXISTS` → `CREATE`의 idempotent 형태로 작성해 prod에도 안전하게 적용된다. **staging에는 적용 완료**, prod 적용은 미결정.

### 5.4 프로세스 교훈

측정 착수 전 drift를 점검하고 "없음"으로 판단했으나 **틀렸다.**

- 컬럼 정의는 마이그레이션과 대조했으나, RLS 정책은 prod 목록을 조회해 **눈으로 보기만 하고 마이그레이션 파일과 교차 대조하지 않았다.**
- `supabase migration list`의 13/13 일치를 과신했다. **마이그레이션 이력 테이블은 대시보드에서 직접 실행한 DDL을 탐지하지 못한다.**
- `supabase db diff`는 Docker를 요구해 이 환경에서 실행 불가였다. Docker 없이 점검하려면 `pg_policies`/`information_schema`를 마이그레이션 파일과 **항목 단위로** 대조해야 한다.

## 6. 병목 재해석 (실측 기반)

### 6.1 "10만 행 전송"은 애초에 발생할 수 없다

계획서 5장은 `getVoteCounts`를 "행 수에 선형, 1만 표 = 1만 행 전송"으로 규정했으나, 4장에서 확인했듯 **PostgREST가 1,000행에서 자르므로 전송량은 표 수와 무관하게 상수(최대 약 56KB)다.**

계획서의 이 서술은 수정이 필요하다. 다만 **결론(RPC로 집계를 내려야 한다)은 그대로 유효하며, 이유가 "느려서"에서 "틀려서"로 격상된다.**

### 6.2 실제 비용은 왕복 1회 그 자체다

RLS 정책 적용 **전** 측정에서, 결과 표시 경로 진입만으로 p95가 27.89ms 증가했다. 그때 그 왕복은 **빈 응답(0행)**을 받았고, `getComments`도 댓글 0건이며 둘은 `Promise.all`로 병렬이다(`page.tsx:65-68`).

**즉 +27.89ms는 데이터 전송량과 무관한, HTTP 왕복 1회 추가 그 자체의 비용이다.**

계획서 4장의 명제를 실측이 뒷받침한다:

> "이 스택의 최적화 1순위는 쿼리 튜닝이 아니라 왕복 합치기다."

빈 응답 왕복 하나가 28ms다. 계획서 6장 4순위였던 "왕복 합치기"는 **상위로 올려야 한다.**

### 6.3 `polls` 정렬 인덱스 — 실효성 없음, 우선순위 하향

polls 5,001건으로 시드를 보강한 뒤 측정:

```
Sort (actual time=1.899..1.901 rows=20) — Sort Method: top-N heapsort, Memory: 29kB
  -> Seq Scan on polls (rows=5001) (actual time=0.023..0.906)
Execution Time: 1.985 ms   (3회 반복: 1.985 / 1.935 / 1.957)
```

Postgres가 `top-N heapsort`를 선택해 **전체 정렬을 하지 않는다**(LIMIT 20). 5,000건 기준 총 1.95ms이며, 인덱스를 추가해도 절감폭은 약 1.9ms다. 게다가 이 쿼리가 도는 `/polls`는 30초 캐시라 3분에 6회만 실행된다 — 종단 지연 영향은 사실상 0이다.

→ 계획서 6장 2순위는 **현재 규모에서 측정 가능한 개선을 만들지 못한다.** 계획서 5장의 "매번 전체 정렬" 서술도 `top-N heapsort` 동작에 맞게 수정이 필요하다.

### 6.4 DB 실행시간 (참고)

Management API(RLS 우회)로 실행한 `EXPLAIN ANALYZE`:

| 실행 | Execution Time | Buffers |
|---|---|---|
| 1회차 | 552.27 ms — 배제 (6.5) | shared hit=1235, read=0 |
| 2~4회차 | 30.96 / 23.22 / 20.67 ms | - |

안정 구간 **20~31ms**, `Seq Scan on votes (rows=100000)`. `votes(poll_id)` 인덱스는 존재하나(`20260624130000_add_hot_query_indexes.sql`) 10만 중 10만 행을 읽으므로 플래너의 Seq Scan 선택이 옳다 — **이 쿼리는 인덱스로 개선되지 않는다.**

단, 이는 RLS를 우회한 서버 측 측정이며 실제 앱 경로는 1,000행만 받는다.

### 6.5 552ms 이상치는 "콜드 캐시"가 아니다

1회차의 `Buffers: shared hit=1235, read=0` — 디스크 읽기 0이다. 데이터가 이미 메모리에 있었으므로 콜드 캐시로 설명되지 않고, `EXPLAIN ANALYZE`의 Execution Time은 서버 측 시간이라 네트워크도 아니다.

남는 설명은 **무료 티어 공유 인스턴스의 CPU 경합**이며, 실부하 중 재발해 p95를 오염시킬 수 있다. 동시에 단발 측정 한 번으로 판단했다면 병목을 20배 과대평가했을 사례다.
