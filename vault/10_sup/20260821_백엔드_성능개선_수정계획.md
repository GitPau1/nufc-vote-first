## 1. 배경 — 무엇을 고치려는가

성능 테스트 1차에서 발견한 문제 중 **정확성 버그**가 최우선이다.

Supabase PostgREST의 `db-max-rows` 기본값(1,000)이 조회 응답을 자르는데, 범위를 지정하지 않고 전량을 가정해 JS에서 집계하는 코드가 세 곳 있다. 에러 없이 HTTP 200으로 잘린 배열이 오므로 탐지되지 않는다.

prod 실측 결과 현재 최대 52건이라 **미발현 상태**다. 장애 대응이 아니라 계획된 개선으로 처리할 수 있는 지금이 수정 적기다.

| 위치 | 함수 | 잘리는 조건 |
|---|---|---|
| `queries/polls.ts:340` | `getVoteCounts` | poll당 1,000표 초과 |
| `queries/polls.ts:93` | `getRatingParticipantCounts` | 목록 페이지 poll들의 **합계** 1,000 초과 |
| `queries/polls.ts:393` | `getRatingResults` | poll당 평점 1,000건 초과 |

동시에 이 수정은 최대 성능 병목(상세 페이지 p95 290.75ms) 해소와 같은 작업이다. 정확성과 성능이 같은 방향으로 풀린다.

## 2. 설계 판단 — 왜 RPC를 만들지 않는가

### 2.1 검토한 선택지

| 선택지 | 판정 | 근거 |
|---|---|---|
| `.range()` / `.limit()`으로 더 요청 | **불가** | `db-max-rows`는 서버 측 하드 캡. 실측: `Range: 0-99999` → 1,000행, `?limit=5000` → 1,000행 |
| 페이지네이션 루프 | **논외** | 1,000행씩 100회 = 왕복 100회 × 28ms ≈ 2.8초. 계획서 4장 "왕복 합치기" 원칙에 정면 위배 |
| `db-max-rows` 전역 상향 | **부적합** | ① 모든 엔드포인트의 안전장치 제거 ② 대시보드 설정이라 마이그레이션에 안 남음 → **drift 재생산** ③ 10만 행(5MB)을 실제 전송하게 되어 **성능은 오히려 악화** |
| PostgREST 집계 함수 (`select=option_id,count()`) | **불가** | 이 프로젝트에서 비활성. `PGRST123: Use of aggregate functions is not allowed` |
| **임베디드 집계 (`votes(count)`)** | **채택** | 아래 |
| RPC `GROUP BY` 신규 작성 | **불필요** | 임베디드 집계로 동일 효과. 새 개념 도입 없이 해결됨 |

### 2.2 채택 근거 — 리포에 이미 있는 패턴이다

목록 페이지(`polls.ts:196`)는 이미 `vote_count:votes(count)`로 **서버 측 집계**를 쓰고 있고, 이 경로는 캡에 걸리지 않는다.

즉 **같은 숫자를 두 방식으로 세고 있었고, 한쪽만 틀렸다:**

| 화면 | 방식 | 10만 표에서 |
|---|---|---|
| 목록 `/polls` (`polls.ts:196`) | 서버 측 집계 — 숫자만 전송 | **정확** (`count: 100000`, 119 bytes) |
| 상세 `/polls/{id}` (`polls.ts:340`) | 행 전량 조회 후 JS 집계 | **잘림** (`Content-Range: 0-999/100000`, 56 KB) |

선택지별로도 같은 패턴이 동작함을 실측 확인했다:

```
GET /poll_options?select=id,label,vote_count:votes!votes_option_id_fkey(count)&poll_id=eq.<poll>

→ [{"label":"선수 1","vote_count":[{"count":0}]}, ...,
   {"label":"선수 5","vote_count":[{"count":100000}]}]
   483 bytes, 0.22s
```

`votes`와 `poll_options` 사이 FK가 두 개(`votes_option_id_fkey`, `votes_option_matches_poll_fkey`)라 FK 명시가 필요한 것 외에는 제약이 없다.

### 2.3 두 방식 비교

| | RPC 신규 작성 | 임베디드 집계 (채택) |
|---|---|---|
| 마이그레이션 | 필요 | **불필요** |
| `types/database.ts` `Functions` | 추가 필요 (현재 `[_ in never]: never`) | **불필요** |
| 변경 파일 수 | 3 | **1** |
| 전송량 | 5행 | 483 bytes (5행) |
| 리포 내 선례 | 없음 (앱 최초 RPC — `.rpc()` 사용처 0건) | **`polls.ts:196`** |

성능·정확성 효과는 사실상 동일한데 새로 도입하는 개념이 없다.

### 2.4 왕복까지 합치지 않는 이유 (중요)

`getPollById`가 이미 `poll_options`를 조회하므로, 거기에 count를 중첩하면 왕복 1회(약 28ms)를 더 줄일 수 있다. **그러나 해서는 안 된다.**

`poll` 객체는 `TypeBPollClient poll={poll}` 형태로 클라이언트 컴포넌트에 직렬화된다. 득표수를 `poll`에 실으면 **투표 전 사용자에게 결과가 RSC 페이로드로 노출된다.** CLAUDE.md가 깨지면 안 된다고 명시한 "결과는 참여 후에만 공개" 제약 위반이다.

→ `getVoteCounts`는 별도 호출로 유지하고 **구현만** 교체한다.

## 3. 실행 계획

### 1단계 — `getVoteCounts` 구현 교체

**변경 범위: `src/lib/queries/polls.ts` 단일 파일, 단일 함수 (335~351행)**

```ts
// AS-IS — 행을 다 끌어와 JS가 셈 → 1,000행 캡
.from('votes').select('option_id').eq('poll_id', pollId)

// TO-BE — DB가 세서 숫자만 받음 → 캡 무관
.from('poll_options')
.select('id, vote_count:votes!votes_option_id_fkey(count)')
.eq('poll_id', pollId)
```

영향 범위 점검 (CLAUDE.md의 스키마 변경 체크리스트 기준):

| 항목 | 변경 |
|---|---|
| 마이그레이션 | 없음 |
| `types/database.ts` | 없음 |
| RLS 정책 | 없음 (기존 `votes: public read`, `poll_options: public read` 사용) |
| 반환 타입 `VoteCountMap` | 유지 (`Record<string, number>`) |
| 호출부 `page.tsx:66` | 없음 |
| `ResultView` | 없음 |
| mock (`mockGetVoteCounts`) | 없음 — `IS_MOCK` 분기가 앞에서 반환 |

부수 효과: 득표 0인 선택지가 명시적 `0`으로 포함된다. `ResultView`는 `voteCounts[option.id] ?? 0`으로 읽으므로 동작 동일.

### 2단계 — 정확성 검증

측정보다 먼저 한다. staging에 10만 표가 있으므로:

> **합계 100,000이면 통과, 1,000이면 실패.**

이 프로젝트에서 가능한 가장 짧고 결정적인 검증이다. 기존 `node --test` 테스트들은 DB 없이 도는 순수 로직 테스트라 이 변경에는 맞지 않으므로, 새 테스트 파일을 만들지 않고 staging 실측으로 확인한다.

### 3단계 — 개선 전후 측정

동일 조건(스크립트·시드·VU 램프)으로 지연 + 포화 재측정.

| 지표 | 개선 전 (실측 완료) | 개선 후 |
|---|---|---|
| 상세 p95 | 290.75 ms | |
| 상세 평균 | 143.20 ms | |
| 상세 최대 | 3,260 ms | |
| 처리량 | 54.46 iter/s (108.9 req/s) | |
| 포화 p95 | 13.51 s | |
| 응답 페이로드 | 약 56 KB | |

**1단계만 적용한 상태로 측정한다.** 세 함수를 한꺼번에 고치면 어느 변경이 얼마를 줄였는지 귀속되지 않는다. 계획서 1장이 요구하는 건 `290ms → ?ms` 형태의 귀속 가능한 수치다.

### 4단계 — 나머지 두 버그 (해법이 다르다)

세 버그는 성격이 달라 같은 패턴으로 해결되지 않는다. 이를 명확히 해둔다:

| 함수 | 필요한 연산 | 임베디드 집계 적용 | 필요한 접근 |
|---|---|---|---|
| `getVoteCounts` | 선택지별 행 수 | **가능** | 1단계 |
| `getRatingParticipantCounts` (:93) | **중복 제거된 참여자 수** (`Set`으로 user_id 유니크 처리) | **불가** — `count()`는 행 수라 과다 집계 | `COUNT(DISTINCT user_id)`가 필요 → RPC 또는 뷰 |
| `getRatingResults` (:393) | 표시용 평점 목록 (작성자·코멘트 포함) | **불가** — 집계가 아니라 목록 | 페이지네이션 또는 명시적 `limit` 정책 |

1단계 결과를 확인한 뒤 각각 별도 설계한다.

### 5단계 — 시드 데이터 수정

현재 시드는 10만 표가 전부 한 선택지("선수 5")에 몰린다. `ORDER BY random() LIMIT 1` 상관 서브쿼리가 한 번만 평가되기 때문이다.

성능 측정에는 큰 영향이 없으나(그룹 수 동일), 수정 후 정확성 검증에는 고른 분포가 낫다. 결정적(deterministic) 분배로 바꾸면 재현성도 함께 올라간다 (계획서 배점 15점 항목).

## 5. 이전 계획과 달라진 점

초안은 RPC 신규 작성(마이그레이션 + `types/database.ts` + 쿼리 수정, 3개 파일)이었다. 검토 중 목록 페이지가 이미 올바른 패턴을 쓰고 있음을 발견해 **1단계가 함수 하나 수정으로 축소**됐다.

대신 4단계에서 나머지 두 함수는 각각 다른 해법이 필요하다는 점이 명확해졌다 — 초안은 "동일 방식으로 수정"이라고 뭉뚱그렸으나 이는 부정확했다.
