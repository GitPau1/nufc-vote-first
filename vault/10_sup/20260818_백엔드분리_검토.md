## 결론 요약

## 1. 현황 조사 결과

| 항목 | 수치 | 시사점 |
|---|---|---|
| Supabase import 파일 | 28개 | 이관 표면 |
| RLS 정책 | 25개 (`auth.uid()` 14곳) | **최대 리스크** |
| Postgres RPC 호출 | 0건 | 로직이 이미 앱 레이어에 있음 |
| Realtime 구독 | 0건 | 이관 부담 없음 |
| Storage 버킷 | 1개 (`player-photos`) | 사용처 `lib/actions/images.ts` 한 곳 |
| `auth.getUser()` 호출부 | ~15곳 | 세션 검증 교체 대상 |

**RPC 0건 / Realtime 0건** → 비즈니스 로직이 이미 Next.js server actions에 있음. 백엔드는 *새로 만드는* 게 아니라 *옮기는* 작업.

**RLS 25개** → 인가 로직 상당수가 DB에 있음. 세 가지 불변조건(투표 1회 / 결과는 참여 후 공개 / 댓글은 참여자만)이 여기 걸려 있어 하나만 놓쳐도 조용히 뚫린다.

## 2. 성능 이슈 진단 — "리전 때문에 느리다"

원래 이전 동기였으나, **조사 결과 EC2 없이 고칠 수 있는 문제였음.**

### 문제 A. Vercel 함수 리전 미지정
- `vercel.json` 없음, `preferredRegion` 지정 0건
- → 서버 함수가 기본 리전 `iad1`(미국 버지니아)에서 실행 중
- 해결: `frontend/vercel.json` 에 `{ "regions": ["icn1"] }` 한 줄

### 문제 B. 서버 컴포넌트 쿼리 워터폴 (더 큼)
`app/polls/[id]/page.tsx` 직렬 체인:
```
auth.getUser() → poll 조회 → ratingVoteCount → getRatingResults → getMyVote → [voteCounts, comments]
```
- 직렬 라운드트립 **5~6회**
- 전체 리포에서 `Promise.all` 은 3곳뿐, `queries/polls.ts` 하나에 `await` 27개

> **대기시간 = RTT × 라운드트립 횟수**
> 리전 이전은 앞의 항만 줄인다. **워터폴은 인프라를 옮겨도 그대로 곱해진다.**

### 결론
성능만이 목적이라면 `Supabase Seoul + Vercel icn1 ≈ RDS Seoul + EC2 Seoul` 로 거의 동등.
→ **이전의 명분은 성능이 아니라 소유권**으로 정리함.
→ 단, 문제 A·B는 이전 여부와 무관하게 **먼저 처리**할 것 (이전 후 성능 회귀 판별에도 필요).

## 3. Supabase에 실제로 묶여 있는 것

| 기능 | 사용 현황 | RDS 이전 시 |
|---|---|---|
| `auth.uid()` | RLS 14곳 | ❌ `auth` 스키마 없음 — 전부 재작성 |
| `auth.users` 트리거 | `public.users` 자동 생성 | ❌ 재설계 |
| **`pg_net`** | `net.http_post()` 캐시 revalidate | ❌ **RDS 미지원.** 앱 레이어로 이관 필요 |
| `pg_cron` | 주간 레이팅 배치 | ✅ RDS 지원 |
| 타입 자동생성 | `npm run types:supabase` | ❌ 직접 구축 |
| 커넥션 풀러 | Supavisor 내장 | ⚠️ RDS Proxy 별도 |
| Storage | `player-photos` | ❌ S3 이전 |

**반전:** 백엔드가 인가를 앱 코드에서 하게 되면 `auth.uid()` RLS / `pg_net` / `pg_cron` 은 어차피 걷어낼 대상.
→ Supabase의 최대 장점이 이 계획에선 스스로 사라짐. 남는 건 "관리형 Postgres"뿐이고 그 지점에선 RDS와 대등.

### DB는 RDS로 (EC2 직접 운영 ❌)
EC2에 Postgres 올리면 Supabase가 제공하던 걸 전부 떠안음: PITR, 자동 백업 검증, 마이너 패치, failover, 커넥션 풀링.
RDS도 자사 AWS 계정 안이므로 소유권 요건 충족. 앱 서버와 **같은 리전·같은 AZ** 배치 시 DB RTT 1ms 미만.

## 4. 이관 순서 (strangler-fig)

| 단계 | 내용 | 비고 |
|---|---|---|
| 0 | **`google_sub` 백필** | 시한부 — 아래 5장 |
| 0 | `pg_net` 의존 앱 레이어로 이관 | 어느 쪽을 택하든 필요 |
| 1 | 백엔드 골격 + 배포 파이프라인 | health check만, 프론트 변경 없음 |
| 2 | **읽기 전용 도메인** (`queries/polls.ts`, `club.ts`) | 인가 없음 → 리스크 최저, 파이프라인 검증용 |
| 3 | **Storage** | 버킷 1개·사용처 1곳, 독립 진행 가능 |
| 4 | **쓰기 도메인** (투표 → 댓글 → 관리자) | 도메인별 순차 |
| 5 | **Auth** | 가장 크고 리스크 높음 → 마지막 |
| 6 | `lib/supabase/*` 삭제, OpenAPI 문서화 | |

### 각 도메인 이관 시 규칙
- 이관 **전에** 계약 테스트부터 작성 (기존 `*.test.mjs` 패턴) — 투표 중복 방지, 미참여자 댓글 차단 등. 이관 전/후 동작 동일성을 테스트로 증명.
- 해당 RLS 정책을 읽고 동일 검사를 백엔드 Guard로 명시적 이관
- **RLS는 바로 지우지 않는다.** 세 불변조건만큼은 이중 방어로 유지 — 백엔드 버그 시 DB가 최후 방어선.

### 하지 말 것
- 마이크로서비스 분할 ❌ — 이 규모엔 모놀리식 하나로 충분
- 스키마 변경과 접근 계층 이관 동시 진행 ❌ — 원인 분리 불가
- Auth 먼저 이관 ❌ — 가장 큰 조각이 앞에 오면 초반에 멈춤
- tRPC ❌ — 멀티 클라이언트 목적이면 REST + OpenAPI

## 5. Google OAuth 자체 이관

### 좋은 소식: FK가 `auth.users`를 참조하지 않음
```
votes.user_id         → public.users(id)
comments.user_id      → public.users(id)
comment_likes.user_id → public.users(id)
```
`auth.users`는 트리거로 `public.users`에 복사만 될 뿐(동일 UUID).
→ **`public.users.id` 값만 보존하면 투표·댓글·좋아요 전부 생존.**

### ⚠️ 시한부 작업: `google_sub` 백필
`public.users`엔 `email`만 있고 Google `sub`(고유 계정 ID)가 없음.
`sub`는 `auth.identities` 에만 존재 → **Auth 걷어내는 순간 영구 소실.**
이메일은 변경 가능하므로 이메일 매칭은 계정 유실 위험.

```sql
ALTER TABLE public.users ADD COLUMN google_sub text UNIQUE;

-- Supabase Auth 가 살아있는 지금만 가능
UPDATE public.users u
SET google_sub = i.provider_id
FROM auth.identities i
WHERE i.user_id = u.id AND i.provider = 'google';
```

### 세션 전략: JWT ❌ → 불투명 세션 ID + DB ✅

| | JWT + refresh 로테이션 | 불투명 세션 ID + DB |
|---|---|---|
| 즉시 로그아웃/차단 | ❌ 블록리스트 필요(=결국 세션 테이블) | ✅ 한 줄 DELETE |
| 키 로테이션 인프라 | 필요 | 불필요 |
| 요청당 비용 | 서명 검증 | DB 조회 1회 |

백엔드와 DB가 같은 VPC에 있으므로 조회 1ms. 그걸 아끼려 만료·로테이션·폐기 로직을 짤 이유 없음.
관리자 강제 로그아웃 / 계정 삭제 즉시 반영도 공짜.

```sql
CREATE TABLE sessions (
  id         text PRIMARY KEY,           -- crypto.randomBytes(32)
  user_id    uuid NOT NULL REFERENCES public.users(id) ON DELETE CASCADE,
  expires_at timestamptz NOT NULL
);
```
쿠키: `HttpOnly; Secure; SameSite=Lax`. **localStorage 토큰 저장 금지** (XSS).

### OAuth 구현
- 직접 구현 ❌ → `openid-client` (OIDC 인증 라이브러리) 사용. 프로토콜만 위임하고 세션은 자체 소유.
- 어려운 건 OAuth 교환(100줄)이 아니라 state/PKCE 검증, 쿠키 플래그, 만료, 로그아웃 전파.

### 도메인 설계 (나중에 변경 어려움 — 먼저 확정)
```
프론트: nufc-vote.com
백엔드: api.nufc-vote.com    ← 같은 상위 도메인
쿠키:   Domain=.nufc-vote.com; SameSite=Lax
```
다른 최상위 도메인에 두면 크로스사이트 → `SameSite=None` 강제 → Safari ITP·서드파티 쿠키 차단에 걸림.

### 무중단 전환 가능
기존 Google Cloud OAuth 클라이언트는 이미 자사 소유(Supabase 연동 시 필수).
1. 해당 클라이언트에 **새 redirect URI 추가** (기존 유지) → 양쪽 동시 동작
2. 새 백엔드 로그인 경로 배포 후 소수 계정 검증
3. `getUser()` 호출부(~15곳) 순차 교체
4. 완료 후 Supabase redirect URI 제거

→ 전환 중 사용자 로그아웃 없음.

### 하지 말 것
- 이메일로 계정 매칭 ❌ → 반드시 `google_sub`
- UUID 재발급 ❌ → 투표 이력 전부 고아화
- Keycloak/Ory 도입 ❌ → 소셜 로그인 1개짜리엔 과함. SSO/SAML 필요해지면 그때
