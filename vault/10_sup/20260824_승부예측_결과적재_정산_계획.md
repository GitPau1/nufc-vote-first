## 0. 조사 결과 — 출발점이 생각과 다르다

`20260823_프로젝트_전체점검.md` §3.1은 "`fixtures`, `season_squads`, `fixture_player_ratings` 세 테이블에 쓰는 코드가 리포 전체에 없다"고 적었다. **틀린 게 아니라 리포 밖이었다.** 배포된 Edge Function 5개를 내려받아 확인한 결과:

| 함수(slug) | 하는 일 | DB write |
|---|---|---|
| `sync-fixture` | FotMob 팀 API → `fixtures` 전 경기 upsert. 멱등, POST 전용, dedupe·빈배열 방어까지 구현됨 | ✅ |

| `health-check` | — | — |

추가로 확인한 사실:

- **앱 코드는 이 함수들을 한 번도 호출하지 않는다** (`grep -rn "functions/v1\|functions.invoke" src` → 0건). 전부 크론/수동 전용이다.

- `match-ratings`가 파싱(`extractLineupPlayers` / `extractRating`)을 이미 방어적으로 구현해뒀다. FotMob 응답 구조가 여러 갈래라 후보 경로를 순회하는 형태다.

**따라서 실제로 없는 것은 평점 write 하나 + 트리거다.** 채점·랭킹 view(`prediction_results`, `week_leaderboard`, `season_leaderboard`)와 결과 화면(`PredictionResult`, `getMyResults`, `getWeekRanking`)은 §3.2 지적 이후 이미 연결됐다.

## 2. 1단계 — 평점 적재: `match-ratings` → `sync-fixture-ratings` — ✅ 완료 (2026-08-24)

새 함수를 만들지 않고 기존 조회 함수를 개명·전환한다. 파싱이 이미 있고, 앱에서 호출하는 곳이 0건이라 조회 응답을 유지할 이유가 없다.

```
supabase/functions/sync-fixture-ratings/index.ts   (match-ratings 이동 + 껍데기 교체)
```

### 대상 선별 = 멱등성

`fixtures`에서 `finished = true`인 경기 중, 적재된 `fixture_player_ratings` 행이 **11개 미만**인 것. 임베디드 count(`select=fixture_id,fixture_player_ratings(count)`)로 한 번에 뽑는다 — FK가 있어 그대로 동작한다.

"행이 하나라도 있으면 적재 완료"로 판정하지 않는 이유:

> FotMob 평점은 경기 종료 시점에 확정되지 않는다. 종료 직후에는 일부 선수만 채워져 내려올 수 있다. 그 상태로 적재하고 "행이 있으니 완료"로 굳으면, 나머지 선수는 `prediction_pick_points`에서 **영구히 0점**이 된다. 조용히 틀린 점수가 남는 형태라 가장 위험하다.

선발 11명을 기준선으로 두면 부분 적재가 다음 실행에서 자동으로 재시도되고, 연장·퇴장 같은 예외에도 깨지지 않는다.

### 배치 상한

`limit(5)` + 응답에 남은 경기 수. 두 가지를 동시에 막는다.

- **CPU 2초 제한**: 무료 플랜 Edge Function은 호출당 wall clock 150초, CPU 2초다. `matchDetails` 응답이 경기당 수백 KB~1MB급이라 파싱만 경기당 수십 ms. 첫 백필에서 시즌 40경기를 한 번에 돌면 CPU 1.5~2초로 제한에 걸려 중간에 죽고, 앞쪽만 적재된 채 성공한 것처럼 보인다.
- FotMob rate limit / 구조 변경 시 한 번에 40번 때리는 것.

백필은 며칠에 걸쳐 알아서 끝나거나 관리자 버튼을 몇 번 누르면 끝난다.

### 쓰기

`rating !== null`인 선수만 `fixture_player_ratings` upsert(`onConflict: 'fixture_id,player_id'`). 평점 없는 선수는 행을 만들지 않고, 그게 그대로 0점이다 — FR-015(선수 미출전 0점)가 그대로 유지된다.

껍데기는 `sync-fixture`와 동일하게 맞춘다(POST 전용, service-role, 요약 JSON 반환). 디버깅용 `?matchId=` 파라미터만 남긴다.

### 배포

```bash
npx supabase functions deploy sync-fixture-ratings
npx supabase functions delete match-ratings
```

## 3. 2단계 — 크론 하루 1회 (KST 08:00) — 🔶 관리자 버튼 완료 / 크론 등록 대기

### 왜 하루 1회인가

1. **경기 시간대가 이미 하루 1회로 수렴한다.** EPL 킥오프를 KST로 옮기면 토 23:00, 일 00:30~02:00, 늦은 경기 04:00~05:00. 컵 미드위크도 KST 04:00~05:00. **전 경기가 KST 07시 전에 끝난다.** 08:00 실행이면 어제 끝난 경기가 한 번에 다 잡힌다. 매시간 돌리면 24회 중 23회가 no-op이다.
2. **지연 1시간과 8시간의 차이가 사용자에게 없다.** 새벽에 끝난 경기의 결과를 보러 오는 사람은 아침에 온다.
3. **촘촘한 폴링이 오히려 위험하다.** 종료 직후를 때리면 §2의 "평점 미확정 창"에 정확히 들어간다. 종료 후 몇 시간 지난 뒤 한 번 읽는 게 데이터 품질 면에서 낫다.

### 부담

| 항목 | 사용량 | 무료 한도 | 비중 |
|---|---|---|---|
| Edge Function 호출 | 2회/일 ≈ 60회/월 | 500,000회/월 | 0.01% |
| FotMob 호출 | 팀 API 1회 + 경기당 1회 = 하루 1~3회 | — | — |
| DB 쓰기 | 경기당 약 18행 → 시즌 전체 약 900행 | — | 무의미 |
| egress | 요약 JSON 몇 KB (FotMob 수신은 인바운드라 미집계) | 5GB/월 | ~0% |

여유가 4자리수 배다. 실제로 신경 쓸 건 주기가 아니라 배치 상한 하나뿐이다.

### 등록 방법 — 대시보드 작업 (미완료)

**Supabase 대시보드 → Integrations → Cron**에서 job 2개를 만든다. 두 함수가 `verify_jwt: true`라 호출에 service_role 키가 필요한데, 마이그레이션에 넣으면 키가 커밋된다. Vault 참조로 우회할 수도 있지만 등록은 한 번이라 그만큼의 SQL을 살 이유가 없다.

| job | 스케줄(UTC) | KST | 대상 |
|---|---|---|---|
| `sync-fixture-daily` | `0 23 * * *` | 08:00 | Edge Function `sync-fixture` (POST) |
| `sync-fixture-ratings-daily` | `5 23 * * *` | 08:05 | Edge Function `sync-fixture-ratings` (POST) |

pg_cron job 하나에서 두 함수를 순차 호출하려면 SQL을 써야 하므로, **5분 간격 job 2개로 나눴다.** 스코어가 먼저 들어와야 평점 대상이 잡히는 순서 의존성이 이 간격으로 해결된다. 실패해도 다음 날 자동 재시도되고, 급하면 관리자 버튼을 누르면 된다.

기록은 `supabase/functions/README.md`.

## 4. 3단계 — 제출 완료 화면 O/X 표기

DB·쿼리 변경 0건. `MatchView`가 이미 `finished`와 `actual`([우리, 상대])을 들고 `PredictionDone`까지 내려간다.

- `lib/predictions/result.ts`에 순수 함수 추가: `matchHit(predicted, actual) → 'exact' | 'outcome' | 'miss'`. SQL `prediction_match_points`와 같은 기준이므로 양쪽에 상호 참조 주석을 남긴다. `result.test.mjs`에 케이스 3개.
- `PredictionDone`의 경기 카드: 종료된 경기면 예측 스코어 아래에 실제 스코어 + 배지(`정확히 적중` / `승패 적중` / `미적중`).
- **점수 숫자는 표시하지 않는다** — 4단계(정산 게이트)와 일관되게. 선수 픽 O/X도 제외한다(평점이 곧 점수라 정산 화면 몫).

### `[weekKey]/page.tsx` 조건 수정 (필수)

현재는 `week.status === 'upcoming'`이면 `notFound()`다. 그런데 킥오프이 지나고 아직 `finished`가 적재되지 않은 구간은 "모든 경기 locked + 전부 finished 아님" → `upcoming`으로 판정된다(`week.ts`의 `weekStatus`). **하루 1회 크론이면 경기가 끝난 새벽부터 08:00까지 페이지가 사라진다.**

아직 열리지 않은 주차만 막도록 좁힌다.

```ts
if (!week || (week.status === 'upcoming' && week.matches.every(m => !m.locked))) notFound()
```

- 아직 오픈 전 주차: 모든 경기가 `locked = false` → `notFound()` 유지.
- 경기 진행 중 / 종료 후 적재 전: 모두 `locked = true` → 통과해서 완료 화면(`pending`이 비어 `PredictionDone`)으로 떨어지고, 적재되면 같은 화면에 O/X가 붙는다.
- 경기 없는 빈 주차: `every`가 true → `notFound()` 유지.

## 5. 4단계 — 주차 정산 게이트 (마이그레이션 1개)

`prediction_results` view를 `create or replace`(컬럼 변화 없음)하고 "그 주차에 안 끝난 경기가 없다" 조건을 추가한다.

```sql
and not exists (
  select 1 from public.fixtures f2
  where f2.cancelled = false and f2.finished = false and f2.kickoff_at is not null
    and date_trunc('week', f2.kickoff_at at time zone 'Asia/Seoul')
      = date_trunc('week', f.kickoff_at  at time zone 'Asia/Seoul')
)
```

- `week_leaderboard` / `season_leaderboard`가 이 view 위에 있어 자동 적용된다. 더블 매치위크에서 첫 경기 점수가 시즌 랭킹으로 새는 것을 막는다.
- 킥오프 미정(`kickoff_at is null`)과 취소 경기는 세지 않는다 — `groupFixturesByWeek`과 같은 기준이라 화면/DB 판정이 어긋나지 않는다.
- 화면 정합은 이미 맞다: `status === 'result'`(주차 전 경기 종료)와 settled가 항상 동시에 성립하므로, 결과 화면이 빈 점수로 뜨는 구간이 없다.

### `weekly_scores` 테이블은 만들지 않는다

점수는 배당 스냅샷(`predictions.*_multiplier`) + 평점(`fixture_player_ratings`)으로 완전히 파생되고, "산식을 고치면 과거 경기 점수까지 같이 따라온다"가 기존 설계의 명시적 의도다(`20260821120000_create_predictions.sql` 주석). 지금 필요한 건 저장이 아니라 **노출 게이트**다.

정산 시점을 크론 스케줄로 통제하는 방안도 검토했으나 기각했다. 취소·연기 경기(FotMob이 `cancelled`를 내려주고 킥오프이 다음 주로 밀리는 경우)에서 바로 깨진다. 데이터 상태로 판정하면 그게 알아서 맞는다. **"언제 가져오나"(크론)와 "언제 공개하나"(view 조건)를 분리하는 것이 요구 3건을 동시에 만족시키는 가장 짧은 길이다.**

랭킹 조회가 무거워지면 그때 matview + 갱신으로 승격한다.

남은 것은 2b(대시보드) → 3 → 4 → 5. 1단계를 먼저 끝낸 이유는 실데이터 없이 3·4단계를 검증할 수 없기 때문이다.
