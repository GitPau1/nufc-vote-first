## 0-1. 조사 배경

Storybook에 우리 서비스 디자인시스템을 정리하려는 작업을 시작하면서, "정리 구조와 내용"의 참고 모델로 원티드의 **Montage**를 먼저 살펴봤다. 이후 "토큰에 사용 맥락(언제/어떻게 쓰는가)이 있는가, MCP 서버는 그 맥락을 어떻게 다루는가"라는 질문으로 조사가 확장되면서 당근의 **Seed Design**까지 비교 대상에 넣었다. 이 문서는 두 시스템에서 실제 코드/문서를 열어 확인한 내용만 담는다.

> **읽는 규칙**: 인용은 출처 파일을 함께 표기했다. "확인하지 않음"이라고 적힌 항목은 조사 범위 밖이며, 추론은 "추론"으로 명시했다.

## 1. Montage (원티드)

### 1.1 문서 사이트 구조

`montage.wanted.co.kr` 기준. **Storybook이 아니라 자체 제작 Next.js 앱**이다 (`docs/` 디렉토리, `create-next-app` 기반).

- **Foundations** (Base material): Color / Typography / Grid / Icons / Elevation
- **Components** — 6개 그룹, 60개 컴포넌트
  | 그룹 | 컴포넌트 |
  |---|---|
  | Actions | Action area, Button, Chip, Icon button, Text button |
  | Contents | Accordion, Avatar, Avatar group, Card, Content badge, List card, List cell, Play badge, Section header, Table, Thumbnail |
  | Feedback | Alert, Fallback view, Push badge, Section message, Snackbar, Toast |
  | Loading | Loading, Skeleton |
  | Navigations | Bottom navigation, Category, Page counter, Pagination, Pagination dots, Progress indicator, Progress tracker, Tab, Top navigation |
  | Presentation | Autocomplete, Bottom sheet, Menu, Popover, Popup, Tooltip |
  | Selection and Input | Check mark, Checkbox, Date picker, Filter button, Framed style, Radio, Search field, Segmented control, Select, Slider, Switch, Text area, Text field, Time picker |

컴포넌트 개별 문서(예: Button)는 Design / Web / iOS / Android 탭으로 나뉘고, Design 탭은 **Anatomy → Variants → States → Size → Loading → Usage → Application → Hierarchy → Layout → How to use(Do/Don't) → Customize** 순으로 구성된다.

### 1.2 토큰 아키텍처 — atomic → semantic 2계층

`packages/wds-theme/src/theme/`

- **atomic**: 색상 팔레트별 파일(`blue.ts`, `red.ts`, `coolNeutral.ts` 등). 숫자 웨이트로만 키를 매김. 의미 없음.
  ```ts
  const blue = { 10: '#001536', ..., 50: '#0066FF', ..., 99: '#F7FBFF' } as const;
  ```
- **semantic**: atomic + opacity를 조합해 역할·강조 단계로 재구성. `light`/`dark` 두 세트가 통째로 존재.
  ```ts
  export const light = {
    label: { normal, strong, neutral, alternative, assistive, disable },   // 6단계 강조 사다리
    background: { normal: {...}, elevated: {...}, transparent: {...}, status: {...} },
    line: { normal: {...}, solid: {...}, primary: {...}, status: {...} },
    interaction: { inactive, disable },
    fill: { normal, strong, alternative },
    accent: { background: {...7색}, foreground: {...11색} },
    elevation: { shadow: { normal, drop, spread } },  // 크기별(xsmall~xlarge) × 기법별 3종
  }
  ```
- opacity(15단계), spacing(0~80px, 20단계), breakpoint(xs~xl), z-index도 같은 방식의 flat 스케일.

### 1.3 토큰 소비 규칙 (실제 컴포넌트 코드로 확인)

`packages/wds/src/components/button/style.ts`:
```ts
case variant === 'solid' && color === 'primary':
  return css`
    color: ${theme.semantic.static.white};
    background-color: ${theme.semantic.primary.normal};
    &:disabled { color: ${theme.semantic.label.assistive};
                 background-color: ${theme.semantic.interaction.disable}; }
  `;
```

- **컴포넌트는 semantic만 참조하고, atomic은 직접 참조하지 않는다.** `.claude/references/architecture.md`에 명문화: "Reference `theme.semantic.*` over `theme.color.*`. Never hardcode hex values. If a token doesn't exist, add one in `wds-theme`".
- **상태(hover/pressed/disabled)는 opacity 계산이 아니라 전용 semantic 토큰으로 색을 교체**한다. 우리 프로젝트의 LDSG 기반 원칙(hover 0.7 / pressed 0.5)과 다른 철학이다.
- light/dark 전환은 `ThemeProvider`가 `next-themes`로 두 세트 중 하나를 통째로 주입 — 컴포넌트 코드는 바뀌지 않는다.
- 컴포넌트 폴더는 `index.tsx` + `types.ts` + `style.ts` 3파일로 통일.

### 1.4 타이포그래피 — 우리 프로젝트와 거의 동일

`packages/wds/src/components/typography/style.ts`의 letter-spacing 값이 우리 `tailwind.config.ts`와 소수점까지 거의 일치한다 (`display1: -0.0319em`, `headline1: -0.002em`, `caption2: 0.0311em`). 크기(variant)와 굵기(weight)는 독립된 두 축(`typographyStyle('body1', 'bold')`).

이유는 §3-1에서 확인했다 — 우리 타이포가 Wanted Design Library에서 온 것이다.

### 1.5 "맥락"의 위치 — 코드와 문서로 분리

토큰 정의 파일(`atomic/*.ts`, `semantic/index.ts`)에는 **주석이 없다.** 맥락은 두 갈래로 분리되어 있다.

1. **컴포넌트 prop의 JSDoc** — `.claude/references/coding-style.md`: "JSDoc every public prop. These comments surface in IDE tooltips and the docs site."
2. **문서 사이트용 `.mdx`** — `docs/data/components/actions/button/design.mdx`. 실제 인용:
   > "Level.4 → 화면 내에서 가장 중요한 메인 행동을 유도 및 제안합니다" (Solid Primary)
   > "변경된 타입은 자유롭지만, 사용자에게 혼란을 줄 수 있는 여지가 있는 Primary에서 Primary의 변경은 지양합니다" (토글 버튼 Do/Don't)

### 1.6 강제력 — 토큰 lint는 하지 않는다

`packages/eslint-plugin-wds/src/rules/`에 룰이 **2개뿐**이고 둘 다 접근성이다:
- `icon-button-uses-name` — 아이콘 버튼에 `name`/`aria-label` 필수
- `image-uses-alt`

즉 **Montage는 토큰 사용을 lint로 강제하지 않는다.** 우리 `design-foundation.test.mjs`(임의값 정규식 차단)가 이 축에서는 더 강하다.

### 1.7 AI 에이전트 지원

- `.claude/references/` — `architecture.md`, `coding-style.md`, `workflow.md` (모두 자기 저장소 내부 컨벤션 문서)
- `.claude/skills/` — `create-pr`, `sync-icons` (2개, 운영 작업용)
- `AGENTS.md` — 위 references로 라우팅하는 진입점
- `packages/wds-mcp` 존재. **내용은 조사하지 않았다.**

## 2. Seed Design (당근)

### 2.1 MCP 서버가 두 개, 역할이 다르다

| | `@seed-design/mcp` | `@seed-design/docs-mcp` |
|---|---|---|
| 정체 | Figma MCP 서버 | 문서 MCP 서버 |
| 하는 일 | Figma 파일 데이터 조회·편집·codegen (REST/WebSocket 이중 경로) | 가이드라인·토큰 스펙·아이콘 정보를 LLM에 도구로 제공 |
| 맥락 데이터 | 없음 (구조 데이터만) | **있음** |

`docs-mcp` 도구: `discover_seed_docs` / `list_docs` / `get_doc` / `get_full_docs` / `get_rootage` / `list_icons` / `search_icons` / `get_icon_details`

### 2.2 `rootage` — 토큰 + 컴포넌트 스펙의 단일 원천

`packages/rootage/`. YAML로 정의하고 `bun rootage:generate`로 CSS 변수 등을 생성. 네이밍은 `$type.category.name`. Light/dark가 **토큰 하나 안에** 있다:
```yaml
$color.palette.gray-500:
  values:
    theme-light: "#d1d3d8"
    theme-dark: "#5b606a"
```

### 2.3 `description` 필드가 스키마에 정식으로 존재한다

`packages/rootage/components/action-button.yaml` (JSON 스키마로 검증되는 정식 필드):

```yaml
variant:
  values:
    brandSolid:
      description: 브랜드의 핵심 가치를 전달하며, 사용자 간 연결이 일어나는
        서비스의 주요 기능에 사용합니다. 한 화면에 하나만 사용하는 것을 권장합니다.
    criticalSolid:
      description: 삭제나 초기화처럼 되돌릴 수 없는 중요한 작업에 사용합니다.
    neutralOutline:
      description: variant=brandSolid, neutralSolid, criticalSolid와 함께
        사용할 수 없으며, variant=brandOutline과 조합하여 사용하는 것을 권장합니다.
layout:
  values:
    iconOnly:
      description: 아이콘만으로 의미를 전달하기 때문에 접근성이 떨어집니다.
        꼭 필요한 경우에만 접근성 레이블과 함께 사용하는 것을 권장합니다.
slots:
  prefixIcon:
    description: 주로 액션의 의미를 보조합니다. suffixIcon과 함께 사용할 수 없습니다.
```

값 + "언제/왜 쓰는가" + "무엇과 같이 못 쓰는가" + 접근성 주의가 같은 파일에 공존한다. 상태(`enabled`/`pressed`/`disabled`/`loading`)도 코드 `switch`문이 아니라 이 YAML의 데이터로 정의된다.

### 2.4 **description 밀도는 "판단 난이도"에 비례한다** (실측)

컴포넌트 4개의 slot/variant 설명 유무를 직접 뽑아본 결과:

| 컴포넌트 | 설명이 붙은 slot | 설명 없는 slot | variant 설명 |
|---|---|---|---|
| badge | 없음 | root, label | 없음 |
| chip | prefixIcon | root, label, prefixAvatar, suffixIcon, icon | 없음 |
| callout | prefixIcon, link | root, title, description, suffixIcon | 없음 |
| action-button | icon, prefixIcon, suffixIcon | root, label, progressCircle | **7개 전부 있음** |

규칙:
- `root`/`label`/`title`처럼 **이름만으로 자명한 slot엔 설명이 없다.**
- **제약이 있는 slot에만** 붙는다 ("suffixIcon과 함께 사용할 수 없습니다").
- variant도 badge/chip/callout의 tone은 설명이 없고(이름이 곧 의미), action-button만 전부 있다 — 어느 걸 CTA로 쓸지 판단이 필요한 컴포넌트라서.
- 원시 팔레트(`$color.palette.gray-500`)엔 설명이 없고, 역할 색(`$color.bg.brand-solid`)엔 있다.

→ **"모든 것에 설명을 쓴다"가 아니라 "제약이나 판단이 있는 곳에만 쓴다"**가 실제 기준이다.

### 2.5 사람용 문서와 스펙이 같은 문장을 공유한다

`docs/content/components/action-button.mdx`(Anatomy/Properties/Guidelines/Hierarchy 구성)에 위 YAML의 `description`과 **글자 그대로 동일한 문장**이 등장한다("아이콘만으로 의미를 전달하기 때문에 접근성이 떨어집니다"). 자동 동기화 파이프라인은 확인하지 않았다.

### 2.6 Foundations 범위가 넓다 (15개)

`docs/content/foundations/`: color, typography, spacing, radius, elevation, gradient, layout, motion, **state**, iconography, design-token, writing, voice-and-tone, inclusive-design, international-design

`patterns/`는 `loading.mdx` 하나뿐 — 컴포넌트를 넘는 공통 관심사만 얇게 두는 카테고리.

**`state.mdx`의 구조** (값이 아니라 분류와 조합 규칙이 핵심):
- 상태를 두 유형으로 나눔 — **상호작용 상태**(pressed처럼 사용자 행동으로 변함) vs **옵션 상태**(disabled/selected처럼 옵션으로 정해짐)
- 각 상태(Enabled/Pressed/Selected/Disabled) 정의 + 겹칠 수 있는지 규칙
  > "Disabled는 ... 일반적으로 다른 상호작용 상태와 함께 표현되지 않습니다."

**`motion.mdx`의 구조**:
- 매크로(0.2초 초과, 페이지 전환·모달) / 마이크로(0.2초 이하, 버튼 클릭·포커스) 구분
- timing function 4종에 각각 용도 — `easing`(기능적 마이크로), `enter`/`exit`(시트·다이얼로그), `expressive`(강조)
- duration 토큰

### 2.7 **스킬 체계 — MCP 없이 맥락을 전달하는 방식**

`skills/` 디렉토리에 9개 스킬이 있다: `seed-design`(통합), `create-component`, `changeset`, `deprecation`, `migrate-component-docs-from-figma`, `snapshot-release`, `verify-figma-mcp-transports`, `write-lynx-component-docs`, `dev-figma-v3-migration-plugin`

#### 2.7.1 핵심 원칙 — 복사 금지

`skills/seed-design/SKILL.md` 첫 문단:
> SEED Design의 공식 문서와 CLI를 단일 원천으로 사용합니다. 이 스킬에는 **문서 내용을 복사하지 않고**, 공통 디자인 지식 → 플랫폼 구현 → 플랫폼별 Doctor로 이어지는 탐색·판정 절차만 둡니다.

문서 사이트(`docs/content/ai-integration/skill/index.mdx`)에서 이유를 밝힌다:
> 셋업 절차나 컴포넌트 목록, 토큰 이름은 공식 문서와 `docs` CLI가 원본이고 **복사본은 원본보다 먼저 낡습니다.**

이 문제를 실제로 겪었다는 증거: Doctor의 `unknown` 사유 분류에 **`doc-conflict`(공식 문서끼리 충돌하거나 두 가지로 읽힘)**가 별도 항목으로 존재한다.

#### 2.7.2 인덱스 라우팅

스킬은 문서 목록을 갖지 않고 실행 시점에 인덱스를 읽는다:
- `https://seed-design.io/llms.txt` (전체)
- `https://seed-design.io/react/llms.txt`, `/lynx/llms.txt` (플랫폼별)

> 인덱스가 제공한 leaf URL을 열어 실제 계약을 읽습니다. **기억한 경로나 URL 조합으로 leaf 문서를 만들지 않습니다.**

#### 2.7.3 Doctor — 읽기 전용 진단

`references/doctor.md` + `rules/*.md` 10개. category는 `config | compatibility | setup | foundations | components | library`.

**계약 위반과 맥락 적절성을 다른 룰로 분리한다.** `rules/foundation-contract.md`:
> ## 하지 않는 판단
> - 하드코딩 값이 나쁜지
> - semantic token 선택이 디자인 맥락에 적절한지
> - 토큰 값 자체가 화면 의도에 맞는지
>
> Doctor는 존재·공개성·제거·내부 API 의존 같은 **계약 위반만** 판정합니다.

**판정 기준을 룰 파일에 박지 않고 실행 시점에 문서에서 도출한다.** `rules/component-guidelines.md`:
> 판정 기준과 플랫폼 지원 목록은 이 파일에 두지 않습니다. 실행할 때 ... 개별 문서에서 도출합니다.
> `component-guidelines`의 기준은 룰 파일에 고정돼 있지 않습니다. **문서의 Do/Don't가 바뀌면 판정 기준도 함께 바뀝니다.**

→ 스키마 파이프라인 없이 drift를 막는 방법이다.

**"확인 안 했는데 통과처럼 보이는" 사고를 막는 장치들**:
- check status 4종: `pass | fail | not-applicable | not-verified`
- `unknown` 사유 4종: `no-threshold`(문서에 임계값 없음) / `runtime-dependent` / `not-in-code` / `doc-conflict`
- `coverage.expected != coverage.judged`면 **실행 결함**으로 간주
- `rejected` — "안 본 것"과 "보고 뺀 것"을 구분
- `findings[].remediation` — 설명문이 아니라 그 자체로 완결된 수정 요청 프롬프트. 생성만 하고 실행은 사용자 요청 전까지 안 함

#### 2.7.4 `create-component` — 신규 컴포넌트 절차

```text
Platform Gate → Delivery Surface Gate → Phase 0 Pre(Brainstorm) → Phase 0(Architecture) → Phase 1(Implementation) → Phase 2(Verification)
```
각 Phase 사이에 게이트가 있고, 통과 전엔 다음으로 안 간다. reference 파일은 **해당 Phase 진입 시점에 읽는다**(미리 다 읽지 않음).

**Phase 0 Pre의 5개 합의 영역** (`references/brainstorming.md`) — 한 영역씩 순서대로, 질문은 한 번에 하나, 객관식 우선:
1. Purpose (왜/누가/어떤 사용 사례)
2. 기존과의 관계 (신규/확장/대체)
3. 엣지케이스 시나리오 (상태·제어·키보드·스크린리더·모바일·폼·RTL·폰트스케일)
4. **토큰 의존성**
5. **외부 레퍼런스 우선순위**

이 단계가 빠지면 생기는 통증을 문서 스스로 명시한다:
> - 외부 레퍼런스를 임의로 골라 SEED 패턴과 충돌
> - **토큰을 임의 생성해 rootage가 비대해짐**

**Red Flags 표** (사용자가 이렇게 말하면 멈추고 확인):
| 시그널 | 의미 | 다음 행동 |
|---|---|---|
| "그냥 알아서 해줘" | 요구사항이 본인도 불명확 | 객관식 후보를 만들어 좁히기 |
| "Base UI처럼 만들어줘" | 외부를 그대로 베끼라는 신호 | 충돌 영역을 먼저 확인 |
| "엣지케이스는 나중에" | 가장 흔한 후회의 원인 | 코드 진입 전 합의해야 한다고 설명 |
| "토큰은 적당히..." | 토큰 임의 생성의 신호 | 책임자 확인 필요 |

**토큰이 부족할 때의 탈출구 3안** (트레이드오프와 함께 제시하고 사용자가 고름):
| 접근법 | 언제 | 트레이드오프 |
|---|---|---|
| Figma 동기화 기다림 | 디자인시스템 토큰을 Figma가 먼저 정의해야 할 때 | 안전하지만 느림 |
| 임시 추가 후 동기화 | 토큰 형태가 명확하고 Figma 정의가 뒤따를 예정일 때 | 빠르지만 동기화 리스크 |
| 컴포넌트별 vars만 사용 | 토큰 자체는 기존, 컴포넌트 vars 자동 생성 | 가장 안전, 가장 빠름 |

**외부 레퍼런스 차용 결정 트리** (`references/external-references.md`). 원칙: "외부 라이브러리는 영감이지 복사 대상이 아니다. SEED 아키텍처가 항상 최우선."
```text
외부 패턴 발견
  ├─ 기존 패턴과 충돌? ──Yes──> 거부
  └─ No → 같은 문제를 다른 방식으로 이미 푸는가?
            ├─ Yes → 거부 (같은 문제에 두 패턴 공존 금지)
            └─ No → 차용 가능. 단 naming을 기존과 정렬
```
추가로 **결정 영역별 1순위 레퍼런스 표**(headless 훅 API는 Base UI, compound 구조는 Radix, prop naming은 Chakra, snippet은 shadcn)와 **카테고리별 조사 깊이 표**가 있다.

### 2.8 Storybook은 시각 회귀 전용이다

`skills/create-component/references/storybook.md` + 실제 stories 형태:
```tsx
export const LightTheme = CommonStoryTemplate.extend({});
export const DarkTheme = CommonStoryTemplate.extend({
  parameters: withChromaticParameters({ theme: "dark" }),
});
export const FontScalingExtraExtraExtraLarge = CommonStoryTemplate.extend({
  parameters: withChromaticParameters({ fontScale: "Extra Extra Extra Large" }),
});
```

`VariantTable`을 라이트/다크 × 폰트스케일 조합으로 렌더해 **Chromatic 시각 회귀를 돌리는 기계 검증 표면**이다. 사용 규칙 산문은 stories에 없고 전부 문서 사이트(`docs/content/components/*.mdx`)에 있다.

→ **Montage는 Storybook을 안 쓰고(자체 Next.js 문서 사이트), Seed는 시각 회귀 전용으로만 쓴다.** 둘 중 어느 쪽도 Storybook을 사람이 읽는 규칙 카탈로그로 쓰지 않는다.

### 3-1. `design.md`와 `11-design-system.md`의 계보 (확인)

`vault/99_old/design.md`는 **LINE 디자인시스템(LDSG) 카탈로그 항목**이다. 프런트매터:


`11-design-system.md`는 **LDSG + Wanted 혼합**이다. 문서 안에 그렇게 적혀 있다:

| 영역 | 출처 | 근거 |
|---|---|---|
| 색상, radius, shadow, 상태 처리(opacity), 컴포넌트 패턴 | LDSG (LINE) | 3~6행 "LDSG 기반으로, Newcastle United 브랜드 색상을 적용한 커스텀" |
| 타이포그래피 스케일 | Wanted Design Library | 63행 "Wanted Design Library의 역할 기반 타입 스케일을 따른다" |
| 그리드/간격 | Wanted Design Library | 99행 "Wanted Design Library의 모바일 우선 그리드 원칙을 ... 적용한다" |

**왜 섞였는지도 `design.md`의 "Known Gaps"에 적혀 있다**:
> **Typography 픽셀 값**: 토큰명·용도 매핑은 명확하지만 픽셀·rem 값이 공식 페이지에 이미지로만 표기되어 텍스트 추출 불가
>
> **Spacing 토큰**: 글로벌 spacing 스케일 페이지 부재. 컴포넌트별 design spec 표에 케이스로만 정의 — 다운스트림이 스케일을 정의해야 한다

즉 LDSG가 타이포 픽셀값과 spacing 스케일을 공개하지 않아 그 두 영역만 Wanted에서 가져온 구조다. Pretendard를 쓰는 이유도 같은 섹션:
> **한국어(KR) Language Pack**: Typography Language Pack 1차 지원이 EN/JP/TC/TH로 한정 — 한국어 환경 적용 시 LINE Seed KR 또는 Pretendard Variable로 폴백 매핑을 다운스트림이 정의해야 한다

→ §1.4의 "Montage 타이포가 우리와 소수점까지 일치한다"는 관찰이 여기서 설명된다. Montage가 원티드 디자인시스템이고, 우리 타이포가 원티드에서 왔다.

**다른 서비스 카탈로그**: 리포 전체에서 `design_system_name` 프런트매터를 가진 파일은 `design.md` 하나뿐이다. `related_services`에 seed-design·toss·socar가 적혀 있고 로고 URL이 `getdesign.kr`을 가리키지만, **그 필드의 의미와 getdesign.kr에 다른 카탈로그가 있는지는 확인하지 않았다.**

## 4. 종합 인사이트

1. **MCP는 맥락을 만들어내는 장치가 아니라 이미 있는 문서/스펙을 API로 재노출하는 장치다.** 핵심은 MCP 유무가 아니라 "언제/왜 쓰는가"를 어디에, 어떤 단위로, 몇 개의 원본으로 관리하느냐다.
2. **Seed의 '복사 금지 + 인덱스 라우팅'이 우리 문제의 직접적 해답이다.** 스킬에 규칙을 복사하지 않고 인덱스를 통해 원본으로 라우팅하면, 원본만 고쳐도 판정이 따라온다.
3. **판정 계층은 "기계적 계약 검사"와 "맥락 적절성 판단"을 분리해야 한다.** Seed는 후자의 기준을 룰 파일에 박지 않고 실행 시점에 문서에서 도출해 drift를 원천 차단한다.
4. **설명은 판단이 필요한 곳에만 쓴다.** 모든 slot/variant에 설명을 다는 게 아니라, 제약(상호배제·개수 제한·접근성 경고)이 있는 곳에만 붙인다.
5. **레퍼런스는 영감이지 복사 대상이 아니다.** 결정 영역별 1순위를 정하고, 충돌 시 기존 시스템을 우선하는 결정 트리를 명문화한다. 토큰이 부족할 때는 임의 생성하지 않고 트레이드오프가 붙은 선택지를 사용자에게 제시한다.
6. **Storybook을 사람용 규칙 카탈로그로 쓰는 것은 두 참고 사례 어느 쪽도 하지 않는 방식이다.** 우리는 별도 문서 사이트를 만들 여력이 없어 Storybook에 그 역할을 겸하게 하는 선택을 했으므로(→ [[디자인시스템-스토리북-실행계획]]), 두 사례에서 검증된 구조가 아님을 알고 진행한다.
