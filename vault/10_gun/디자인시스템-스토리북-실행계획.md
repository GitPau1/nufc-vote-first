## 1. 목표 (Goal)

지금 가지고 있는 디자인 베이스를 정리해 **디자인시스템으로 정립하고, 그 기준으로 이후 만들어지는 모든 화면·컴포넌트(신규 화면뿐 아니라 이미지 레퍼런스를 보고 즉석에서 만드는 일회성 컴포넌트까지)가 일관성을 유지하게 한다.**

## 2. 요구사항 / 제약 (사용자 명시)

1. **구조·내용 참고 모델**: 원티드 Montage, 당근 Seed Design — [[디자인시스템-리서치-몽타주-시드디자인]] 참고.
2. **MCP 서버를 붙이지 않는다.** "맥락 전달"은 **Skill 매칭**으로 해결한다.
3. **기존 작업 방식을 그대로 존중한다**:
   > 만들 화면 정하기 → 관련 UX/UI 레퍼런스 조사 → 대략적인 방향성 수립 → lofi 시안으로 레이아웃 구성 확정 → 해당 lofi를 서비스 디자인에 맞게 재변형 → (이 과정에서 이미지 레퍼런스를 전달해 원하는 디자인을 만듦 — **이때 생기는 일회성 컴포넌트도 다른 컴포넌트처럼 정형화된 규칙을 따라야 함**) → 디테일 개선 → 핸드오프
4. 이 흐름은 이미 `.claude/skills/screen-design-workflow/SKILL.md`가 6단계로 구현하고 있다. **새 스킬을 만들지 않고 이 스킬을 보강한다.**
5. **확대해석 금지** — 조사 결과를 보고할 때 출처가 말한 범위를 넘지 않고, 확인 안 한 건 확인 안 했다고 표시한다.

```
1계층  토큰(foundation)   tailwind.config.ts + globals.css
                          └ 유지. state·motion 토큰만 추가

2계층  규칙 원본          frontend/src/storybook/**/*.mdx
                          └ 사용 규칙의 단일 원천. Storybook에서 시각 예시와 함께 렌더

3계층  라우팅 인덱스      frontend/src/storybook/DESIGN-SYSTEM.md
                          └ 스킬이 읽고 2계층으로 라우팅. 규칙을 여기 쓰지 않는다

4계층  판정              screen-design-workflow 6단계
                          └ 3계층 인덱스 → 2계층 MDX에서 판정 기준을 실행 시점에 도출
```

### 각 계층의 설계 근거 (리서치 대조)

| 계층 | 근거 |
|---|---|
| 1계층을 그대로 두는 이유 | atomic→semantic 2계층 리팩터의 가치는 테마 전환에서 나오는데 우리는 다크모드 계획이 없다 (리서치 §3-3 비교표) |
| 2계층을 Storybook MDX로 두는 이유 | 사용자 결정. 별도 문서 사이트를 만들 여력이 없어 Storybook이 그 역할을 겸한다. **두 참고 사례 어느 쪽도 안 하는 방식임을 알고 진행** (리서치 §4-6) |
| 3계층에 규칙을 쓰지 않는 이유 | Seed 원칙 — "복사본은 원본보다 먼저 낡습니다." 스킬은 목록을 갖지 않고 인덱스로 라우팅한다 (리서치 §2.7.1~2.7.2) |
| 4계층이 기준을 실행 시점에 도출하는 이유 | Seed `component-guidelines` — "판정 기준은 룰 파일에 고정돼 있지 않습니다. 문서의 Do/Don't가 바뀌면 판정 기준도 함께 바뀝니다." 스키마 파이프라인 없이 drift를 막는 방법 (리서치 §2.7.3) |

### 설명(description)을 쓰는 기준

Seed 실측(리서치 §2.4)에서 도출: **"모든 것에 쓴다"가 아니라 "제약이나 판단이 있는 곳에만 쓴다."**

| 대상 | 설명을 쓰는가 |
|---|---|
| 이름만으로 자명한 slot (root, label, title) | 안 쓴다 |
| 제약이 있는 slot (상호배제, 조건부 사용, 접근성 경고) | **쓴다** |
| 이름이 곧 의미인 variant (chip 색상 계열) | 안 쓴다 |
| 선택에 판단이 필요한 variant (어느 게 CTA인가) | **쓴다** |
| 원시 토큰 값 | 안 쓴다 |
| 역할 토큰 | **쓴다** |

### 3.5 — Palette + Semantic 재설계 (계획에 없던 추가 작업)

Phase 3에서 Color.mdx를 만든 뒤, "지금 프로덕트에 있는 것만 담아서 다양성·케이스가 부족하다"는 피드백을 받아 원시 색(palette) + 역할 색(semantic) 2계층을 새로 설계했다. 원래 계획에 없던 단계지만, 이후 Phase에서 만들 컴포넌트 색상이 전부 이 위에 올라가므로 먼저 처리했다.

**Palette** (`storybook/foundations/PaletteProposal.mdx`, `_internal/palette-proposal.ts`)
- OKLCH 색공간에서 11단계(50~950) 생성 — HSL은 같은 단계에서도 색상별 밝기가 들쭉날쭉해짐
- 앵커 7개: brand `#0a54ff`(사용자 지정), critical `#d93025`(기존 negative), positive `#2e9e4f`(기존 positive), warning `#d46a00`(과거 chip-eval 스펙), informative `#0891b2`, magic `#9333ea`, neutral(쿨톤, 최대 채도 0.010)
- **2차 피드백으로 재조정**: brand를 `#41b6e6`→`#0a54ff`로 바꾸며 informative(`#2563eb`, 색상각 0.3° 차이로 충돌)와 magic(`#7c3aed`, 29.8°로 애매)을 다시 잡음. 계열명도 `sky`→`blue`로 변경
- **neutral 채도 곡선을 실측으로 교정**: Montage `coolNeutral` 16단계를 측정해 채도가 선형이 아니라 가우시안(종 모양)임을 확인. 처음 만든 안은 가장 밝은 단계가 Montage보다 8배 진해 "너무 세다"는 피드백을 받음 → 곡선을 가우시안으로 재작성, 강도 default(0.010, Montage의 70%)로 확정

**Semantic** (`storybook/foundations/SemanticProposal.mdx`, `_internal/semantic-proposal.ts`)
- 축: `bg-{intent}-{prominence}[-{state}]` / `text-{intent}` / `border-{intent}-{prominence}`. intent 7개, prominence는 solid/weak, pressed는 opacity 계산에서 토큰으로 전환(사용자 결정)
- **대비 실측으로 solid 축소를 정당화**: 6개 계열의 텍스트 대비를 500~900단계까지 전부 측정. **700단계부터 예외 없이 WCAG AA(4.5:1) 통과**, 600 이하는 전부 미달. brand·critical·magic만 anchor 자체가 AA를 통과해 solid 배경(흰 텍스트용)을 그 셋에만 둠 — 나머지(positive·warning·informative)는 weak만 두는데, 이게 "지금 badge/chip이 전부 weak만 쓴다"는 기존 코드 근거와도 일치
- **부수 발견**: 현재 프로덕션 `text-positive`(`#2e9e4f`)가 이미 AA 미달(3.43:1)이었다. 700단계로 교체하면 4.56:1로 처음 통과
- 근거 있는 공백 3곳을 formalize: `bg-black/45`(모달 3곳) → `bg-overlay`, `active:bg-disabled`를 press 피드백으로 재사용하던 것(PollCard) → 별도 이름의 `bg-neutral-weak-pressed`, warning 계열 부재 → `bg-warning-weak`/`fg-warning` 신설
- `fg-on-solid`는 intent별로 안 나누고 하나로 공유(간소화, 근거는 문서에 기록) — Seed는 intent마다 분리하지만 다크모드가 없어 불필요

**작업 중 재발한 버그**: MDX 표현식을 백틱(인라인 코드) 안에 넣어 평가 안 되고 문자 그대로 렌더되는 문제가 **두 번째로** 발생. 전체 문서를 grep으로 재검사해 추가 발생 없음을 확인. 헬퍼 컴포넌트의 임의값 클래스(`w-[220px]` 등)도 표준 스케일로 교체.

**상태 갱신 (2026-08-22)**: Palette + Semantic CSS 변수를 `globals.css`에, Tailwind 유틸리티를 `tailwind.config.ts`에 **추가 반영했다** (기존 클래스는 안 건드림 — 아래 §3.7 참고).

### 3.6 — positive↔informative 구분 문제 + red↔orange 재검증 (사용자 지적)

Semantic 리뷰 중 "positive와 informative가 언뜻 비슷해 보인다"는 피드백을 받아 재조사했다.

- **원인**: 색상각 간격(73.1°)은 Montage 실측(green↔cyan 70.0°)과 거의 일치했다. 문제는 채도 비율 — Montage는 green을 cyan보다 1.62배 진하게 만드는데 우리는 1.38배뿐이었고, 700단계가 전 계열 명도를 강제로 통일하는 규칙과 겹쳐 명도로도 구분이 안 됐다.
- **결정 및 반영**: "이 기준(Montage 실측 비율)에 따라 개선"하기로 하고, (a) 700단계 채도 캡 0.92→1.00 해제(6개 계열 전체), (b) green의 700단계만 명도 0.550→0.542·채도 1.176배 예외 적용. ΔE 0.148→0.178 (Montage 0.211에 근접). `palette.mjs`/`palette-proposal.ts`/`SemanticProposal.mdx`에 반영 완료.
- **부수 발견 — red↔orange도 문제였다**: 같은 방법으로 재검증하니 critical↔warning 간격(24.3°)이 Montage 자신의 red↔orange 간격(35.2°)의 절반도 안 됐다. **이전 v0.1~v0.2에서 "충분하다"고 판단했던 게 실제로는 확인 없이 넘어간 것**이었다 — 이번에 처음 제대로 검증됨.
- **red↔orange는 미반영**: 채도를 올리는 건 역효과였다(같은 방향으로 채도를 올리면 거리가 0.123→0.097로 오히려 줄었다). 색상각을 넓히는 것만 유효했는데, 얼마나 넓혀야 "여전히 오렌지로 보이는지"는 눈으로 판단할 문제라 65°/75°/85° 후보 3개만 문서에 남기고 확정하지 않았다.
- **교훈**: "충분하다"고 판단한 근거 없는 결론은 나중에 같은 방법으로 재검증되면 뒤집힐 수 있다. 이번처럼 한 쌍에 방법론을 적용하면 유사한 다른 쌍에도 같은 방법론을 적용해 일관성을 확인해야 한다.
- **red↔orange 확정**: 65°/75°/85° 후보를 눈으로 비교해 **75°**로 확정. 85°는 거리가 가장 크지만(0.133) "오렌지"보다 "황토색"에 가까워 보이기 시작해 제외. `orange` 앵커를 hue 53.3°→75°로 회전.
- **반영 중 잡은 버그**: `hueShift`를 도(degree) 단위로 넘겼는데 함수 내부의 각도는 라디안이라, 변환 없이 더해서 오렌지가 아니라 청록색이 나왔다. 도→라디안 변환을 추가해 고쳤다. 다른 계열은 `hueShift`를 0(기본값)으로만 써서 이 버그의 영향을 안 받았음을 확인.
- **fg-neutral-subtle/placeholder/disabled가 동일했던 문제**: 확인 없이 셋을 같은 값으로 만든 것이었다. 코드 재검사 결과 placeholder 지정도 이미 안 통일(4곳 중 3곳 `text-gray-3`, 1곳 `text-muted-foreground`). Montage 실측값(`label.assistive` 28%↔`label.disable` 16% opacity)이 서로 다른 걸 확인하고, disabled만 한 단계(neutral-500→400) 밝게 분리. subtle·placeholder는 "읽혀야 하는 보조 텍스트"라는 같은 역할이라 유지(Montage의 `assistive`가 두 역할을 겸하는 것과 동일 논리).
- **재발 방지**: 같은 실패가 세션 내에서 반복돼(1차 Foundations 문서, 2차 red↔orange, 3차 subtle/placeholder/disabled) 메모리 3건 정리 — `no-over-extrapolation`(범위 좁혀 적었던 걸 확장), `reader-first-for-artifacts`, 신규 `verify-before-assert`(근본 원인: 확인 없이 넘어가는 것 자체). 이후 최종 커밋 전 전체 재검증을 명시적으로 한 번 더 수행(§3.7 도입부).

### 3.7 — Palette + Semantic을 실제 코드에 반영 (추가 반영, 기존 클래스는 안 건드림)

커밋 직전 전체 최종값을 재검증했다 — 6개 계열 전부 AA(4.5:1) 통과, 모든 쌍 hue 간격 30° 이상(critical↔warning 32.7°로 목표 달성). 이후 반영:

- `globals.css`: `--p-{family}-{step}` 팔레트 변수 77개, `--sem-{bg|fg|stroke}-{name}` semantic 변수 39개 추가. semantic 변수는 팔레트 변수를 `var()`로 참조해 원본이 하나로 유지됨.
- `tailwind.config.ts`: `backgroundColor`/`textColor`/`borderColor`를 (기존처럼 공유 `colors` 객체가 아니라) **별도 extend 블록**으로 추가 — 이유는 아래.
- **이름 충돌 검사**: 신규 토큰 이름을 기존 Tailwind 클래스 목록과 전부 대조. `bg-disabled`(기존 #ebebeb ↔ 신규 neutral-200), `text-disabled`(실사용 1곳 확인됨), `text-positive`(실사용 9곳 확인됨) 3개는 이름은 같지만 값이 달라 지금 노출하면 기존 화면이 조용히 바뀐다 — **Tailwind 클래스로는 아직 안 열었다.** CSS 변수(`--sem-bg-disabled` 등)는 준비해뒀고, 실제 노출은 다음 단계(기존 이름 전체 이전)에서 화면별로 검토하며 한다.
- **검증**: 신규 클래스가 실제로 생성되는지 확인하려다 두 가지를 거쳤다. 먼저 독립 Tailwind CLI로 강제 컴파일을 시도했으나 커스텀 `.ts` config가 제대로 로드되지 않아 전부 실패로 나왔다(디버깅 대신 이미 동작이 확인된 실제 빌드 파이프라인으로 전환). `Overview.mdx`에 신규 클래스 35개를 임시로 노출해 Storybook을 빌드하고 CSS 산출물에서 35개 전부(`.bg-informative-weak{background-color:var(--sem-bg-informative-weak)}` 등) 정확히 생성되는 걸 확인한 뒤 임시 코드 제거.
- **회귀 확인**: 앱 빌드 성공, 테스트 90/90, lint 신규 경고 0건.

**다음 단계**: 기존 토큰 이름 전체 이전(`primary`→`brand`, `negative`→`critical`, `bg-disabled`/`text-disabled`/`text-positive` 값 교체 포함) — 이건 파일 수가 많고 화면별 확인이 필요해 별도로 진행한다.

### 3.8 — 이름 충돌 3개 전환 + primary 계열 전체 이전 (2026-08-22)

사용자 결정: 토큰별로 순서대로(primary부터), 이름 충돌 3개는 값 전환(살짝 바뀜 감수).

**이름 충돌 전환** — `bg-disabled`(#ebebeb→neutral-200, 49건), `text-disabled`(#a8a8a8→neutral-400, 1건), `text-positive`(#2e9e4f AA 미달→green-700 AA 통과, 9건). `disabled`/`positive`를 공유 `colors` 객체에서 빼고 `backgroundColor`/`textColor` 개별 블록으로 분리(bg/text가 서로 다른 값을 써야 해서).

**primary→brand 전체 이전** — 대상 30개 파일(사전 측정: `bg-primary` 30개·64건, `text-primary` 24개·51건 등, 고유 파일 42개 중 30개가 primary 계열). 매핑: `bg-primary`→`bg-brand-solid`, `bg-primary-dark`→`bg-brand-solid`(대비 재검증 결과 -dark 변형이 새 시스템에서 불필요해져 흡수), `bg-primary-dim`→`bg-brand-weak`, `border-primary`→`border-brand-solid`, `ring-primary`→`ring-brand-solid`(Tailwind는 ring을 border와 별도 테마 키로 다뤄서 `ringColor` 확장 추가), `text-primary`→`text-brand`, `text-primary-dark`→`text-brand`, `text-primary-foreground`→`text-on-solid`.

**사고 — storybook/ 제외 필터 실패**: perl 일괄 치환 시 `grep -v "^./storybook"` 제외가 이번엔 안 먹혀서 문서 6개(Overview.mdx, Color.mdx, State.mdx, SemanticProposal.mdx, semantic-proposal.ts, ColorSwatch.tsx)까지 같이 치환됐다. `Color.mdx`에서 **자기 자신과 모순되는 문장**이 생김("`text-brand`를 쓰지 않는다 ... 항상 `text-brand`를 쓴다" — 원래 "primary는 쓰지 말고 primary-dark를 쓰라"였는데 둘 다 brand로 바뀌어 모순), Brand 스와치도 3개(solid/dim/dark)가 2개로 중복·소실. `semantic-proposal.ts`의 note 4곳도 "bg-brand-solid가 bg-brand-solid를 대체한다"는 자기참조로 깨짐. 전부 수동으로 다시 확인해 고쳤다 — Color.mdx는 새 시스템 사실(brand 앵커가 대비를 이미 통과해 -dark 변형이 정말로 사라졌다는 것)에 맞게 문단을 재작성, note 4곳은 옛 이름 참조를 복원.

**테스트 회귀 2건**: `design-foundation.test.mjs`(carousel `bg-primary-dark` 리터럴 검사), `players-page-client.test.mjs`(`ring-primary` 리터럴 검사) — 둘 다 디자인 의도는 그대로고 클래스 이름만 바뀐 것이라 새 이름으로 갱신하고 이유를 주석으로 남김.

**검증**: 앱 빌드·Storybook 빌드 성공, 테스트 90/90, lint 신규 경고 0건. 실앱 파일(storybook 제외) 전수 재검사로 옛 primary 계열 잔존 0건 확인. 컴파일된 CSS에서 `bg-brand-solid`/`text-brand`/`ring-brand-solid` 등 실제 값 확인.

**다음**: `negative`→`critical`, `positive-dim`→`positive-weak`, `gray-*`→`neutral-*` 순서로 계속.

**검증**: 실앱 파일 잔존 0건, 앱 빌드·Storybook 빌드 성공, 테스트 90/90, CSS 값(`bg-critical-weak`/`text-critical`/`border-critical-weak`) 확인.

### 3.11 — gray-*→neutral-* 이전 (2026-08-22)

10개 파일. `text-gray-3`는 문맥에 따라 셋으로 갈라야 했다 — 같은 클래스 이름이 위치(pseudo-class)에 따라 실제로 다른 역할(본문 흐림/힌트/비활성)을 하고 있었기 때문이다.

매핑:
- `disabled:text-gray-3` → `disabled:text-disabled`
- `placeholder:text-gray-3` → `placeholder:text-placeholder`
- bare/`hover:text-gray-3` → `text-neutral-subtle`
- `text-gray-2` → `text-neutral-muted`
- `bg-gray-4` → `bg-neutral-weak`
- `border-gray-4` → `border-neutral-weak`

**의도적으로 미이전 — 새 3단계 체계에 대응 칸이 없는 진짜 gap 3건**:

| 패턴 | 실사용처 | 미이전 사유 |
|---|---|---|
| `text-gray-1` (4건) | `PlayersPageClient.tsx:275,321`, `CommentsSection.tsx:184`, `ResultView.tsx:112` — 굵게 강조하는 라벨 | `foreground`와 `muted-foreground` 사이 위계라 새 3단계(neutral/neutral-muted/neutral-subtle)에 그대로 대응 안 됨 |
| `bg-gray-1` (1건) | `PlayersPageClient.tsx:414` — Pick One 카드 전용 어두운 배경 | 이미 State.mdx에 예외로 기록된 카드 전용 값과 같은 계열, bespoke 취급 |
| `hover:border-gray-3` (1건) | `PlayerPickModal.tsx:123` — 미선택 카드 hover 테두리 | 새 stroke 스케일에 hover용 중간 회색 테두리 단계가 없음 |

세 항목 다 "억지로 끼워 맞추면 틀린 매핑이 된다"고 판단해 옛 이름 그대로 남겼다 — 4번째 neutral 단계를 새로 만들지, bespoke 예외로 문서화만 할지는 아직 사용자 결정 대기.

**exclusion 필터**: 3.10과 동일하게 `^storybook` 패턴으로 정상 작동, storybook 문서 변경 없음.

**검증**: 앱 빌드 성공, 테스트 90/90, Storybook 빌드 성공. 컴파일된 CSS에서 `.text-neutral-subtle`/`.text-neutral-muted`/`.text-disabled`/`.bg-neutral-weak`/`.border-neutral-weak` 실값 확인. `.text-placeholder`가 처음엔 CSS에 "없는" 것처럼 보였는데, 원인은 버그가 아니라 검색 패턴 오류였다 — `placeholder:` variant는 Tailwind가 콜론을 이스케이프해 `::placeholder` 의사 요소로 컴파일하므로(`.placeholder\:text-placeholder::placeholder{color:var(--sem-fg-placeholder)}`), 이스케이프 없는 셀렉터로 찾으면 안 나온다. 올바른 패턴으로 재검색해 정상 생성 확인.

**추가 발견 — Foundations 문서가 이번 이전과 어긋남**: `Color.mdx`(텍스트 위계 섹션)와 `State.mdx`(Disabled 섹션)가 여전히 `text-gray-1`/`text-gray-3`/`disabled:text-gray-3`를 실제 `className`으로 문서화하고 있다. 이 클래스들은 tailwind.config.ts의 옛 `gray` 팔레트가 아직 남아 있어 빌드는 되지만, 지금 실앱 코드가 가리키는 토큰(`text-neutral-subtle`, `disabled:text-disabled` 등)과는 이름이 어긋난 상태다. 문서 갱신은 Phase 4(컴포넌트 문서화) 범위로 볼지, 지금 바로 고칠지 사용자 확인 필요.

### 3.12 — neutral 4번째 단계(`neutral-strong`) 신설 (2026-08-22)

사용자 결정: 3.11에서 남긴 gap 3건을 억지로 3단계에 끼워 맞추지 않고, 4번째 단계를 새로 만들어 대응.

**실측값 대조** — 신규 팔레트 값을 만들지 않고, 기존 11단계 팔레트 중 이미 있는 단계가 옛 gray 값과 거의 일치하는 걸 확인해 그대로 재사용했다.

| 옛 값 | 신규 팔레트 단계 | 오차 |

| `--c-gray-1` `#333333` | `--p-neutral-900` `#313335` | 각 채널 ±2, 육안 구분 불가 |

- `--sem-bg-neutral-strong` = neutral-900 → `bg-neutral-strong` (어두운 중립 배경, Pick One 카드 전용)
- `--sem-stroke-neutral-strong` = neutral-500 → `border-neutral-strong` (hover 강조 테두리)

### 3.13 — Foundations 문서(Color.mdx/State.mdx/Overview.mdx) 옛 이름 정리 (2026-08-22)

사용자 지적: 3.9~3.12에서 storybook을 의도적으로 제외하고 앱 코드만 이전해온 탓에, Foundations 문서가 이미 폐기한 옛 이름(`gray-1/3`, `positive-dim`)을 여전히 "이걸 써라"로 안내하고 있었다. 문서가 앱 코드보다 뒤처진 상태.

**고친 범위 — "지금 뭘 써야 하는지" 안내하는 문서만**:
- `Color.mdx` 텍스트 섹션: `text-gray-1`→`text-neutral-strong`, `text-gray-3`(뭉뚱그림)→`text-neutral-subtle`/`placeholder:text-placeholder`/`disabled:text-disabled` 3갈래로 분리해 재작성(실제 코드가 이미 이렇게 갈라 쓰고 있으므로 문서도 맞춤). "상태" 섹션 `bg-positive-dim`→`bg-positive-weak`.
- `State.mdx` Disabled 섹션: `text-gray-3`→`text-disabled`(코드 블록 + 프로즈 모두).
- `Overview.mdx`: className(`bg-positive-dim`→`bg-positive-weak`, `text-gray-3`→`text-disabled`, `bg-gray-4`×5→`bg-neutral-weak`) 및 화면에 찍히는 라벨 텍스트(`primary`→`brand`, `primary-dim`→`brand-weak`, `negative`→`critical`)까지 전부 새 이름으로 통일. 라벨을 옛 이름으로 남겨두기로 한 이전 결정(§3.8)은 이번 사용자 지시로 번복됨 — "익숙한 이름 유지"보다 "문서가 옛 이름을 안 가르친다"를 우선.

**의도적으로 안 고친 것**: `SemanticProposal.mdx`와 `semantic-proposal.ts`의 note 필드. 둘 다 "왜 이름이 이렇게 바뀌었는가"를 설명하는 히스토리 기록이라, 옛 이름을 현재형으로 쓰는 게 아니라 과거 상태를 서술하는 문장이다. 여기까지 새 이름으로 바꾸면 역사 기록이 틀린 내용이 된다 — 사용자 확인 필요하면 알려달라고 남김.

**검증**: Foundations 문서·Overview.mdx 전수 재검사로 `gray-1~4`/`positive-dim`/`bg-primary`/`text-primary`/`negative` 잔존 0건. Storybook 빌드 성공, 앱 빌드 성공, 테스트 90/90.

### 3.15 — pressed 토큰 전환 (2026-08-22)

§3.14에서 보존해둔 체크리스트(4개 파일)를 그대로 적용하려다, **AA 대비 계산에서 두 가지를 새로 발견**했다.

**계산 스크립트 자체의 버그를 먼저 잡았다**: 이번 턴에서 새로 짠 인라인 대비 계산 스크립트가 `hex2rgb`의 문자열 인덱스를 `[1,3,5]`(앞에 `#`가 있는 hex 기준)로 잘못 잡아서, `#` 없는 6자리 hex를 넣을 때마다 색을 잘못 읽고 있었다. 검산(`#000000`/`#ffffff` → 21.00)으로 고친 뒤 재확인 — 이전에 이 버그로 계산했던 neutral-strong 대비(§3.12, "13.01"로 보고)는 결론(AA 통과)은 안 바뀌지만 수치 자체는 틀렸었다(정확한 값은 12.68). **결론이 안 바뀐 경우라도 계산기 버그는 계산기 버그다** — 이후 모든 수치는 검산된 스크립트로 다시 뽑았다.

**실제로 AA를 깨는 조합 2건을 찾았다** — 원래 체크리스트(§3.14)는 값을 미리 계산하지 않고 "같은 계열 유지"라는 방향성만 정한 상태였다.

| 케이스 | 시도한 값 | 대비 | 판정 |
|---|---|---|---|
| destructive 버튼: `text-critical` on `bg-critical-weak-pressed` | red-700 on red-200 | 3.94:1 | **미달** (평상시 critical-weak 자체도 4.54:1로 턱걸이라 한 단계만 진해져도 깨짐) |
| `MatchWeekList`: `text-muted-foreground` on `bg-brand-weak-pressed` | #666666 on blue-200 | 4.48:1 | **미달** (기존 `active:bg-disabled` 상태의 4.73:1보다 후퇴) |
| `PollCard`: `text-muted-foreground` on `bg-neutral-weak-pressed` | #666666 on neutral-300 | 4.06:1 | **미달** (기존 4.73:1보다 후퇴) |

**처리**: 세 곳 다 "한 단계 더 진하게"를 포기하고 이미 대비가 검증된 톤을 재사용했다.
- destructive → `active:opacity-50` 유지(색 교체 안 함)
- `MatchWeekList` → `active:bg-brand-weak-pressed` 대신 `active:bg-brand-weak`(hover와 같은 톤)
- `PollCard` → `active:bg-neutral-weak-pressed` 대신 `active:bg-neutral-weak`(값은 기존 `bg-disabled`와 동일 — 시각적으로는 그대로지만 "disabled 색을 press 피드백으로 재사용"하던 이름만 바로잡음)

**실제로 적용한 3건**:
- `ui/button.tsx` default 변형: `active:bg-brand-solid-pressed`(white on blue-800, 8.21:1 통과)
- `ui/button.tsx` secondary 변형: `active:bg-neutral-weak-pressed`(text-foreground는 거의 검정이라 13.36:1로 여유 통과)
- `ui/badge.tsx`: 체크리스트대로 변경 없음(칩은 press 대상이 아님)

**미착수로 남긴 것**: destructive 버튼, `MatchWeekList`, `PollCard`의 pressed는 여전히 opacity 또는 값이 안 바뀐 색 재사용이다 — "pressed는 전부 색 토큰으로"라는 원래 목표를 세 곳에서 완전히 달성하지 못했다. 더 진한 톤을 안전하게 쓰려면 semantic 단계 자체(critical-weak-pressed, brand-weak-pressed, neutral-weak-pressed)를 재조정해야 하는데, 이건 다른 화면(배지·칩 등)에서 이미 쓰이는 값이라 지금 바꾸면 파급 범위가 커진다 — 별도 논의 필요.

**State.mdx 갱신**: "상호작용 상태는 opacity로" 단일 원칙을 "hover는 항상 opacity, pressed는 배경에 색이 있으면 토큰·없으면 opacity"로 재작성. 위 3건의 AA 미달 사례를 실측 표로 문서에 남겨, 다음에 pressed 토큰을 더 넓게 적용할 때 같은 실수(값 미리 계산 안 하고 방향성만으로 진행)를 반복하지 않게 했다.

**검증**: 앱 빌드 성공, Storybook 빌드 성공, `design-foundation.test.mjs` 9/9 + 지정 테스트 스크립트 전부 통과. 컴파일된 CSS에서 `active:bg-brand-solid-pressed`(default 버튼)·`active:bg-neutral-weak-pressed`(secondary 버튼)·`active:bg-brand-weak`(MatchWeekList)·`active:bg-neutral-weak`(PollCard)·`active:opacity-50`(destructive·outline·ghost·link) 전부 생성 확인. `active:bg-critical-weak-pressed`(AA 미달로 폐기)와 `active:bg-brand-weak-pressed`(MatchWeekList용, AA 미달로 폐기)는 의도대로 미생성 확인.

### 3.16 — weak/weak-pressed 배경 재조정 (2026-08-22)

§3.15에서 "critical-weak-pressed 등 pressed 단계값을 다시 조정해보자"는 요청으로 시작했는데, 파보니 **pressed보다 먼저 rest(평상시) 상태가 이미 깨져 있는 라이브 버그**를 발견했다.

**발견 — 6개 계열 전부 fg-{intent}(700, 고정)를 자기 weak 배경 위에 올리면 문제가 있었다**:

| 계열 | weak(rest) | weak-pressed | 실사용 |
|---|---|---|---|
| brand(blue) | 4.69 통과 | 4.16 미달 | 배지·버튼 다수 |
| critical(red) | 4.54 통과(턱걸이) | 3.94 미달 | 버튼·배지·에러메시지 5곳 |
| **positive(green)** | **4.29 미달** | 3.94 미달 | **배지 3곳 — 라이브 버그** |
| warning(orange) | 4.42 미달 | 4.00 미달 | 미사용 |
| informative(cyan) | 4.19 미달 | 3.87 미달 | 미사용 |
| magic(violet) | 4.85 통과 | 4.30 미달 | 미사용 |

원인은 §3.5에서 700단계를 정할 때 **흰 배경 위 대비만 쟀지, 자기 자신의 weak 배경 위는 확인한 적이 없었던 것** — `bg-{intent}-weak` + `text-{intent}`(배지 패턴)는 실제로 한 번도 검증되지 않은 조합이었다.

**계산 스크립트 버그 재발**: 이번에도 이 조사 도중 새로 짠 대비 계산 스크립트에 버그가 있었다(하나는 hex 인덱스 오프셋, 하나는 0~1 정규화 값에 0~255 스케일 함수를 잘못 적용) — 매번 흑백(`#000000`/`#ffffff` → 21.00)으로 검산해서 잡았다. **패턴 재발 방지가 안 되고 있다**는 신호로 남겨둔다.

**구조적 한계 확인**: weak 자체가 이미 대비 여유가 거의 0인 지점까지 밝아져야 통과하는 계열이 많아서, **weak-pressed를 그보다 더 어둡게 만들 여지가 6개 계열 전부 없다**(이분탐색으로 weak의 최소 요구 L을 구하면, 그 아래로는 즉시 AA 미달). 텍스트를 700에 고정하는 한 "배경만 진해지는 pressed"는 이 6개 계열에서 애초에 불가능한 설계였다.

**사용자 결정**: fg-{intent}는 그대로 두고(text-brand 등 흰 배경 위 사용처가 넓어 안 건드림), weak 배경 쪽을 6개 계열 전부 지금 재조정.

**최종 값** (OKLCH에서 목표 대비 4.55로 역산, green·cyan은 순도 100%로는 흰색까지 가도 대비가 안 나와 채도를 절반(chromaMult 0.5)까지 낮춤):

| 계열 | 기존 weak | 새 weak = weak-pressed | 대비 |
|---|---|---|---|
| brand | `#dcf4ff` | `#d8f1ff` | 4.57 |
| critical | `#ffe7df` | `#ffe8e0` | 4.57 |
| positive | `#e2fce5` | `#f4fff5` | 4.55 |
| warning | `#fff0d5` | `#fff5d9` | 4.57 |
| informative | `#dff8ff` | `#f5ffff` | 4.55 |
| magic | `#fceaff` | `#f4e3ff` | 4.57 |

brand·critical·warning은 기존 값과 거의 구분 안 될 만큼 차이가 작다(1~2 단위). **positive·informative는 눈에 띄게 밝아졌다** — 특히 positive는 실사용 중(선수 포지션 배지 DEF 태그 등)이라 화면상 색이 옅어지는 게 사용자에게 보일 것이다. informative는 미사용이라 지금은 영향 없음.

**weak-pressed는 weak을 `var()`로 그대로 참조**한다(값 중복 대신 참조로 묶어 drift 방지) — 위 구조적 한계 때문에 둘을 다르게 둘 수가 없다. 색이 있는 배경에서 눌림 피드백이 필요해지면 색 교체가 아니라 opacity를 쓴다(§3.15에서 이미 이 결론에 도달한 destructive 버튼과 같은 처리).

**구현**: `--sem-bg-{intent}-weak`을 `var(--p-{family}-100)` 참조 대신 새로 계산한 hex를 직접 박아 넣는 방식으로 바꿨다 — 원시 팔레트 100/200단계(`--p-red-200`은 `--sem-stroke-critical-weak`에서도 쓰이는 등 다른 용도와 공유돼 있어) 자체를 바꾸면 파급 범위가 넓어지는 걸 피하려는 의도. 원시 팔레트 값은 그대로 두고 semantic 계층에서만 새 값을 쓴다.

**검증**: 앱 빌드·Storybook 빌드 성공, `design-foundation.test.mjs` 9/9 + 지정 테스트 스크립트 전부 통과. 컴파일된 CSS에서 6개 계열의 `--sem-bg-{intent}-weak-pressed`가 전부 `var(--sem-bg-{intent}-weak)`로 정확히 참조되는 것 확인. 6개 계열 전부 독립적으로 새로 짠 스크립트로 교차검산(4.55~4.57, 전부 통과).

### 3.17 — §3.14 과잉 삭제 정정: Palette/Semantic 참조 페이지 복원 (2026-08-22)

사용자 지적: "storybook 업데이트는 하고 있어? palette랑 semantic에 있던 내용들이 없던데."

**§3.14의 판단 오류**: `PaletteProposal.mdx`/`SemanticProposal.mdx`를 지운 근거는 "제안(proposal) 프레이밍과 뒤집힌 결정이 남은 **서술**이 이제 사실이 아니다"였는데, 이 판단은 맞았다. 문제는 실행 — 서술만 지워야 했는데 **같은 파일 안에 있던 원시 팔레트 색상표(7계열×11단계)와 semantic 토큰 전체 목록(39개, warning·informative·magic 포함)까지 통째로 지웠다.** 이 데이터는 서술과 달리 지금도 유효한 참조 자료였다.

**차이를 못 가른 이유**: "제안 페이지 폐기"를 파일 단위로 판단했지, 파일 안에서 "이제 틀린 서술"과 "지금도 맞는 데이터"가 섞여 있다는 걸 구분하지 않았다.

**복원 — 단, 옛 방식 그대로 되살리지 않았다**: 원래 `palette-proposal.ts`/`semantic-proposal.ts`는 손으로 유지하는 하드코딩 데이터 파일이라 실제 CSS 값과 어긋날 위험이 있었다(이번 §3.16처럼 값이 바뀔 때마다 두 곳을 같이 고쳐야 함). 대신 `Color.mdx`가 이미 쓰던 방식 — 실제로 클래스를 적용한 요소의 `getComputedStyle`을 읽어 표시 — 로 다시 만들어서 값이 바뀌면 문서가 자동으로 따라가게 했다.

- `foundations/Palette.mdx`(신규) — 7계열×11단계 원시 팔레트. "제안" 프레이밍 없음, `--p-*` CSS 변수를 `_internal/PaletteSwatch.tsx`(신규, inline style로 변수 참조 + computed value 표시)로 렌더링.
- `foundations/Semantic.mdx`(신규) — bg/text/border 39개 토큰 전체 목록. 기존 `ColorSwatch`/`TextSwatch` 재사용. `ColorSwatch`에 `readProperty` prop을 추가해(`backgroundColor` 기본값 / `borderColor`) border 토큰도 같은 컴포넌트로 표시할 수 있게 확장.
- `DESIGN-SYSTEM.md` 인덱스에 두 항목 추가, 이번 과잉 삭제 경위를 한 줄로 남김.

**검증**: 앱 빌드(lint 오류 1건 발견·수정 — `PaletteSwatch.tsx`에서 읽어온 `value`를 실제로 렌더링 안 해서 `no-unused-vars`) 후 재빌드 성공, Storybook 빌드 성공(`index.json`에 `Foundations/Palette`·`Foundations/Semantic` 등재 확인), `design-foundation.test.mjs` 9/9 + 지정 테스트 전부 통과.

### 3.18 — Phase 7: radio-button 컴포넌트화 (2026-08-22)

Phase 4(컴포넌트 stories) 착수 직전에, radio-button이 여러 곳에 중복돼 있는 채로 문서화하면 "어느 구현이 정답인지" 판정이 안 서서 먼저 처리했다.

**§5-1 조사 결과 재검증**: 계획서엔 "3개 파일(`ConfirmModal`, `PollListClient`, `TypeAPollClient`)에 중복"이라고 적혀 있었는데, 실제로 다시 찾아보니 **부정확했다**. `PollListClient.tsx`의 `rounded-full border-2` 매치는 로딩 스피너(`animate-spin`)였다 — 라디오가 아니었다. 실제 라디오 인디케이터(링+안쪽 점) 패턴은 `ConfirmModal.tsx`·`TypeAPollClient.tsx` **2곳**뿐이었다. (참고로 `UserPollCreateForm.tsx`의 선수 다중 선택 UI도 원형+체크 모양이라 얼핏 비슷해 보이지만, `selectedIds.includes()`로 여러 개를 고르는 **체크박스**라 라디오와 성격이 달라 이번 통합 대상에서 뺐다.)

**설계**: `ui/radio.tsx` 신설.
- `RadioIndicator({selected})` — 링+점 시각 요소만. `ConfirmModal`은 상호작용이 없는 "내 선택" 요약이라(클릭 핸들러 자체가 없음) 이것만 `selected` 고정값으로 쓴다.
- `RadioOption` — 행 전체가 클릭 대상인 버튼. `role="radio"` `aria-checked` 추가(기존엔 없었다 — 사소한 접근성 개선을 겸함). `TypeAPollClient`가 이걸 쓴다.
- 기존 시각값 그대로 보존: 미선택 링 색(`border-muted-foreground/40`), `active:scale-[0.98]` 등 건드리지 않음 — 통합이 목적이지 재디자인이 아니다.

**이전**: `ConfirmModal.tsx`(라디오 인디케이터 6줄 → `<RadioIndicator selected />` 1줄), `TypeAPollClient.tsx`(버튼+인디케이터 20여 줄 → `<RadioOption>` 래핑).

**검증**: 앱 빌드 성공, `design-foundation.test.mjs` 9/9, `players-page-client.test.mjs` 12/12, 지정 테스트 스크립트 전부 통과.

### 3.19 — Phase 3 완료 claim 재검증 + 발견된 공백 3건 수정 (2026-08-22)

사용자 요청으로 §6 Phase 3 완료 claim을 코드·빌드·테스트와 대조 검증했다. 대부분(duration 4토큰, framer-motion 제거, 회귀 가드 2개의 글롭 스캔 방식, 90/90 테스트, Storybook 사이드바 등재)은 문서대로였지만 3건의 공백을 찾았다.

**공백 1 — Typography·Radius·Elevation 3개 Foundations 문서에 구체값이 없었다**: `TokenList.tsx`의 주석은 "실제 CSS 변수를 참조해 렌더한다"고 적혀 있었지만, 실제로 그렇게 동작하는 건 `ColorSwatch`/`TextSwatch`(색상 계열)뿐이었다. `Box`/`TypeSample`은 className만 붙인 빈 껍데기라 radius px, box-shadow 값, font-size/line-height/letter-spacing이 화면에 전혀 안 나왔다 — 참고 모델(Seed/Montage)이 항상 hex/px/토큰명을 같이 보여주는 것과 격차가 있었다.

- **수정**: `Box`에 `readProperty`(`borderRadius`|`boxShadow`) prop을 추가해 `ColorSwatch`와 같은 방식(computed style을 읽어 캡션으로 표시)으로 확장. `TypeSample`도 동일하게 font-size·line-height·letter-spacing을 읽어 표시하도록 확장. `Radius.mdx`/`Elevation.mdx`의 `Box` 호출에 `readProperty` 추가. `State.mdx`의 기존 `Box` 호출(opacity 예시)은 값이 이미 클래스 이름에 있어 그대로 둠(`readProperty` 미지정 시 캡션 자체가 안 나오게 설계해 회귀 없음).
- **검증**: `npm run build-storybook` 성공, 빌드된 청크(`TokenList-*.js`, `Radius-*.js`, `Elevation-*.js`)에서 `getComputedStyle`·`borderRadius`·`boxShadow` 참조 확인.

**공백 2 — JS `setTimeout` 숫자 duration 3건**: duration 회귀 가드는 Tailwind 클래스(`duration-\d+`)만 검사해서, `PlayersPageClient.tsx`의 Pick One 카드 애니메이션에 남아있던 JS 타이머 숫자(1000, 120, 700)는 검사 대상 밖이었다. 이 중 `700`은 `duration-slow`와 값을 맞춰야 하는 타이머였고, `120`은 duration 매핑 표(§6 하단)에 아예 없는 값이었다.

- **수정**: 값은 그대로 두고(동작 변경 없음) `PICK_ONE_CONFIRM_HOLD_MS`(1000)·`PICK_ONE_EXIT_STAGGER_MS`(120)·`PICK_ONE_EXIT_FADE_MS`(700) 3개의 이름 있는 상수로 추출, 각각 "토큰과 무관한 UX 대기값" / "4개 토큰에 안 맞는 stagger — opacity-[0.34]와 같은 성격의 예외" / "`duration-slow`와 반드시 같이 바꿔야 함"이라는 근거를 주석으로 남겼다. `Motion.mdx`에 "예외 — CSS 클래스가 아닌 JS 타이머" 절 신설.
- **회귀**: `players-page-client.test.mjs`가 숫자 리터럴(`1000`, `120`)을 정규식으로 검사하고 있어 상수명으로 바뀌자 깨짐 — §3.8/§3.9와 같은 패턴(리터럴 이름 변경 시 테스트도 같이 갱신). 상수 정의부(`= 1000` 등)와 사용부(`PICK_ONE_CONFIRM_HOLD_MS` 등) 양쪽을 검사하도록 테스트를 갱신.
- **JS 타이머까지 기계적으로 막는 검사**는 추가하지 않았다 — R4(하드코딩 파일목록 → 글롭 스캔)와 같은 구조적 확장이라 지금 범위를 벗어난다고 판단, Motion.mdx에 사실만 기록.

**공백 3 — §6 opacity 요약 문구가 예외를 언급하지 않음**: opacity는 실제로 "4종 + 예외 1건"(`opacity-[0.34]`, Pick One 카드 전용)인데 §6 진행 상황 표는 "6종→4종"만 적어 예외가 없는 것처럼 보였다. 예외 자체는 `State.mdx`와 테스트 주석에 이미 정확히 기록돼 있어 은폐는 아니었지만, 요약 문구가 부정확했다. (별도 수정 없이 이 절에 사실을 남김 — §6 표 자체는 지면상 요약이라 예외까지 표기하면 다른 행과 형식이 어긋나, 상세는 여기와 State.mdx를 참고하도록 함)

**최종 검증**: `npm run lint`(신규 에러 0, 기존 `<img>` 경고만), `npm run build`(18/18 성공), `npm run build-storybook`(성공), `node --test`(90개 중 88 통과 — 나머지 2건은 `result-view-figma-contract.test.mjs`).

**정정(§3.20에서 발견)**: 위 2건 실패를 "이번 작업과 무관한 기존 실패"로 판단했던 건 **틀렸다.** §3.20에서 실제로 원인을 추적해보니, `ResultView.tsx`의 퍼센트 막대·썸네일 마크업을 `ui/result-progress.tsx`(`ResultProgress`)로 추출하면서 이 계약 테스트가 검사하던 리터럴(`width: `\${item.percent}%``, `size-[40px]` 등)이 다른 파일로 옮겨간 게 원인이었다 — **이번 세션의 작업으로 생긴 회귀가 맞았다.** "git stash로 대조해 이전부터의 실패임을 확인했다"는 근거가 왜 틀렸는지는 불명(다른 세션에서 검증한 시점과 실제 반영 시점이 어긋났을 가능성) — 원인 규명보다 **어차피 재검증해야 하는 결론**이라는 게 이번 교훈이다. §3.20에서 테스트를 새 파일 구조에 맞게 갱신해 8/8 통과로 고쳤다.

### 3.20 — Phase 4: 생존 컴포넌트 14개 stories + MDX (2026-08-22)

§5-1의 14개 패턴 전부 작성했다. 형식은 `.stories.tsx`(CSF3, `Meta`/`StoryObj`) + `.mdx`(`<Meta of={...}/>`로 스토리에 연결, `<Canvas>`/`<Controls>`로 실제 렌더 + 조작 가능한 컨트롤 삽입) — Foundations MDX와 달리 컴포넌트 문서는 값을 문자열로 안 옮기는 원칙에 더해 **실제 컴포넌트를 진짜로 마운트**해서 보여준다.

**작성한 14개**: Button(actions) · Badge(contents) · Avatar(contents) · PollCard(contents) · PollCarouselCard(contents) · ResultProgress(contents) · ListGroup(contents) · ActionSheet(feedback) · AppHeader(navigations) · BottomNav(navigations) · Separator(presentation) · Radio(selection-and-input) · TextInput(selection-and-input) · RatingMatrix(selection-and-input) · FormSection(selection-and-input).

**진행 중 발견한 것 3건 — 전부 기존 기록(계획서 또는 다른 세션이 §3.19에 남긴 결론)을 그대로 믿지 않고 재확인해서 나왔다**:

1. **radio-button 중복이 3개가 아니라 2개였다** (Phase 7, §3.18에 상세). `PollListClient.tsx`의 매치는 로딩 스피너였다.
2. **`ui/progress.tsx`(Radix 기반)가 실사용 0건이었다.** 결과 막대(`ResultView.tsx`)는 이 컴포넌트를 안 쓰고 직접 만든 `div`+`width%`로 따로 구현돼 있었다 — 같은 일을 하는 코드가 두 곳에 나뉜 상태. 사용자 결정으로 `ResultView`의 실제 마크업 그대로 `ui/result-progress.tsx`(`ResultProgress`)로 통합하고 옛 `ui/progress.tsx`는 삭제했다. Radix `Progress` primitive를 얹으면서 `role="progressbar"`·`aria-valuenow` 등 접근성 속성도 새로 얻었다(예전 직접 구현엔 없었다).
3. **`result-view-figma-contract.test.mjs`(§3.19가 "이번 작업과 무관한 기존 실패"로 결론 낸 테스트)가 실제로는 위 2번(`ResultProgress` 통합)이 원인인 회귀였다.** 이 파일의 존재 자체를 몰랐다가(§3.19가 문서에 남긴 기록으로 알게 됨), 직접 실행해서 2건 실패를 확인하고 원인을 추적한 결과였다. 리터럴(`width: `\${item.percent}%``, `size-[40px]`, `thumb ?`)이 `ResultView.tsx`에서 `result-progress.tsx`로 옮겨간 걸 테스트가 못 따라간 것 — `design-foundation.test.mjs`에서 이미 여러 번(§3.8/§3.9) 겪은 것과 같은 유형의 회귀다. 새 파일 구조에 맞게 assertion을 옮겨 8/8 통과로 고쳤다.

**verify-before-assert가 이번에도 필요했던 사례**: 세 발견 다 "이미 적혀 있는 결론"을 그대로 믿지 않고 실제 코드·테스트를 다시 돌려봐서 나왔다. 3번은 특히 **다른 세션이 남긴 결론조차 재검증 대상**이라는 걸 보여준다 — 내가 쓴 기록이든 남이 쓴 기록이든, "이미 확인됐다"는 문장 자체가 검증을 면제해주지 않는다.

**또 다른 발견 — 이 문서 자체가 동시에 두 곳에서 편집되고 있었다**: §3.18을 쓰려고 보니 이미 다른 세션이 쓴 §3.18(현재 §3.19로 재번호)이 있었다 — 번호가 겹친 걸 뒤늦게 발견했다. `## 0. 변경 이력`에 v0.6까지 정상적으로 버전이 매겨져 있었는데, 그 이후(§3.5~§3.20 전체)는 이번 세션 내내 변경 이력에 한 줄도 안 남기고 있었다는 것도 이번에 알았다 — 문서 상단 frontmatter(`상태: 진행 중 v0.6 ... Phase 4 대기`)도 Phase 4가 끝난 지금 시점과 안 맞다. 아래 §0에 누락분을 정리해 채워 넣었다.

**컴포넌트별로 기록해둔 실제 코드와의 불일치(문서화하되 지금 안 고친 것)**:
- `Badge`의 `secondary` variant가 이름과 달리 초록(positive) 색이다.
- `RatingMatrix`(`OverallRatingPollClient.tsx`)가 `text-on-solid` 대신 `text-white` 리터럴을 쓴다(값은 같음).
- `Radio`의 미선택 링 색(`border-muted-foreground/40`)이 아직 semantic stroke 토큰으로 안 옮겨져 있다.

**PollCard/PollCarouselCard는 컴포넌트 분리 없이 실제 컴포넌트를 mock 데이터로 그대로 렌더**했다 — 둘 다 도메인 타입(`PollListItem`/`PollDetail`)과 분석 이벤트·라우팅 훅이 얽혀 있어서, 오늘 범위에서 프레젠테이션 로직만 분리하는 건 하지 않았다. Storybook의 Next.js 라우터 mock(`parameters.nextjs.navigation`)으로 `usePathname`/`useRouter`를 지원했다.

**DESIGN-SYSTEM.md 인덱스 전면 갱신**: Components 표 7개 카테고리 전부 "미작성"→실제 경로로 채움. `Progress`→`ResultProgress` 이름 변경, `Radio`의 "3곳 중복" 기록을 "2곳, Phase 7에서 통합 완료"로 정정, `Sheet`/`ActionSheet`를 Presentation에서 Feedback으로 재분류(실제로 만들어보니 오버레이 성격상 Feedback이 더 맞다고 판단).

**검증**: 25개 페이지(Foundations 9 + 개요 1 + 컴포넌트 14 + 미분류 1) 전부 Storybook 인덱스 등재 확인, 앱 빌드 성공, `tsc --noEmit` storybook 관련 타입 오류 0건, `design-foundation.test.mjs` 9/9, `players-page-client.test.mjs` 12/12, 지정 테스트 스크립트 전부 통과.

**미착수로 남긴 것**: `Radio`의 `role="radiogroup"` 컨테이너, `Badge`의 `secondary`→`positive` 이름 정정, `RatingMatrix`의 `text-white`→`text-on-solid` 정리 — 전부 MDX에 "하지 말 것"/불일치로 기록만 해두고 코드는 안 건드렸다. Phase 6(11-design-system.md 은퇴)에서 참조 갱신할 때 같이 볼지 별도 판단 필요.

### 3.21 — Storybook dev 서버 무한 로딩 (2026-08-22)

사용자 보고: "storybook이 무한로딩되면서 안 보인다."

**원인**: `globals.css`의 `.input-field`가 `@apply ... focus:border-brand-solid`를 쓰고 있었는데, Storybook의 Vite dev 서버에서 `focus:border-brand-solid class does not exist` PostCSS 에러로 요청마다 죽고 있었다(로그에 86회 반복). **`npm run build-storybook`(프로덕션 빌드)과 Next.js `npm run build`는 매번 통과했는데 dev 서버만 실패했다** — Vite dev 서버는 요청 시점에 필요한 모듈만 지연 컴파일하는 반면, 프로덕션 빌드는 전체 콘텐츠를 미리 스캔해 커스텀 색 유틸리티(`brand-solid`)를 먼저 등록해두기 때문에, `@apply` 안에서 이 유틸리티를 쓰는 순간의 스캔 완료 여부가 둘 사이에서 갈렸다. §3.8/§3.9에서 이미 겪은 "dev와 build가 다르게 동작한다"는 패턴이 이번엔 Storybook 쪽에서 재현된 셈이다.

**수정**: `.input-field`의 `@apply`에서 `focus:border-brand-solid`를 빼고, `.input-field:focus { border-color: var(--sem-stroke-brand-solid); }`를 별도 규칙으로 뒀다 — `@apply` 자체를 안 쓰고 CSS 변수를 직접 참조해 이 타이밍 문제를 원천적으로 피했다. CSS 네스팅(`&:focus`)은 이 프로젝트 PostCSS 설정에 nesting 플러그인이 없어서 시도했다가 되돌리고 평범한 별도 선택자로 썼다.

**검증**: 기존에 떠 있던(2:07PM부터, 다른 시점에 이미 이 에러를 겪고 있었을 것으로 보이는) dev 서버 프로세스를 죽이고 재기동 — Vite가 `globals.css`를 컴파일한 실제 산출물에서 에러 0건, `.input-field:focus` 규칙 정상 생성 확인. `npm run build`·`npm run build-storybook`·전체 테스트(90/90) 재확인 — 전부 통과, 회귀 없음.

**사용자 조치 필요**: 브라우저에 열려있던 Storybook 탭은 예전(죽은) 서버 프로세스에 연결돼 있던 상태라 새로고침이 필요하다.

### 3.22 — Storybook 런타임 에러: App Router 미마운트 (2026-08-22)

§3.21로 무한 로딩은 풀렸는데, 사용자가 이어서 다른 에러를 보고했다: `AppHeader` 스토리에서 `Error: invariant expected app router to be mounted`(`useRouter` 호출 지점에서 발생).

**원인**: `@storybook/nextjs-vite`는 `next/navigation` 훅(`useRouter`·`usePathname`)을 쓰는 컴포넌트를 마운트하려면 스토리의 `parameters.nextjs`에 **`appDirectory: true`를 명시해야 한다**(타입 정의에 "If your story imports components that use next/navigation, you need to set this parameter to true"라고 문서화돼 있음). §3.20에서 `AppHeader`·`BottomNav`·`PollCard`·`PollCarouselCard` 4개 스토리에 `navigation: { pathname: ... }`만 넣고 이 플래그를 빠뜨렸다.

**왜 지금까지 못 잡았나**: 이 에러는 컴포넌트가 브라우저에서 실제로 렌더될 때만 던져지는 런타임 에러다. 지금까지 검증 수단이 `npm run build-storybook`(정적 번들 빌드, 컴포넌트를 실제로 마운트하지 않음)뿐이었어서 — 그리고 브라우저 확장이 연결 안 돼 있어 직접 렌더 확인도 못 했다 — 4개 스토리 다 빌드는 성공하는데 실제로 열면 깨지는 상태로 지나갔다. **정적 빌드 성공 ≠ 런타임 정상 동작**이라는 걸 이번에 또 확인한 셈이다(§3.9의 시각 회귀 확인 때도 비슷한 한계가 있었다 — 그때는 컴파일된 CSS 값 비교로 우회했지만, 이번은 React 렌더 자체의 문제라 그 방법도 안 통한다).

**수정**: 4개 스토리(`AppHeader`·`BottomNav`·`PollCard`·`PollCarouselCard`)의 `parameters.nextjs`에 `appDirectory: true` 추가. `next/navigation`을 쓰는 나머지 컴포넌트(`LoginModal`·`OverallRatingPollClient`·`PollListClient`·`TypeAPollClient`·`UserPollCreateForm`·`DesktopNavLinks`·`PageContainer`)는 스토리가 이들을 직접 마운트하지 않아서(`RatingMatrix`/`FormSection`은 마크업만 옮겨 썼지 실제 컴포넌트를 import하지 않았다) 이번 문제와 무관하다 — 전체 14개 스토리 중 next/navigation 관련 컴포넌트를 실제로 마운트하는 건 이 4개뿐임을 `grep`으로 재확인했다.

**한계 — 이번에도 런타임으로 최종 확인은 못 했다**: `npm run build-storybook` 재빌드 성공은 확인했지만, 브라우저 확장이 계속 연결 안 돼 있어 실제로 이 4개 페이지를 열어 에러가 진짜 사라졌는지는 확인하지 못했다. `appDirectory: true`가 정확히 이 에러 메시지에 대한 공식 해결책이라는 근거(타입 정의 주석)는 있지만, 사용자가 직접 열어 확인해야 완결된다.

### 3.23 — Typography 샘플 font-size가 전부 같게 나오는 라이브 버그 (2026-08-22)

> **번호 충돌 재발 기록**: 이 절을 쓸 때도 §3.19를 다시 썼다가, 다른 세션이 이미 §3.18(radio-button)·§3.19(Phase 3 재검증)·§3.20~§3.22를 채워둔 걸 늦게 발견했다(§3.20의 "이 문서 자체가 동시에 두 곳에서 편집되고 있었다" 기록 참고). §3.23으로 바로잡았다 — 동시 편집 문제가 한 번 정리된 뒤에도 또 재발한다는 뜻이라, 큰 편집 전에 파일을 다시 읽는 습관이 필요하다.

§3.19에서 Typography/Radius/Elevation에 구체값을 추가한 뒤, 사용자가 "샘플이 다 같은 크기로 보인다", "값 칸의 글자크기가 전부 16px로 나온다"고 지적했다. 처음엔 "Vite dev 서버 HMR 캐시일 것"이라고 확인 없이 넘겼는데(재발 — `no-over-extrapolation`/`verify-before-assert`에서 이미 지적된 병), 사용자가 **HMR이 있을 수 없는 새 정적 빌드(포트 6008)에서도 재현**시켜 그 추측이 틀렸음이 드러났다.

**근본 원인**: `storybook-static/assets/blocks-*.js`(addon-docs 번들)를 직접 뒤져서 찾았다. Storybook의 문서 페이지 컨테이너가 emotion으로 이런 스타일을 주입한다:

```js
[UZ('span')]: { fontFamily: theme.typography.fonts.base, fontSize: theme.typography.size.s3, margin: 0, ... }
```

CSS로 치면 `.sbdocs-content span { font-size: 16px; ... }` — **클래스+태그 선택자(우선순위 0,1,1)**다. 우리 `.text-display-1`은 클래스 하나(0,1,1보다 낮은 0,1,0)라서 이 리셋에 항상 진다. `line-height`·`letter-spacing`은 이 리셋이 건드리지 않는 속성이라 우리 값이 그대로 살아남았고, 그래서 "font-size만 16으로 고정, line-height는 토큰마다 다르게 정확히 나오는" 특이한 증상이 나온 것이었다 — letter-spacing(em)도 실제로는 "옳은 em값 × 잘못된 16px"로 계산되어 나온 것까지 전부 이 메커니즘으로 설명된다.

**검증(추측 아님)**: jsdom으로 이 정확한 리셋 규칙(`.sbdocs-content span{font-size:14px;...}`, `!important` 없음)을 재현하고 우리 클래스를 얹어봤다.
```
리셋 있음, 수정 전: text-display-1     → font-size: 14px (버그, 56px여야 함)
리셋 있음, 수정 후: !text-display-1    → font-size: 56px (정상)
```

**수정**: `TypeSample`/`TypeSampleValue`(둘 다 `<span>` 기반)의 클래스 전체에 Tailwind `!` 접두사(`!important`)를 강제하는 `important()` 헬퍼 추가. emotion 쪽 리셋엔 `!important`가 없는 걸 확인했으므로 이걸로 항상 이긴다.

**부수 문제 — Tailwind가 동적으로 조합한 `!text-*` 클래스를 인식 못 함**: `important()`가 런타임에 문자열을 이어붙여 만든 `!text-display-1` 같은 이름은 어떤 소스 파일에도 리터럴로 존재하지 않아서, Tailwind의 콘텐츠 스캐너가 못 찾아 해당 CSS를 생성하지 않았다(1차 시도 시 발견, 배포 전에 잡음). `tailwind.config.ts`에 `FONT_SIZE_SCALE` 상수를 분리해 `fontSize`와 `safelist`(`!text-{key}` 전체)가 같은 객체를 참조하게 해서, 타이포 스케일이 바뀌어도 safelist가 자동으로 따라가게 했다.

**영향 범위**: `<span>`으로 텍스트를 렌더하는 Foundations 컴포넌트만 영향받는다 — `TypeSample`/`TypeSampleValue`(Typography.mdx, 수정함). `Box`/`BoxValue`(Radius/Elevation)는 border-radius·box-shadow를 다뤄서 이 리셋과 무관해 영향 없음. `TextSwatch`(Color.mdx/Semantic.mdx)도 `<span>`으로 텍스트를 렌더하지만 측정 대상이 `color`(이 리셋이 안 건드리는 속성)라 **데이터는 정확했고 시각적으로만 약간 작게 보였을 것** — 데이터 무결성 문제는 없었지만 시각적 일관성을 위해 후속으로 손볼 수 있음(범위 밖으로 미룸, 필요 시 재확인).

**검증**: 앱 빌드·lint·Storybook 빌드 성공, `design-foundation.test.mjs`(tailwind.config.ts 리터럴 검사)를 포함해 `node --test` 90/90 통과. 컴파일된 CSS에서 `.\!text-display-1{font-size:56px!important;...}` 등 실제 생성 확인.

**교훈**: 이번에도 "아마 캐시겠지"라고 확인 없이 답했다가 사용자가 추가 재현 사실(6008에서도 동일)을 제공해서야 진짜로 팠다. `no-over-extrapolation`/`verify-before-assert` 메모리가 지적하는 패턴이 이 세션에서도 반복됐다 — 반박 가능한 주장(HMR 캐시)을 실제로 반박해볼 수단(정적 빌드 재현)이 이미 있었는데도 먼저 시도하지 않고 사용자에게 확인을 미뤘다.

### Phase 순서의 근거

Phase 1을 맨 앞에 둔 이유는 **레퍼런스 치환 규칙이 Storybook 콘텐츠에 의존하지 않고, 사용자분의 다음 화면 작업에서 바로 필요하기 때문**이다. Phase 5(판정 계층)는 인덱스와 MDX가 있어야 동작하므로 Phase 2~4 뒤에 온다.

### Phase 1의 구체 내용 (사용자 요구사항 3번의 실체)

현재 `screen-design-workflow` 4단계는 "foundation 토큰(컬러, 간격, 라운드값, 타이포 스케일)을 재료로 2~3개의 후보 변형을 생성한다"까지만 있다. 추가할 것:

**(a) 결정 영역별 치환 규칙** — Seed의 "결정 영역별 1순위 레퍼런스" 표(리서치 §2.7.4)를 우리 상황에 맞게:

| 결정 영역 | 레퍼런스에서 | 판단 |
|---|---|---|
| 색상, radius, shadow, 타이포, 간격 | 참고만 | **기존 토큰으로 강제 치환** |
| 슬롯 구성·순서(anatomy) | 참고 | 가장 가까운 기존 패턴의 anatomy를 따름 |
| 레이아웃 비율, 정보 위계 | **채택 가능** | 토큰과 무관 |
| 인터랙션 아이디어 | **채택 가능** | 단 motion foundation의 duration·easing으로 치환 |

**(b) 차용 vs 거부 결정 트리** — Seed의 트리(리서치 §2.7.4)를 그대로 차용:
```text
레퍼런스에서 패턴 발견
  ├─ 기존 패턴과 충돌? ──Yes──> 거부
  └─ No → 같은 문제를 우리가 다른 방식으로 이미 푸는가?
            ├─ Yes → 거부 (같은 문제에 두 패턴 공존 금지)
            └─ No → 차용 가능. 단 naming을 기존과 정렬
```

**(c) 토큰 탈출구 3안** — 기존 토큰으로 표현 불가할 때 임의 생성하지 않고 아래를 제시해 선택받는다:

| 접근법 | 언제 | 트레이드오프 |
|---|---|---|
| 가장 가까운 기존 토큰으로 치환 | 차이가 미미할 때 | 일관성 최상. 레퍼런스 의도 일부 손실 |
| 새 토큰을 foundation에 추가 | 이 값이 앞으로 반복될 때 | 의도 보존. 토큰 수 증가, 승인 필요 |
| 컴포넌트 내부 예외로 두고 기록 | 이 화면 한정이 확실할 때 | 가장 빠름. 예외가 쌓이면 일관성 붕괴 |

**(d) Red Flags** — Seed의 표(리서치 §2.7.4)를 참고해 우리 상황에 맞게 재작성. 예: "이 이미지처럼 해줘"는 색·radius까지 그대로 베끼라는 뜻일 수 있으니 (a)의 치환 규칙을 먼저 확인한다.

### 3.24 — §3.23 수정안의 부작용 2건: 숨김 span 노출 + 라벨 없는 값 나열 (2026-08-22)

사용자가 §3.23 수정 결과를 직접 확인하다가 두 가지를 더 지적했다.

**문제 1 — 측정용 숨김 span이 화면에 그대로 노출됨**: `TypeSampleValue`의 숨김 span 클래스 전체(`absolute h-0 w-0 overflow-hidden opacity-0 ${className}`)에 `important()`를 걸어서 `!absolute`·`!h-0`·`!w-0`·`!overflow-hidden`·`!opacity-0`를 만들었는데, 이 이름들은 `tailwind.config.ts`의 `safelist`에 없어서(§3.23의 safelist는 `!text-{key}`만 다룸) Tailwind가 해당 CSS를 아예 생성하지 않았다. 결과: "숨겨야 하는" 클래스 5개가 전부 무효화되고 `!text-display-1`(생성됨)만 살아남아, **실제 크기의 "가" 글자가 값 칸에 그대로 노출**됐다.

- **수정**: `important()`를 폰트 크기 클래스(`className`)에만 적용하도록 범위를 좁혔다. `absolute`/`h-0`/`w-0`/`overflow-hidden`/`opacity-0`는 원래도 `.sbdocs-content span` 리셋이 안 건드리는 속성이라 `!`가 필요 없었다 — 처음부터 전체 문자열에 거는 게 과잉이었다.
- **검증(추측 아님)**: jsdom으로 `.sbdocs-content` 안에 `class="absolute h-0 w-0 overflow-hidden opacity-0 !text-display-1"` 요소를 만들어 확인 — `font-size: 56px`(정상) · `position: absolute` · `height: 0px` · `overflow: hidden` · `opacity: 0` 전부 의도대로 나옴.

**문제 2 — "값" 한 칸에 크기·행간·자간을 라벨 없이 나열**: 사용자 요청으로 "값" 열을 없애고 **크기 / 행간 / 자간 3개 열**로 분리했다. `TokenList`가 `valueColumns`(헤더 배열) prop을 받고, `item.value`가 배열이면 각 원소를 해당 순서의 칸에 나눠 넣도록 확장했다(단일 값을 쓰는 Radius/Elevation/State는 `valueColumns` 생략 시 기존과 동일하게 "값" 한 칸 — 회귀 없음). `TypeSampleValue`(문자열 조합)는 폐기하고, 속성 하나만 읽어 보여주는 `TypeMetric({ className, metric })`으로 교체 — 세 칸에 각각 독립된 인스턴스를 넣는다. `Typography.mdx`에 헬퍼 `metrics(cls)`를 추가해 세 `<TypeMetric>` 배열을 한 번에 만들도록 반복을 줄였다.

**검증**: 앱 빌드·lint·`node --test` 90/90·Storybook 빌드 전부 통과. 컴파일된 CSS에서 `.absolute{position:absolute}`(non-important, 정상)·`.\!text-display-1{...!important}`(정상) 둘 다 확인.

**교훈**: `!important`를 "안전빵으로 전체 클래스 문자열에" 건 게 원인이었다 — 정말 이겨야 하는 속성(font-size)에만 정밀하게 걸어야 했다. 넓게 적용하면 (a) 원래 필요 없던 클래스까지 이름이 바뀌어 safelist 누락으로 조용히 깨지고 (b) 그 사실이 시각적으로만 드러나(테스트로는 안 잡힘) 사용자가 화면을 직접 봐야 발견된다는 두 위험이 같이 온다.

### 3.25 — Typography에 "예시" 절 추가: 18개 토큰 실사용 데스크탑·모바일 목업 (2026-08-22)

사용자가 원티드 타입 문서(예시 화면 캡처)를 참고 자료로 제시 — 역할별로 "실제 어디에 쓰이는지" 데스크탑/모바일 목업을 나란히 보여주는 방식. 3가지 선택 확인 후 진행: (1) 18개 토큰 전부(미사용 토큰도 새로 구성), (2) 실제 컴포넌트 렌더, (3) 뷰포트 토글 대신 고정폭 박스 두 개를 나란히.

- **story 인덱서가 최상위 JSX 주석(`{/* ... */}`)을 못 처리해 빌드가 깨짐**: `import`/`export` 사이에 `{/* 설명 */}` 형태로 주석을 넣었더니 `Unable to index ...: Unexpected BlockStatement in code: only import/exports are supported`로 실패. MDX의 story 인덱서는 파일을 완전히 실행하지 않고 최상위 code block을 제한된 문법(import/export만)으로만 정적 파싱하는데, 중간에 낀 JSX 표현식 주석이 이 파서를 깨뜨린 것. 두 군데 다 지워서 해결 — 이후 MDX 최상위 code block에는 JS 주석(`//`, `/* */`)만 쓰고 JSX 스타일 주석은 안 쓴다.

**검증**: `npm run lint`(신규 에러 0), `node --test` 90/90, `npm run build`(성공), `npm run build-storybook`(성공, 인덱싱 에러 해소 확인).

### 3.26 — §3.25가 예상한 대로 실제 런타임 크래시 발생: MDX raw JSX는 데코레이터를 안 탄다 (2026-08-22)

§3.25에서 "런타임 최종 확인은 못 했다"고 밝혀둔 그 리스크가 사용자가 직접 열자마자 실제로 터졌다 — `TypeBPollClient` 마운트 지점에서 `Error: invariant expected app router to be mounted`. MDX `<Meta parameters={{ nextjs: {...} }} />`로 미리 방어했다고 적었는데, 그게 안 먹은 이유를 이번에 처음 제대로 규명했다.

**근본 원인**: `@storybook/nextjs-vite`의 `RouterDecorator`(next/navigation 컨텍스트를 주입하는 데코레이터)는 패키지 소스(`node_modules/@storybook/nextjs-vite/dist/_browser-chunks/chunk-342N7CWU.js`)를 직접 읽어 확인한 결과, **"story" 렌더링 파이프라인에만 붙는다.** MDX 프로즈에 `<TypeBPollClient poll={...} />`처럼 raw JSX를 직접 박아 넣으면 그 파이프라인을 완전히 건너뛰어서, `<Meta>`에 아무리 `parameters`를 줘도 데코레이터 자체가 실행되지 않는다. §3.22에서 이미 "story 레벨에 `appDirectory: true`가 필요하다"까지는 알았지만, **"MDX에 직접 마운트한 컴포넌트는 story가 아니라서 그 파라미터가 원천적으로 안 먹는다"**는 사실은 이번에 처음 확인했다.

**타입 확인**: `next/navigation`을 실제로 쓰는 컴포넌트는 마운트한 것 중 `TypeBPollClient`·`AppHeader` 2개뿐이었다(`grep -n "useRouter\|usePathname" 대상 8개 파일` — `OnboardingForm`·`MatchWeekList`·`MyFeedbackForm`·`Button`·`Badge`·`ResultProgress`는 0건, 안전했다).

**수정**: 이 2개만 이미 `appDirectory: true`가 설정된 실제 `.stories.tsx`(`PollCarouselCard.stories.tsx`, `AppHeader.stories.tsx`)를 `<Canvas of={...} withToolbar={false} story={{ inline: true }} />`로 참조하도록 바꿨다 — Storybook 공식 문서가 안내하는 "MDX에서 기존 스토리를 재사용하는" 정식 경로라 데코레이터가 정상적으로 붙는다. `EXAMPLE_POLL`(직접 만든 mock)은 더 이상 필요 없어져서 제거 — `PollCarouselCard.stories.tsx`가 이미 가진 mock을 그대로 재사용하는 쪽이 중복도 없고 더 안전하다.

**검증**: `npm run lint`(신규 에러 0), `node --test` 90/90, `npm run build`(성공), `npm run build-storybook`(성공, `index.json`에서 `Foundations/Typography`·`Contents/PollCarouselCard`·`Navigations/AppHeader` 3개 다 정상 인덱싱 확인).

**여전히 남는 한계**: 이번 수정이 "왜 터졌는지"는 소스 코드로 확정했고 "공식 패턴으로 바꿨다"는 사실도 확인했지만, **브라우저로 직접 열어 에러가 실제로 사라졌는지는 이번에도 확인 못 했다** — 브라우저 확장이 이 세션 내내 한 번도 연결되지 않았다. 사용자가 다시 확인해줘야 한다.

### 3.27 — Title 2 크래시: `OnboardingForm`이 서버 액션을 정적 import (2026-08-22)

사용자가 서버 재기동 후 다시 열자 새 에러: `Expected component 'OnboardingForm' to be defined`. 두 가지가 겹쳐 있었다.

**원인 1(단순 실수)**: §3.26에서 `AppHeader`/`TypeBPollClient` import를 `Canvas` 참조로 바꾸는 김에 import 블록을 다시 쓰면서 `OnboardingForm` import 자체를 빠뜨렸다 — MDX가 "정의 안 된 컴포넌트를 참조한다"고 정확히 그 이유를 에러로 알려준 것이었다.

**원인 2(더 근본적, import를 되살렸어도 또 깨졌을 것)**: `OnboardingForm.tsx`는 최상위에서 `saveNickname`(`src/lib/actions/onboarding.ts`, `'use server'`)을 정적으로 import한다. 그 파일은 `next/headers`의 `cookies()`·`next/navigation`의 `redirect()`·실제 Supabase 서버 클라이언트를 쓴다 — 브라우저에서 정적으로 로드하면 모듈 평가 자체가 실패한다. 대조로 `MyFeedbackForm.tsx`은 제출 핸들러 안에서 `await import('@/lib/actions/feedback')`로 **지연 로드**해서 마운트 시점엔 그 모듈이 안 실행돼 안전했다 — 같은 "서버 액션을 쓰는 폼"인데 import 시점(정적 vs 동적) 하나로 결과가 갈렸다.

**수정**: `OnboardingForm` 마운트를 제거하고, §3.25에서 Portal 제약에 썼던 것과 같은 방식(실제 클래스·구조는 그대로, `import` 없이 정적 재현)으로 바꿨다. 나머지 직접 마운트 4개(`MatchWeekList`/`Button`/`Badge`/`ResultProgress`)는 서버 액션·next/headers·next/navigation을 전혀 안 써서(import 문 전수 확인) 이 문제와 무관함을 재확인했다.

**검증**: `npm run lint`(신규 에러 0), `node --test` 90/90, `npm run build`(성공), `npm run build-storybook`(성공). 컴파일된 청크에서 `saveNickname`/`actions/onboarding`이 더 이상 실제 import가 아니라 `note` 텍스트(문자열)로만 남아있는 것 확인 — 모듈 자체가 안 딸려 들어옴.

**정리 — 이번 "예시" 절(§3.25~§3.27)에서 실제 컴포넌트 마운트가 최종적으로 실패한 원인 3가지**: (1) MDX raw JSX는 Storybook 데코레이터를 안 탐(§3.26, next/navigation 2건) (2) Radix Dialog/Sheet의 Portal이 고정폭 박스를 벗어남(§3.25, 4건) (3) 서버 액션을 최상위에서 정적 import하는 컴포넌트는 브라우저에서 모듈 평가 자체가 실패(§3.27, 1건). 세 경우 다 "실제 컴포넌트를 그대로 마운트한다"는 원칙에서 예외를 만들었고, 그때마다 이유를 MDX `note`에 남겼다.

### 3.28 — "예시" 절 전면 삭제 + Display·Title·Heading·Headline 의미 재정의 (2026-08-22)

사용자가 §3.25~§3.27 내내 겪은 "예시" 절(실제 컴포넌트 마운트) 자체를 통째로 삭제해도 된다고 판단, 대신 타입 스케일의 `1`/`2`/`3` 접미사가 애초에 뭘 뜻하는지를 정정했다. 지금까지는 "역할별 위계"(더 강한 강조 vs 약한 강조)로 다뤘는데, 실제로는 **같은 역할을 어떤 화면 크기에서 쓰느냐**의 구분이었다.

**확정된 대응 관계** (사용자가 두 번에 걸쳐 알려줌):
- `heading-1`(데스크탑) ↔ `heading-2`(모바일) — 둘 다 "섹션 제목"
- `headline-1`(데스크탑) ↔ `headline-2`(모바일) — 둘 다 "카드·모달 제목"
- Display·Title은 **연쇄적으로** 대응(한 단계 큰 화면의 토큰이 한 단계 작은 화면에서는 다음 토큰으로 내려간다): `display-1`(데스크탑)↔`title-1`(모바일), `title-1`(데스크탑)↔`title-2`(모바일), `title-2`(데스크탑)↔`title-3`(모바일). 그래서 `title-1`·`title-2`는 **이중 역할**이다 — 모바일에서는 한 단계 위 역할, 데스크탑에서는 한 단계 아래 역할.

**처리**: `UsageExample.tsx`·§3.25~§3.27에서 쌓은 "예시" 절 전체 삭제(파일 삭제 + import 정리). `title-3`가 그대로 갖고 있던 "앱 헤더 서비스명"(§3.19 조사에서 확인된 실사용, 실제로는 화면 크기 구분 없이 공통으로 쓰는 용도)은 지우지 않고 캐스케이드 설명과 나란히 남겼다 — 확대해석해서 하나로 합치지 않음.

**검증**: `npm run lint`(신규 에러 0), `node --test` 90/90, `npm run build`(성공), `npm run build-storybook`(성공).

### 3.33 — Foundations 문서의 마크다운 표가 텍스트로만 보이는 문제: `remark-gfm` 부재 (2026-08-22)

사용자가 Foundations 문서에서 `| 토큰 | 값 | 언제 쓰는가 |` 같은 표가 실제 표가 아니라 그냥 텍스트로 보인다고 지적. `TokenList` 같은 커스텀 컴포넌트가 아니라 **마크다운 문법으로 직접 쓴 표**(Motion/Color/Layout/State/Radius/Elevation/Typography 7개 파일, `grep -c "^|"`로 확인)에서 발생.

**원인**: 이 프로젝트에 `remark-gfm`이 설치돼 있지 않았다. 기본 MDX(CommonMark)는 GFM 표 문법(`| a | b |` + `|---|---|`)을 지원하지 않아서, 파이프 문자가 그냥 리터럴 텍스트로 렌더된다 — HTML `<table>`로 파싱 자체가 안 됐다.

**수정**: `remark-gfm`을 devDependency로 설치하고, `.storybook/main.ts`의 `addons` 배열에서 `'@storybook/addon-docs'` 문자열 항목을 `{ name, options: { mdxPluginOptions: { mdxCompileOptions: { remarkPlugins: [remarkGfm] } } } }` 객체로 바꿔 remark 플러그인을 얹었다. (참고: `@storybook/addon-docs`의 webpack 프리셋 소스에서 이 옵션 경로를 먼저 확인한 뒤 적용 — Vite 빌더에도 같은 옵션 키가 통하는지는 실제 빌드 산출물을 까서 검증)

**검증(추측 아님)**: 컴파일된 청크(`Motion-*.js` 등)를 직접 열어 `t.table`/`t.thead`/`t.tr`/`t.th`/`t.td` JSX 호출이 실제로 생성됐는지 확인 — 7개 파일 전부(`Color`/`State`/`Layout`/`Radius`/`Elevation`/`Typography`/`Motion`) `t.table` 존재 확인. `npm run lint`(신규 에러 0), `node --test` 90/90, `npm run build`(앱, 성공), `npm run build-storybook`(성공).

### 3.35 — "Storybook 문서 vs 실제 서비스 값" 드리프트 전수 점검 (2026-08-22)

§3.33(remark-gfm)이 "문서가 실제와 다르게 보인다"는 문제의 한 사례였을 뿐이라는 사용자 지적으로, **Foundations 문서에 정적으로 적힌 값·이름이 실제 코드(tailwind.config.ts/globals.css/컴포넌트)와 어긋나는 곳**을 전수 대조했다. 동적으로 값을 읽어오는 부분(`ColorSwatch`/`PaletteSwatch`/`TypeMetric`/`BoxValue`)은 구조적으로 드리프트가 불가능해서 제외하고, **정적 텍스트로 적힌 값·이름**만 대상으로 했다.

**대조한 것(문제 없음 확인)**: Layout.mdx의 컨테이너 폭(480/1140/680px)↔`--shell-w`/`--content-w`/`--detail-w`, Elevation.mdx의 배경 hex(#fafafa/#ffffff)↔`--c-bg`/`--c-surface`, Motion.mdx의 keyframe 타이밍(0.2s/1.15s)↔`globals.css`의 `@keyframes`, Motion.mdx의 JS 타이머 예외 표(1000/120/700)↔`PlayersPageClient.tsx`의 실제 상수, State.mdx의 pressed AA 미달 3케이스(3.94/4.48/4.06:1)↔`button.tsx`/`MatchWeekList.tsx`/`PollCard.tsx`의 현재 클래스, State.mdx의 `opacity-[0.34]` "유일한 예외" 주장↔실제 grep(여전히 1건).

**드리프트 발견·수정(3건)**:
1. **Color.mdx:74** — "`-weak`/`-dim`은 배경에 쓴다"에서 `-dim`은 §3.8/§3.10에서 전부 `-weak`로 이전되며 죽은 이름이 됐다(`globals.css`에 원시 `--c-*-dim` 변수만 남아있고 실제 Tailwind 클래스는 0건). `-dim` 삭제.
2. **Elevation.mdx:45** — "강조는 색(`primary`)이나 테두리로"의 `primary`는 §3.8에서 `brand`로 전체 이전된 옛 이름. `brand`로 교정.
3. **Color.mdx:23** — "새 brand 앵커(#0a54ff)는... 5.34:1로 AA 통과"에서 헥스값과 대비 수치가 서로 안 맞았다. 실제 `--p-blue-700`(brand-solid 실값)은 `#115aff`이고, `#115aff` vs 흰색을 직접 계산하면 정확히 5.34:1 — 즉 **비율은 최신값 기준으로 이미 맞았는데 헥스만 §3.6 색상각 조정 이전의 옛 값으로 남아있었다.** `#115aff`로 교정, "처음부터"라는 표현도 삭제(값이 한 번 바뀐 적이 있으므로).
4. **`DESIGN-SYSTEM.md`** — Typography 항목이 "19종"이라고 적혀 있었는데 실제 토큰을 세면 18종(Display 2 + Title 3 + Heading 2 + Headline 2 + Body 4 + Label 3 + Caption 2). "18종"으로 교정.

**검증 방법**: 헥스값은 손계산 대신 WCAG 상대휘도 공식을 코드로 실행해서 확인(이 문서 자체가 §3.15/3.16에서 "계산기 버그" 재발을 여러 번 겪은 적이 있어, 직접 계산하지 않고 항상 스크립트로 재계산). `npm run lint`(신규 에러 0), `node --test` 90/90, `npm run build-storybook`(성공).

**남긴 것**: Badge의 "이름과 실제 색이 하나 어긋남"(`secondary`가 초록/positive) 같은 **의도적으로 기록해둔 기존 불일치**는 손대지 않았다 — 이건 문서 오류가 아니라 코드 자체의 알려진 특이사항이라 문서가 정확히 반영하고 있는 것이다.

### 3.36 — Montage/Seed 대비 Foundations 충분성 검토, 갭 3건 신설 (2026-08-23)

사용자 질문: "실제 다른 기업들이 디자인시스템을 운영하는 거에 대비해서 우리가 만든 디자인시스템, 그중에서도 foundation 내용이 충분히 기입된 걸까?" — 이미 완료된 리서치(`디자인시스템-리서치-몽타주-시드디자인.md`)를 근거로 대조했다.

**대조 결과**: 핵심 시각 Foundations(색·타이포·레이아웃·radius·elevation)는 두 참고 기업 대비 부족하지 않았다 — Color는 Palette/Semantic/Color 3개로 나눠 더 세분화돼 있고, State·Motion은 Montage에도 없는 카테고리를 우리는 갖고 있다. 리서치 문서 §3-3의 "Foundations 개수: 우리 5"는 State/Motion 신설(v0.7) 이전 시점의 낡은 값이라 9로 갱신했다(아래).

**실제 갭 3건(확인된 것만, 확대해석 안 함)**:
1. **Icons** — Montage·Seed 둘 다 독립 Foundation으로 문서화. 우리는 `lucide-react` 22종을 이미 쓰는데 문서화가 0건. 실제 크기 사용을 grep으로 전수 확인한 결과 이미 3단계(14/16/24px)로 정돈돼 있었다 — 판단이 필요한 문제가 아니라 이미 있는 암묵 규칙을 적어두면 되는 문제였다.
2. **Gradient** — Seed에만 있는 항목이지만 우리도 실사용 4곳이 있다. 문서화하며 대조하다가 그중 한 곳(아바타 대체 배경)이 §3.8~3.10에서 이미 폐기된 `primary`/`primary-dark`(#41b6e6 계열)를 여전히 쓰고 있는 걸 발견 — 그라디언트라 임의값 검사(`design-foundation.test.mjs`)에 안 걸리고, 문서화된 적이 없어 아무도 못 잡았던 드리프트다.
3. **Design Token** — Seed에는 토큰 체계 자체("왜 지금 구조인가")를 설명하는 별도 페이지가 있다. 우리는 없어서 찾다가, `globals.css`/`tailwind.config.ts`에 실제로 **세 세대**(레거시 flat hex `--c-*` / shadcn HSL `--primary` 등 / 신규 Palette→Semantic `--p-*`→`--sem-*`)가 공존한다는 걸 확인했다. `primary`라는 이름이 레거시 두 세대에 동시에 존재해 `bg-primary`/`text-primary`가 유효한 클래스로 살아있는데, 이걸 브랜드색으로 오인해 쓰면 새 브랜드 파랑(`#115aff`)이 아니라 폐기된 옛 파랑이 나온다 — 실사용 0건은 확인했지만 이름만으로 고르면 걸리기 쉬운 구조적 함정이다.

**확대해석 안 한 것**: 다크모드(양쪽 다 있고 우리는 없음)는 Color.mdx가 "라이트 테마 전용"이라고 이미 스코프를 명시한 별도 이슈라 이번 갭에 안 넣었다. Writing/Voice-and-tone/Inclusive-design(Seed만 있음)은 톤 충돌이 관찰된 적이 없어 "만들어야 한다"는 근거가 약해 보류. International-design은 단일 로케일 서비스라 해당 없음.

**반영**:
- `foundations/Icons.mdx` 신설 — 크기 3단계(14/16/24px), 색 상속(currentColor) 규칙, 아이콘 단독 버튼 `aria-label` 규칙.

- `DESIGN-SYSTEM.md` Foundations 표에 3행 추가.
- **코드 수정**: `TypeBPollClient.tsx`의 `from-primary/30 to-primary-dark` → `from-brand-solid/30 to-brand-solid`(그라디언트 드리프트 수정). 아이콘 단독 버튼 `aria-label` 누락 6곳 보완 — `TypeBPollClient.tsx`(캐러셀 이전/다음 버튼), `MyPageClient.tsx`(닉네임 저장/취소 버튼), `CommentsSection.tsx`(댓글 수정 완료/취소 버튼). 점검했지만 이미 괜찮았던 것: `AppHeader.tsx`의 뒤로가기 버튼(옆에 "돌아가기" 텍스트 있음), `sheet.tsx`의 닫기 버튼(`sr-only` "Close" 텍스트 이미 있음) — 아이콘만 있는 것처럼 보였지만 실제로는 접근 가능한 이름이 이미 있었다.

### 3.37 — 브랜드 스팟라이트 글로우 유틸리티 신설, `shell-desktop-bg` 삭제 (2026-08-23)

사용자가 두 개의 참고 그라디언트 CSS(다중 radial 스팟라이트, `color-mix` 대각선 글로우)를 제시하고 "패턴을 찾아 적용 방법을 제안해달라"고 요청. 공통점은 **중립 베이스 위에 강조색이 앵커 지점(모서리/대각선)에서 진하게 시작해 멀어질수록 옅어지다 베이스로 수렴**하는 구조 — 옅어지는 방식만 다르다(하나는 alpha 감쇄, 하나는 `color-mix()`로 색 자체를 혼합). 우리 토큰(`--p-blue-700`/`--c-surface`/`--c-bg`)으로 적용한 옵션 A(대각선)/B(2-모서리 스팟라이트)/C(파라미터화)를 HTML 아티팩트로 시각 비교 제시 → 사용자가 B 선택.

**적용 대상 확인**: "어디에 적용할까" 물은 결과 — 데스크탑 셸 배경(`.shell-desktop-bg`)은 안 쓰니 삭제하고, B는 특정 화면 없이 재사용 유틸리티로만 준비해두라는 답.

**반영**:
- `globals.css`에 `.spotlight-glow-brand` 신설 — 2개 radial(`--p-blue-700`/`--p-blue-600`, 20% `color-mix`, 250px, 70% 소멸) + `var(--c-bg)` 베이스. 아직 어떤 컴포넌트에도 클래스를 붙이지 않았다 — 순수하게 준비된 유틸리티다.
- `.shell-desktop-bg`(하드코딩 hex `#1a9fd4`/`#123a63`/`#0c2340`, §3.36에서 "확인 필요"로 남겨뒀던 것) 삭제. `PageContainer.tsx`의 `sm:shell-desktop-bg` 참조와 JSDoc도 함께 제거 — 온보딩 화면 데스크탑 좌우 여백은 이제 `body`의 기본 `bg-background`가 그대로 드러난다(시각적 회귀 아님, 의도된 단순화).
- `Gradient.mdx` 갱신: 실사용 표에서 `shell-desktop-bg` 행 제거, `spotlight-glow-brand`를 "준비된 유틸리티" 절로 신설(코드 + `color-mix()` 브라우저 지원 범위 명시). `DESIGN-SYSTEM.md` Gradient 항목 설명도 "실사용 3곳 + 준비된 유틸리티 1개"로 갱신.

**검증**: `npm run lint`(신규 에러 0), `node --test`, `npm run build`, `npm run build-storybook`(신설 유틸리티는 컴포넌트에 아직 안 붙어 있어 별도 렌더 확인 대상 없음 — Gradient.mdx 스와치로 시각 확인).
