# 디자인시스템 컴포넌트·문서 정리 프로세스

## Context

디자인시스템을 "손이 닿을수록 나빠지지 않게" 정돈하고 싶다는 요구다. 사용자가 지목한 4가지:

1. 컴포넌트를 **2단계**(원자 ↔ 조합/일회성)로 정리 — 폴더 재구성까지
2. 문서에서 **이력·경위 서술** 걷어내기 (규칙만 남김)
3. foundation(color·typography) **준수 검토**
4. **모달/바텀시트 shell↔content 분리** — 껍데기는 하나로 통일, 내부 콘텐츠만 사용처별

**현재 상태 진단(탐색 결과):** 상당 부분 이미 되어 있다. 이 작업은 "밑바닥 재구축"이 아니라 **정리·감사·수렴**이다.
- `ui/`(원자 9개) vs feature 폴더(조합체/화면 조립체)로 사실상 이미 분리됨. 다만 분류축이 Montage 기능별(Actions/Contents/…)이라 사용자가 원하는 **"조합 단계(tier)" 축은 없다.**
- 모달 shell/content 분리는 이미 되어 있음: `ui/bottom-sheet.tsx`(shell) ← `LoginModal`/`ConfirmModal`(content). 예외는 `PlayerPickModal` 하나.
- 토큰 준수는 매우 양호. 컴포넌트 내 임의 색상/타이포 클래스 0건(유일 raw hex = `LoginModal`의 구글 로고 SVG, 정당한 예외). `components/design-foundation.test.mjs`가 촘촘한 회귀 방지 장치로 이미 깔려 있음.

**진행 방식:** 사용자 결정 = **감사 리포트 먼저**. 리포트에서 목표 구조·삭제 대상·통합 판단을 눈으로 확정받은 뒤(승인 게이트), 승인된 항목만 실행 웨이브로 반영한다. 폴더 재구성은 리스크가 크므로 가장 마지막에 둔다.

---

## 작업 원칙 — 판단에는 반드시 근거, 근거는 실재 문서 기반

이 작업 전체에 적용되는 최상위 원칙이다.

- **모든 판단에는 판단 근거가 반드시 필요하다.** "그럴듯해서", "보통 그렇게 하니까" 식의 추론으로 결정하지 않는다. 무엇을 삭제·이동·통합·예외 처리하든 그 결정을 뒷받침하는 근거를 먼저 확보한다.
- **판단 근거는 실제로 존재하는 문서(또는 코드)를 기반으로 해야 한다.** 근거는 확인 가능한 실물이어야 한다 — 실제 코드 파일·줄 번호, `design-foundation.test.mjs` 같은 테스트, `src/storybook/**/*.mdx`, `DESIGN-SYSTEM.md`, `CLAUDE.md`. 기억·추측·존재하지 않는 문서를 근거로 삼지 않는다.
- **근거를 못 찾으면 판단을 내리지 말고 남겨 온다.** 확인되지 않은 항목은 리포트에 "근거 미확인"으로 표기해 사용자 판단으로 넘긴다. 임의로 메꾸지 않는다.
- **근거는 기록한다.** 리포트·커밋·문서의 각 결정 옆에 근거(파일:줄, 문서명)를 병기해, 나중에 왜 그렇게 했는지 되짚을 수 있게 한다.
- 관련 프로젝트 규칙: `DESIGN-SYSTEM.md`의 "표에 항목이 없으면 '아직 문서화되지 않았다'고 판단한다. 기억이나 추측으로 규칙을 만들지 않는다"(16번 줄)와 정확히 같은 태도다.

## 산출물 1 — 감사 리포트 (승인 게이트)

한 장짜리 진단서. 위치는 사용자와 합의(scratchpad 또는 vault/10_gun). 아래 4개 섹션. **각 항목에 근거(파일:줄 / 문서)를 병기한다.**

### 1-A. 컴포넌트 tier 표 + 목표 폴더 구조 제안
현재 `components/**`의 모든 컴포넌트를 3열로 분류한 표:
- **Tier 1 (원자/primitive)** — 다른 로컬 컴포넌트를 import 안 하는 재사용 최소단위. 현재 `ui/` 9개: `button` `badge` `avatar` `card` `radio` `result-progress` `separator` `sheet` `bottom-sheet`(sheet만 감쌈).
- **Tier 2-a (재사용 조합체)** — 원자를 조합해 여러 화면이 재사용: `PollCard` `ConfirmModal` `LoginModal` `StickyActionBar` `CommentsSection` `MatchdayHero` `MatchWeekList` `RankingCard` `WeekRankCard` `PlayerPickModal` `LoginButton` `UserMenu` `AppHeader` `BottomNav` 등.
- **Tier 2-b (일회성/화면 조립체)** — 페이지 1곳만 조립하는 클라이언트: `TypeAPollClient` `TypeBPollClient` `OverallRatingPollClient` `HomeClient` `PredictionFlowClient` `MyPageClient` 등 (DESIGN-SYSTEM.md가 이미 "화면 단위 클라이언트"로 식별한 목록과 대조 — 근거: DESIGN-SYSTEM.md 139~155번 줄).

이 표에 **목표 폴더 구조 2안**을 붙여 사용자가 고르게 한다 (실제 이동은 Wave D에서):
- **안 A (tier 디렉토리):** `ui/primitives/` + `ui/patterns/` + `features/<도메인>/`. 기능 폴더(polls/predict/…)는 유지하되 도메인 무관 재사용 조합체만 `ui/patterns/`로 승격.
- **안 B (현 구조 유지 + 라벨링):** 파일은 안 옮기고, DESIGN-SYSTEM.md 각 행에 `tier` 열만 추가. 리스크 0, import 무변경.
- 각 안의 import 파급 범위·테스트 재작성량을 함께 적어 트레이드오프를 명시한다.

### 1-B. 문서 이력·군더더기 목록
`src/storybook/**/*.mdx` + `DESIGN-SYSTEM.md`를 훑어 "규칙 아님, 경위·이력" 문장을 파일별로 열거:
- 예: `DESIGN-SYSTEM.md` 39·41·43·49·51·53·85·129·149~155번 줄류의 "Phase N에서…", "2026-08-23에…", "한때 ~였다가~", "재확인 결과…".
- 각 항목을 **[삭제] / [각주·History 섹션으로 이동] / [규칙이라 유지]** 로 태깅. 삭제 대상은 "규칙 이해에 불필요한 과거 경위"로 한정 — `deleteUserPoll` 보안 경고(151번 줄)처럼 **판단 근거가 되는 서술은 유지**한다.

### 1-C. foundation 준수 위반 목록
`design-foundation.test.mjs`가 이미 통과시키는 범위 밖의 잔여만 보고:
- **확정 위반(테스트가 명시적으로 제외 중):** `app/admin/ratings/page.tsx`, `components/admin/AdminRatingsForm.tsx`, `components/layout/NavigationLoading.tsx` — 아직 `border-gray-4`/`text-gray-2`/`bg-primary` 등 구세대 토큰 사용. 근거: 테스트 383번 줄 주석이 "이 파일들 이관 끝나면 predict 검사를 리포 전체로 넓힌다"고 예고.
- **정당한 예외 재확인:** `LoginModal` 구글 로고 hex, `--c-black` 스크림, `SheetTrigger/Close/Footer` 미사용 보존.
- 결론: 준수 상태는 양호하며, 실제 할 일은 위 3개 파일 이관 + 그 후 predict 전용 검사를 리포 전체 스캔으로 승격.

### 1-D. 모달/바텀시트 — 단일 shell 원칙 전수 점검
**핵심 원칙(사용자 지정):** 모달·바텀시트의 **껍데기(shell)는 하나로 통일**하고, **내부 콘텐츠만 사용처별로 다르게** 둔다. shell = 위치/폭/반응형(모바일 하단시트 ↔ 데스크탑 중앙 모달)/오버레이/드래그 핸들/포커스 트랩·ESC 등 공통 골격. content = 각 모달의 본문(헤더 정렬·아이콘·목록·버튼)만.

- **현행 shell = `ui/bottom-sheet.tsx`**(← `ui/sheet.tsx` primitive). 이미 `side`로 모바일=하단/데스크탑=중앙 반응형 전환을 함(근거: 55~69번 줄). 이걸 **정식 단일 shell로 확정**한다.
- **전수 점검 — 모든 모달/시트/다이얼로그 표면**이 이 shell을 통과하는지, 아니면 우회하는지 표로:
  - `LoginModal` — `BottomSheet` shell + content. ✅ 이미 준수(레퍼런스 사례).
  - `ConfirmModal` — `BottomSheet` shell + content. ✅ 준수.
  - `RequireAuthModal` — `LoginModal`을 띄우는 컨테이너. 준수(간접).
  - `PlayerPickModal` — ❌ **shell 우회.** `@radix-ui/react-dialog`를 직접 조립. 격리 명분("`ui/sheet`는 항상 하단 고정이라 반응형 불가", 근거: 41~43번 줄)이 shell의 현재 반응형 지원과 모순 → **낡았을 가능성 높음.**
  - `UserPollCreateForm` — `ui/sheet`를 **직접** import(shell 래퍼 우회). 이 시트가 모달/바텀시트 문법이면 통일 대상인지, 인라인 폼 섹션이면 제외인지 판정.
  - `UserMenu` 드롭다운 등 팝오버성 표면 — 모달/시트가 아니면 원칙 대상 밖임을 명시(범위 오염 방지).
- **각 우회 표면마다** shell로 이관 가능한지 검증 후 **[shell로 통합] / [본질적 차이로 예외 유지]** 판정. 예외는 반드시 근거를 `feedback/BottomSheet.mdx`에 명문화(예외를 "왜 예외인지"까지 문서화해야 원칙이 침식되지 않음).
- `PlayerPickModal` 통합 검증 포인트: `BottomSheet` shell로 옮겼을 때 (1) 선수 목록 스크롤·`max-h`, (2) 진입 애니메이션(slide-in-from-bottom-2), (3) 선택 UX가 동일 재현되는지.

## 산출물 2+ — 실행 웨이브 (리포트 승인 후)

승인된 항목만, 아래 순서로. **각 웨이브 종료 시 `npm test` + `npm run lint` 통과 확인 후 개별 커밋**(한 줄 메시지, main 직접).

### Wave A — 문서 이력 제거 (리스크 최저, 먼저)
- 1-B에서 [삭제]/[이동] 태깅된 서술을 각 MDX·DESIGN-SYSTEM.md에서 처리.
- 규칙 원문은 손대지 않는다. `DESIGN-SYSTEM.md`의 "이 파일을 쓰는 규칙"(5~18번 줄) 자체를 준수 — 인덱스에는 이름·한 줄·경로만.
- 주의: `design-foundation.test.mjs`의 `retired legacy color class names` 검사(315번 줄~)가 **mdx도 스캔**한다. 폐기 클래스명을 본문에서 지우되, 인용이 필요하면 예외 파일(`DesignToken.mdx`)에만 남긴다.

### Wave B — foundation 잔여 이관
- 1-C의 3개 파일(`admin/ratings`, `AdminRatingsForm`, `NavigationLoading`)을 구세대 → semantic 토큰으로 이관 (`bg-primary`→`bg-brand-solid`, `text-gray-2`→`text-neutral-muted`, `border-gray-4`→`border-neutral-weak` 등, 매핑 근거: test 321~352번 줄이 정답표).
- 이관 후 `design-foundation.test.mjs`의 `prediction screens…` 검사(376번 줄~)를 **predict 한정 → 리포 전체 글롭 스캔**으로 넓힌다(테스트가 예고한 작업). 이걸로 재유입 영구 차단.

### Wave C — 단일 shell 원칙 적용
- **원칙 명문화 먼저:** `feedback/BottomSheet.mdx`에 "모달·바텀시트의 shell은 `ui/bottom-sheet.tsx` 하나로 통일, 내부 콘텐츠만 호출부(children)"를 foundation 규칙으로 승격(근거: `bottom-sheet.tsx` 38~54번 줄 주석). 새 모달을 만들 때 shell을 새로 짜지 말고 이 shell을 재사용하라는 지침 포함.
- **우회 표면 이관:** 1-D에서 [shell로 통합] 판정된 표면을 `BottomSheet` shell 위로 재작성하고 content만 남김.
  - `PlayerPickModal`: `BottomSheet` shell + content(선수 행 목록)로 분리. 접근성(포커스 트랩·ESC)이 `ui/sheet` 경로에서도 유지되는지 확인.
  - `UserPollCreateForm`의 `ui/sheet` 직접 사용분: 판정 결과에 따라 shell 경유로 정리 or 예외 근거 기록.
- [예외 유지] 판정된 표면은 예외 사유를 `BottomSheet.mdx`에 남겨 원칙 침식 방지.

### Wave D — 폴더 재구성 (리스크 최고, 마지막)
- 리포트에서 **안 A가 승인된 경우에만** 실행. 안 B(라벨링만)면 Wave A에 흡수되어 이 웨이브 불필요.
- 파일 이동은 `git mv`로 히스토리 보존. import 경로는 `@/components/...` alias라 이동한 파일만 한 번에 치환.
- **테스트 영향 큼:** `*.test.mjs`들이 소스 경로를 하드코딩(예: `design-foundation.test.mjs`의 파일 목록, `PREDICT_FILES` 배열)하므로 경로 문자열을 함께 갱신. CLAUDE.md 경고대로 "테스트를 지우지 말고 옮겨간 자리로 단정문을 다시 쓴다".
- 이동 후 `DESIGN-SYSTEM.md`·`.stories.tsx`의 경로도 같은 커밋에서 갱신.

## 병렬 처리 전략

**리포트 = 병렬, 실행 웨이브 = 순차(웨이브 내부만 소규모 병렬).**

- **산출물 1 (감사 리포트): 병렬.** 1-A~1-D는 서로 의존 없는 읽기 전용 조사라 4개 subagent로 동시 fan-out 후 결과를 한 장으로 합친다. (규모가 커지면 Workflow로 pipeline화 가능하나, 4갈래 read-only fan-out은 Explore 에이전트 병렬 실행으로 충분.)
- **실행 웨이브 A→D: 순차.** 병렬화 금지 — 웨이브들이 같은 파일을 공유하기 때문:
  - `design-foundation.test.mjs` — Wave B가 검사 범위 확장, Wave D가 경로 목록(`PREDICT_FILES` 등) 갱신.
  - `DESIGN-SYSTEM.md` — Wave A가 이력 삭제, Wave D가 이동된 파일 경로 갱신.
  - Wave D(폴더 이동)는 A·B·C가 만진 파일의 경로를 다시 바꾸므로 반드시 최후미.
- **웨이브 내부는 병렬 가능:** Wave A의 개별 MDX 편집, Wave B의 3개 파일 이관은 파일 단위로 나눌 수 있음. 단 파일 수가 적어 실익은 크지 않으므로 기본은 단일 세션 순차 처리, 필요 시에만 분할.

## 검증

- 각 웨이브: `cd frontend && npm test`(94개 전부) + `npm run lint`. CLAUDE.md 경고 — 개별 test:* 스크립트는 13개 중 7개만 덮으므로 반드시 `npm test`로 전체를 돌린다.
- Wave B 후: 넓힌 글롭 스캔 검사가 신규 위반을 잡는지(일부러 위반 넣어보고 red 확인) 스모크.
- Wave C 후: `npm run storybook`으로 `PlayerPickModal`·`BottomSheet` 스토리 시각 확인(모바일 하단/데스크탑 중앙 전환, 스크롤, 애니메이션).
- Wave D 후: `npm run build` + `npm run build-storybook`으로 경로 해석 전면 확인.
- 토큰·경로 변경은 mock/실연동 양쪽에 영향 없음을 리뷰로 확인(순수 프론트 변경이라 DB 무관).
