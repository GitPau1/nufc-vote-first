# intent — 승부예측 주 경계 일요일 기준 변경

작성: 2026-09-04 · 작성자: Fable(오케스트레이터), 사용자와의 대화 기록
승인권자: 사용자 (프로덕트 디자이너)

## 배경

"승부예측 제출 수정·부분 제출"(TEA-23, PR #18) 작업 중 트리플 매치위크(경기 3개가 한 주에 몰리는
경우) 처리 방식을 확인하다가, 실제 시즌 데이터에 그런 주차가 있다는 게 확인됐다. 이걸 계기로 지금
주차 경계 기준 자체가 맞는지 의문이 제기됐다.

## 현재 기준

주차는 **ISO 8601 주차, 월요일 0시(KST) 시작**이다.
- 클라이언트: `frontend/src/lib/predictions/week.ts`의 `isoWeek()`/`weekKey()` — 킥오프를 KST로
  옮긴 뒤 ISO 8601 규칙으로 주차 번호를 매긴다(`weekKey` 형식: `"2026-35"`).
- DB: `prediction_week_start()`/`prediction_week_first_kickoff()`(`supabase/migrations/
  20260823130000_predictions_weekly_window.sql`)가 `date_trunc('week', kickoff_at at time zone
  'Asia/Seoul')`로 완전히 같은 기준을 쓴다 — 제출/수정 창(RLS)이 이 함수에 의존한다.
- `week_leaderboard`/`season_leaderboard`는 이 `week_key`로 매 조회마다 즉석 집계한다(저장된
  분류가 아니라 쿼리 시점에 `date_trunc`로 다시 계산됨).

## 문제 (실제 DB 조회로 확인, 2026-09-04)

`supabase db query --linked`로 뉴캐슬 전체 시즌 픽스처를 직접 조회해 확인했다:

- 월요일 기준으로 2026-08-24 주(8/24~8/30)에 경기 3개가 몰린다: 일요일 PL전(KST로는 월요일
  00:30) → 수요일 EFL컵(KST 목요일 03:45) → 그다음 토요일 PL전(KST 일요일 01:30). 미드위크 대항전
  때문에 실제 축구 일정에서 흔한 "주말-미드위크-주말" 패턴인데, 월요일 기준 경계가 이 흐름과 안 맞아
  세 경기가 한 주차로 묶인다.
- **일요일 0시(KST) 경계(주 = 일요일~토요일)로 시즌 전체를 다시 계산해봤다.** 위 3경기는 일요일
  기준 두 주차로 갈라진다("일→목" 2경기 / "그다음 일요일부터" 1경기).
- **시즌 전체 픽스처를 일요일 기준으로 다시 묶으면, 프리시즌 친선경기(Club Friendlies,
  2026-07-25~08-16) 구간에서만 3경기가 몰리는 주가 하나 나온다**(2026-08-09 주: 8/9·8/13·8/15).
  **정식 경기(프리미어리그·컵대회)만 놓고 보면 3경기 이상인 주가 없다.**
  사용자 확인(2026-09-04): 친선경기 밀집은 "실제 경기는 저렇게 진행이 안 되니 어쩔 수 없는 예외"로
  신경 쓰지 않기로 함 — 애초에 승부예측 대상 자체가 아닐 가능성이 높다(§"확정된 결정" 3번 참고).
  일요일 기준이 유럽 축구의 표준 리듬("주말 경기 + 미드위크 경기 → 다음 주말 경기")과 맞는다는
  점도 토요일 기준과 동일하게 성립한다.

## 확정된 결정 (2026-09-04)

1. **주차 경계를 월요일 0시(KST) → 일요일 0시(KST)로 바꾼다.** 주는 **일요일 ~ 토요일**이다.
   (처음엔 토요일 0시 기준을 검토했으나, 사용자가 "정확히는 일요일 0시"로 확정 — 실측 결과 정식
   경기 기준으로는 두 방식이 동일한 효과를 낸다. 일요일 기준을 채택한 것으로 확정.)
2. **소급 적용 범위 — 전체 소급 적용.** `week_leaderboard`/`season_leaderboard`가 `date_trunc`를
   매 조회마다 즉석 계산하는 구조라(과거 데이터를 별도 저장해두지 않음), 기준 함수를 바꾸는 순간
   과거 주차들의 랭킹 묶음도 전부 새 일요일 기준으로 재계산된다 — 그 결과 과거 순위가 조용히 바뀔
   수 있음을 감수하기로 확정. "특정 시점부터만 적용"(구현에 별도 저장/마이그레이션이 필요한 옵션)은
   기각.
3. **`weekKey` 형식 — 연도-순번(`"2026-N"`), 시즌 1주차 기준일 확정.** 시즌 1주차 시작일은
   **2026-08-23(일요일)** — 뉴캐슬 프리미어리그 개막전(리버풀전, 실제 킥오프 2026-08-23 15:30
   UTC = 2026-08-24 00:30 KST)이 속한 일요일 기준 주다. 그 이전에 있는 프리시즌 친선경기
   (Club Friendlies, 2026-07-25~08-16, DB에서 직접 확인)는 **시즌 주차 번호에 포함하지 않는다**
   — 승부예측 대상 자체가 아닐 가능성이 높음(구현 시 `competition_name`으로 실제 제외 여부 확인
   필요, 근거 미확인이므로 developer가 재확인). 순번 계산: `주차 번호 = floor((그 경기 킥오프의
   일요일 앵커 날짜 - 2026-08-23) / 7일) + 1`.
   이 키는 URL(`/predictions/[weekKey]`)에 그대로 노출되므로, 기존 ISO 주차 번호로 만들어진 옛
   URL(공유된 링크 등)과의 호환성은 이번 스코프에서 다루지 않는다(근거 미확인 — 얼마나 많은 옛
   링크가 도는지 모름, developer가 필요시 재차 확인).

## 다음 단계 (다음 세션이 이어서 진행)

1. developer 에이전트 → `feature-spec.md` + `plan.md` 작성. 영향 범위:
   - DB: `prediction_week_start()`/`prediction_week_first_kickoff()`(일요일 앵커로 재정의),
     `week_leaderboard`/`season_leaderboard`가 이 함수에 의존하는지 확인
   - 클라이언트: `frontend/src/lib/predictions/week.ts`의 `isoWeek()`/`weekKey()`(위 순번 계산식으로
     교체), `groupFixturesByWeek` 등 이 함수들을 호출하는 전체 지점
   - `weekKey` 형식 변경이 영향 주는 다른 지점(URL 라우팅, 캐시 키, 분석 이벤트 등) 전수 조사
   - 위 "확정된 결정 3"의 "근거 미확인" 2건(프리시즌 친선경기 제외 여부, 옛 URL 호환성)을 코드/데이터로
     재확인하고 spec에 명시
   - plan은 사람 승인 후 구현
2. linear-ops → Linear 프로젝트 생성 (내용은 오케스트레이터가 구성)

## 세션 인계 메모

이 프로젝트는 별도 워크트리(`predictions-week-boundary-saturday` — 폴더명은 검토 초기 "토요일" 안을
따서 만들어졌고, 최종 결정은 "일요일"로 바뀌었다. 워크트리 디렉터리 이름 자체는 그대로 두되 착각하지
말 것 — 실제 결정은 이 문서 기준이 맞다)에서 시작됐고, 사용자가 이 시점에서 컨텍스트를 비우고 새
세션으로 이어가길 원했다(2026-09-04). 새 세션은 이 `intent.md`만 읽으면 바로 "다음 단계"부터
진행할 수 있도록 위에 결정 사항을 전부 확정 형태로 남겨뒀다 — 추가로 사람에게 되물을 필요 없이
developer 에이전트에게 feature-spec 작성을 위임하면 된다.
