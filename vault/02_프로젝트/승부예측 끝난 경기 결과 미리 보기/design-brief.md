## 0. 사용자 확정 사항 (그대로 인용, 바꾸지 않음 — 2026-09-05 개정)

  채워질 때까지 "집계 중" 상태로 막아둔다.

- 재사용: `PredictionResult.tsx`의 `MatchResultBlock`(L291-381)을 그대로 쓴다. 새 컴포넌트 발명 금지.

## 1. 문제 정의

더블 매치위크(경기 2개 이상)에서 한 경기만 먼저 끝나도 주차 전체는 아직 열려 있다(예: 리그 경기 종료,
컵 경기는 며칠 뒤). 이 상태에서 사용자가 남은 경기를 마저 예측/수정하러 들어오는 화면 —
`PredictionDone.tsx`(제출 완료 허브) — 안에서, 끝난 경기는 이제 **주차 결과 화면과 똑같은 상세도로**
(점수 배지까지) 미리 보여줘야 한다.

**범위 확장(0-1, 2026-09-05 확정)**: 같은 종류의 갭이 주차 정산 결과 화면(`PredictionResult.tsx`,
주차가 끝난 뒤 렌더되는 화면)에도 있다 — 정산 게이트는 `f.finished`만 보고 선수 평점이 다 채워졌는지는
안 보므로, 주차 마지막 경기가 끝난 당일(크론이 아직 안 돈 시점)에는 정산 화면도 미집계 평점을 마치
최종처럼 보여줄 수 있다. 이 브리프의 ③ 상태 정의(3절)와 placeholder(3-2)는 `PredictionDone.tsx`뿐
아니라 `PredictionResult.tsx`에도 동일하게 적용된다.

**"예측 화면"이 가리키는 실제 컴포넌트는 여전히 `PredictionDone.tsx`다** — 근거는 이전 판과 동일:
`frontend/src/app/predictions/[weekKey]/page.tsx` L58-146 분기에서 `week.status !== 'result'`인 동안은
`PredictionDone.tsx`가 렌더되고, 더블 매치위크에서 한 경기만 끝난 동안은 `weekStatus()`(`week.ts`
L204-209)가 `'result'`가 될 수 없으므로(그 주 경기 전부가 잠기고 끝나야 함) `PredictionResult.tsx`
(주차 결과 화면)는 아직 렌더되지 않는다. 즉 이번 요구의 "경기 단위 블록"은 `PredictionResult.tsx`
안에 있는 컴포넌트(`MatchResultBlock`)를 **아직 그 화면이 렌더되기 전인 `PredictionDone.tsx` 안으로
가져와 쓰는 것**이 이번 작업의 핵심이다.

## 2. 현재 동작 — 이미 되어 있는 부분과 빠진 부분 (코드 근거)

### 2.1 이미 되어 있는 부분

`PredictionDone.tsx`의 `submittedMatches.map(...)` 블록은 `match.finished`일 때 "실제 결과" 서브카드 +
`HitBadge`(정확히 적중/승패 적중/미적중)를 이미 보여준다. 대회 배지도 이미 TEA-30 규칙
(`COMPETITION_BADGE`)을 따른다. 다만 이건 **점수 없는** 버전이다 — 이번 개정으로 이 카드 자체가
`MatchResultBlock`으로 교체된다(3절).

### 2.2 빠진 부분 — "킥오프됨·진행 중·결과 대기" 상태가 없다

`submittedMatches`는 `match.finished` 여부로만 두 갈래(끝남/안 끝남)로 그려진다. "킥오프는 지났지만
아직 안 끝난" 경기(`match.locked && !match.finished`)는 "안 끝난" 쪽과 같은 카드로 그려져, 지금 화면만
보면 "자유 수정 가능"과 "이미 잠김"이 구분되지 않는다. `MatchWeekList.tsx`의 `weekPhase()`
`'settling'`(주차 단위 "결과 반영중" 배지)과 같은 개념을 경기 단위로 옮겨 쓴다는 방향은 이전 판과
동일 — 이번 개정에서 바뀐 건 없다.

### 2.3 인접 이슈 — 잠긴 제출 경기의 "수정 가능" 제외 (내가 결정하는 게 아님, 이전 판과 동일)

`PredictionDone.test.mjs`에 이미 실패 중인 테스트가 있다: `editableMatches =
submittedMatches.filter(match => !match.locked)`(주석: "2026-09-05 결정, TEA-33"). 이건 이 브리프가
정하는 게 아니라 이미 확정된 별개 결정이고, 이 브리프는 그 결정을 전제로 "그럼 잠긴 경기의 카드는
어떻게 보이는가"만 다룬다. **이번 개정에서 중요해진 지점**: ③·④(아래 3절, 둘 다 `match.finished`라
당연히 `match.locked`)도 ②와 마찬가지로 `editableMatches`에서 제외된다 — 하단 "수정하기" 버튼은
①(제출됨·수정 가능) 경기만 대상으로 한다는 점이 ④가 새로 생겨도 그대로 유지된다.

### 2.4 이전 판이 남겼던 "확인 필요" 중 이번에 해소된 것 — 목록 화면과의 점수 표시 불일치

이전 판 §10-4는 "`MatchWeekList.tsx`(목록 화면)는 끝난 경기의 포인트를 이미 보여주는데,
`PredictionDone.tsx`는 감춘다"는 불일치를 확인 필요로 남겼었다. **이번 개정으로 해소된다** —
`PredictionDone.tsx`도 이제 점수를 보여주므로, 두 화면이 "끝난 경기는 주차 완료 여부와 무관하게 점수를
보여준다"는 같은 규칙을 따르게 된다. 더 이상 열린 질문이 아니다.

### 2.5 새로 발견한 것 — `MatchResultBlock`에는 대회 배지가 없다 (사실 보고, 결정 아님 → 8-3)

`PredictionResult.tsx`에는 `competition`/대회 배지 언급이 전혀 없다(grep 결과 0건) — `MatchResultBlock`도
그 헤더("경기 예측" + `PointsBadge`뿐)도 마찬가지다. 반면 ①·②·⑤(이번에 새로 만들거나 기존 유지하는
카드)는 전부 TEA-30 대회 배지(`COMPETITION_BADGE`)를 단다. **"그대로 쓴다"는 지시를 문자 그대로 따르면
③·④에서만 대회 배지가 사라진다** — 이건 발명 여지가 없는 사실이라 결정 필요 항목(8-3)으로 넘긴다.

### 2.6 새로 발견한 것 — `MatchResultBlock`의 카드는 기존 카드와 그림자·여백이 다르다 (사실 보고)

`MatchResultBlock`은 `Card` 프리미티브(`rounded-lg border border-neutral-weak bg-surface shadow-g200`,
패딩 `p-5`)를 쓴다. 반면 ①·②·⑤가 쓰는 기존 프레임(`PredictionDone.tsx`)은 `rounded-lg border
border-neutral-weak bg-surface px-4 py-5`로 **그림자(`shadow-g200`)가 없고 가로 패딩도 4px 더 좁다**.
즉 이번 개정 이후 한 화면(4절 흐름 3처럼 경기 A=④, 경기 B=①)에 두 카드 종류가 나란히 있으면 그림자
유무·패딩 차이가 눈에 보일 수 있다. "그대로 쓴다"는 지시가 이미 이 차이를 감수하겠다는 뜻으로
해석해 임의로 맞추지 않았다 — 다만 사람이 보기에 어색하면 개발자가 여백만 맞추는 선택지도 있다는 걸
알리기 위해 8-3에 같이 남긴다.

## 3. 카드 상태 정의 (`PredictionDone.tsx`의 경기별 카드 — 5가지)

| 상태 | 판정 조건(개념) | 카피 | 카드 구성 |
|---|---|---|---|
| ① 제출됨·수정 가능 | 제출함 && 안 잠김 | 변경 없음 | 기존 카드(내 예측 스코어 + 내 선수 픽). 하단 "수정하기" 대상 |
| ② 킥오프됨·진행 중·결과 대기 | 제출함 && 잠김 && 안 끝남 | "결과를 기다리는 중이에요"(확정, 0-1) | 내 예측 스코어(그대로, 손댈 수 없음) + 매치업 아래 캡션 한 줄(배지 아님, 8-1 후보 1 확정). 결과는 아직 안 보여줌 |
| ③ 종료·평점 집계 중 | 끝남 && 경기 점수는 나왔지만 선수 평점이 다 안 채워짐(평점 행 11개 미만) | "평점 집계 중이에요"(확정, 0-1) | `MatchResultBlock`의 "경기 예측" 카드는 **그대로**(스코어 비교 + "+N점" 배지). "내 선수 픽" 카드는 콘텐츠를 숨기고 "집계 중" 안내 박스로 막음 |
| ④ 종료·전체 결과 | 끝남 && 선수 평점까지 전부 집계됨 | 없음(재사용) | `MatchResultBlock` 그대로 — 두 카드(경기 예측/내 선수 픽) 전부 실제 값으로 렌더 |
| ⑤ 미제출·마감 | 제출 안 함 && 잠김 | 변경 없음(`missedMatches`) | "이 경기는 예측 마감 시간이 지나 참여하지 못했어요" |

②가 이번에도 새로 정의해야 하는 상태이고, ③은 이번 개정에서 **새로 쪼개진** 상태다(이전 판의 "③
종료·판정"이 점수 유무로 ③/④ 두 갈래로 갈라졌다). ①⑤는 기존 코드/카피 그대로 재사용한다.

### 3-1. 카드 안에 결과 블록이 어떻게 들어가는가 — "펼침"이 아니라 "교체"

**결론: 완료 화면 카드 안에 결과를 접어 넣지 않는다. ③·④에서는 그 경기 자리의 카드 자체가
`MatchResultBlock`이 그리는 카드(들)로 통째로 바뀐다.** 근거는 취향이 아니라 컴포넌트 구조다 —
`MatchResultBlock`은 스스로 `<Card>` 두 개(경기 예측/내 선수 픽)를 그리는 프래그먼트다
(`PredictionResult.tsx` L291-381, 바깥에 감싸는 카드가 없다). 이걸 기존 `rounded-lg border ...`
카드 프레임 **안에** 다시 넣으면 카드 테두리가 두 겹으로 중첩된다. "그대로 쓴다"는 지시를 지키는
유일한 방법은 그 경기의 카드 슬롯을 `MatchResultBlock`으로 교체하는 것이다 — 아코디언으로 펼치는
대안은 애초에 성립하지 않는다(발명이 필요 없을 만큼 코드가 이미 답을 정해준 경우).

- ③에서는 "내 선수 픽" 카드까지 `MatchResultBlock`을 그대로 쓰되(같은 카드 프레임·헤더 배치),
  안쪽만 집계 중 placeholder로 바뀐다 — 이건 `MatchResultBlock`이 이미 갖고 있는 시각 언어(아래
  3-2)를 재사용하는 것이라 새 컴포넌트가 아니다.

### 3-2. ③의 "집계 중" placeholder — 이미 있는 패턴 재사용

`MatchResultBlock`은 **아직 킥오프하지 않은 경기**를 위해 이미 "카드 전체를 안내 박스로 바꾸는" 상태를
갖고 있다(`state.kind === 'pending'`일 때 `rounded-md bg-page px-4 py-6 text-center` 박스,
`PredictionResult.tsx` L307-315, 카피 "예정 · 아직 시작하지 않은 경기예요"). ③의 "내 선수 픽" 카드도
같은 시각 언어(가운데 정렬 안내 박스)를 재사용하는 걸 제안한다 — 카드 프레임은 그대로 두고, 포지션
픽 리스트 자리만 이 박스로 바뀐다. 새 톤·새 레이아웃을 만드는 게 아니라 컴포넌트 안에 이미 있는
"아직 보여줄 게 없다" 표현을 다른 조건(평점 미집계)에 재사용하는 것이다.

- 카피: **"평점 집계 중이에요"**(확정, 0-1) — 기존 "등수 집계 중"(`PredictionResult.tsx` L249)·"스코어
  집계 중"(같은 파일 L345, `PredictionDone.tsx` L202)과 같은 "OO 집계 중" 패턴을 그대로 따른 것이라
  새 어휘는 아니다.
- "전부 들어왔다"의 판정 기준도 확정(0-1): **평점 행 11개 이상**. `sync-fixture-ratings`의
  `MIN_RATED_PLAYERS` 임계값과 같은 값이라, UI 게이트와 크론이 "다 채워졌다"고 보는 기준이 어긋나지
  않는다(정확한 컬럼·구현은 기술 판단, 9절).
- "경기 예측" 카드의 `PointsBadge`/`PickPointsBadge`는 `matchPoints`/`pickPoints`가 `null`이면

  픽" 카드는 배지·콘텐츠를 아예 안 그리고 3-2의 placeholder로 완전히 대체**하는 걸로 판단했다(배지에
  세 번째 의미를 욱여넣지 않는 편이 명확하다) — 9절 제약사항에도 반복해 남긴다.

## 4. UX 흐름 — 진입·전환

1. 사용자가 더블 매치위크에서 리그 경기만 먼저 제출하고 나간다 → ① 상태 카드(리그) + 아직 안 낸
   컵 경기는 `deferredMatches`("아직 예측하지 않았어요") 카드(변경 없음).
2. 리그 경기 킥오프가 지나면(아직 결과 안 남) → 리그 경기 카드가 ①에서 **②로 자동 전환**(서버 렌더
   기준, 사용자 조작 없음). 하단 "수정하기" 버튼은 리그 경기를 대상에서 제외한다(2.3, TEA-33).
3. 리그 경기가 끝나고 실제 스코어·경기 점수가 들어오면 → ②에서 **③으로 자동 전환**. 스코어 비교와
   "경기 예측" 카드의 "+N점"이 이 시점부터 보인다. "내 선수 픽" 카드는 아직 집계 중 박스.
4. 선수 평점이 모두 채워지면(크론 처리 완료, `feasibility.md` §3) → ③에서 **④로 자동 전환**. "내
   선수 픽" 카드가 실제 픽·평점·TOP3로 바뀐다.
5. 컵 경기는 그동안 계속 ①(아직 안 낸 상태면 `deferredMatches`) → 컵 경기도 킥오프 후 ②, 종료 후
   ③→④로 같은 전환을 겪는다.
6. 두 경기 다 ④가 되어도 **주차 종합 점수·등수는 여기서 안 보여준다** — 그건 `week.status === 'result'`가
   된 뒤 `PredictionResult.tsx`의 몫이다(요구사항 "주차 종합 점수는 주차가 끝나기 전에는 표시하지
   않음"과 일치). 이번 개정으로 바뀌는 건 **경기 단위** 점수 공개 여부뿐, 주차 단위 집계는 그대로
   가려져 있다.

카드 전환은 전부 **서버 렌더링 시점의 데이터 상태**로 결정된다 — 사용자가 화면 안에서 누르는 어떤
동작도 이 전환을 만들지 않는다.

## 7. 결정 이유 (디자이너가 스스로 판단해 확정한 것)

- **③·④는 카드를 "펼치는" 게 아니라 "교체"한다.** 3-1 근거. `MatchResultBlock`이 자체적으로 카드
  프레임을 그리는 구조라, 기존 카드 안에 다시 넣으면 이중 테두리가 생긴다 — 대안이 성립하지 않아
  에스컬레이션 대상이 아니라고 판단했다.
- **③의 "내 선수 픽" 카드는 배지를 안 그리고 아예 placeholder로 막는다.** `PointsBadge(null)`이
  이미 "미참여"라는 확정된 의미를 갖고 있어서, 여기에 "집계 중"이라는 세 번째 의미를 얹으면 사용자가
  두 상태(안 참여했음 vs 참여했는데 대기 중)를 헷갈릴 수 있다고 판단했다. `MatchResultBlock`이 이미
  가진 "아직 없음" 표현(pending 박스)을 재사용하는 쪽이 새 배지 상태를 만드는 것보다 안전하다.
- **카드 배경색을 상태별로 바꾸지 않는다.** (이전 판과 동일 판단, 유지) `competitionColor.ts`의
  "경기 카드는 항상 bg-page, 색은 컨테이너/배지가 담당한다" 원칙을 그대로 따른다.
- **②→③→④ 전환에 사용자 조작(버튼 등)을 넣지 않는다.** (이전 판과 동일 판단, 유지)
- **③·④에 결과 화면 링크를 두지 않는다** (이전 판 §8-2 "확인 필요"였던 것을 이번에 확정으로 옮김).
  근거: `PredictionResult.tsx`는 `week.status === 'result'`일 때만 렌더되어(`page.tsx` L58-72) 지금
  시점엔 갈 수 있는 상세 화면 자체가 없다는 점은 이전과 같지만, 이번 개정으로 **③·④가 이미
  `MatchResultBlock`을 그대로 써서 결과 화면과 동일한 상세도(스코어 비교 + 픽 + TOP3)를 인라인으로
  보여준다** — 그래서 "더 자세히 보기"가 가리킬 더 상세한 화면이 목적지 부재를 떠나 애초에 **내용상
  중복**이다. 이전 판보다 확신을 갖고 결정할 수 있어 확인 필요 목록에서 뺐다.

## 9. 개발자 에이전트가 참고할 제약사항
