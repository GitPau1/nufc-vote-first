## 1. 문제 정의 (intent.md에서 이어받음)

현재 결과 화면(`PredictionResult.tsx`)은 등수·점수 히어로가 최상단이라, 사용자가 화면을 여는 순간 가장 궁금해하는 "내 예측이 맞았는지"보다 사회적 순위가 먼저 노출된다. 모바일은 "내 예측/전체 결과" 토글로 랭킹이 숨어 발견성이 낮고, 카드 안에 경기 예측+선수 픽 정보가 길게 늘어서 밀도가 높다(intent.md L8-12).

목표: "판정 퍼스트" 단일 스크롤로 재구성한다. 맞음/틀림 판정을 헤드라인으로, 등수는 피날레로 미룬다(intent.md L14-16).

---

## 2. UX 흐름 — 블록 순서와 각 블록의 역할

모바일·데스크탑 동일 구성, 토글 제거(intent.md L20). 순서는 사용자의 감정 곡선을 따라간다: **개인적 확인(통쾌함) → 근거 확인 → 디테일 몰입 → 사회적 비교(클라이맥스) → 행동 유도.**

| 순서 | 블록 | 역할 (어떤 감정/정보를 주는가) | 근거 |
|---|---|---|---|
| ① | **판정 헤드라인** (다크 카드, `spotlight-glow-brand-strong`) | 진입 즉시 "맞았는지 틀렸는지"부터 알려주는 통쾌함/아쉬움 블록. 기존엔 이 자리가 등수였다 — 문제 1을 정면으로 뒤집는 블록 | intent.md L10, L16, L22-23 |
| ② | **경기별 비교 카드** | 판정의 "근거"를 보여준다. 헤더에 같은 배지 형태로 "+N점", 크레스트 행, 내 예측/실제 결과 2행 비교. 판정 헤드라인이 내린 결론을 스코어로 검증하는 역할 | intent.md L23, L29-30 |
| ③ | **내 선수 픽** | 경기 판정과 별개로 내 선택 하나하나가 어땠는지 디테일 확인. TOP3 아코디언으로 "내 선택이 다른 후보들 사이에서 얼마나 잘한 픽이었나"라는 궁금증까지 해소해 체류를 늘린다 | intent.md L24, L28-32 |
| ④ | **피날레** (다크 카드 하나, 총점 카운트업 → 등수 → 스트립 → 랭킹 → 더보기) | 사회적 비교의 클라이맥스. 카운트업 애니메이션이 잠깐의 긴장을 만들고 등수가 뜬다 — "피날레의 감정 보상"으로 명시적으로 설계됨 | intent.md L25, L31 |
| ⑤ | **공유 버튼** | 결과를 다 확인한 뒤 자연스럽게 공유로 이어지도록 페이지 맨 하단 배치 | intent.md L26 |

**판정 퍼스트 → 피날레 순서의 의도**: 기존 구조는 "사회적 순위(몇 등인지)"가 "개인적 감정(맞았는지)"보다 먼저 나와 위계가 뒤집혀 있었다(문제 1). 새 구조는 개인 확인 → 근거 → 디테일 → 사회적 비교 → 행동 순으로, 가장 즉각적이고 개인적인 감정부터 주고 사회적 비교는 가장 뒤에 배치해 클라이맥스로 만든다.

## 3. 상태 매트릭스

행: 참여 / 미참여. 열: 채점 전 / 집계 중 / 집계 완료.

근거: `result.ts`의 `MatchResultState`(`pending`/`missed`/`scored`, L58-66)와 `aggregateWeekResult`(L64-76, `results`가 있는 매치만 카운트해 합산하고 랭킹에서 내 행을 못 찾으면 `rank: null`).

| | **채점 전** (경기 미종료) | **집계 중** (경기 채점 완료, 주간 랭킹 미확정) | **집계 완료** (개인 채점 + 주간 랭킹 확정) |
|---|---|---|---|
| **참여** | 판정 헤드라인: 판정할 결과가 없어 **미참여와 동일한 안내 문구**가 뜬다(⚠ 아래 유의사항 참고) · 경기 비교 카드: 현행 "아직 시작하지 않은 경기예요" 카드 유지(intent.md L38) | 판정 헤드라인: 정상 노출(적중 여부 확정) · 경기 비교/선수 픽: 정상 노출 · 피날레: 총점 카운트업까지 노출, 등수 자리에 "등수 집계 중"(intent.md L37) | 판정 헤드라인 + 경기 비교 + 선수 픽 + 피날레 등수까지 전부 정상 노출 |
| **미참여** | 판정 헤드라인: 미참여 안내 문구 · 경기 비교 카드: "아직 시작하지 않은 경기예요" | 판정 헤드라인: 미참여 안내 문구 · 실제 경기 결과 카드는 노출 · 랭킹은 공개(참여 무관 정책), 내 등수 자리만 빠짐(intent.md L36) | 위와 동일 — 미참여자는 랭킹 집계 단계와 무관하게 항상 "미참여" 화면 |

**⚠ 구현 유의사항 (열린 질문은 아니지만 개발자가 알아야 할 것)**: 더블 매치위크가 아닌 단일 경기 주차에서, 사용자가 예측을 제출했지만 그 경기가 아직 끝나지 않았다면 `aggregateWeekResult`는 채점된 결과가 없으므로 `null`을 반환한다(`result.ts` L70-76: `results[match.id]`가 있는 매치만 카운트, 예측 제출 여부가 아니라 **채점 완료 여부**로 참여를 판정). 즉 현재 코드 기준으로 "예측은 했지만 경기가 안 끝난" 상태의 판정 헤드라인은 완전 미참여와 같은 문구를 쓰게 된다. 더블 매치위크는 다른 경기가 이미 채점됐다면 부분 결과로 노출되므로 이 문제가 없다. 이 간극을 새 카피로 메울지, 기존 문구를 그대로 쓸지는 이 브리프의 카피 후보(4번)에서 "미참여" 문구를 그대로 재사용하는 것으로 제안하며 — 사람이 다르게 판단하면 알려달라.

## 4. 카피 후보 (판정 헤드라인) — **카피 확정은 사람 승인 사항, 후보만 제시**

톤: 현행 서비스 톤(존댓말 "-어요"체, 이모지 없음) 유지. 근거: `PredictionResult.tsx` L162 "이 기간에는 예측에 참여하지 않았어요", L235 "아직 시작하지 않은 경기예요", L372 "선택하지 않았어요".

각 헤드라인은 시안-v9.html 구조를 따라 **큰 제목 + 서브라인** 2단 구성이다(L94-98). 서브라인 템플릿: `{상대팀}전 {스코어}, {부연설명}`.

### 정확 적중 (`matchHit === 'exact'`)
- **A. "스코어 정확히 적중!" (추천)** — 시안-v9.html L96 그대로. 이미 사용자 승인을 받은 표현이라 톤 리스크가 가장 낮음
- B. "완벽하게 맞혔어요!"
- C. "스코어까지 딱 맞혔어요"
- 서브라인 예: "Wolves전 1–1, 내 예측 그대로였어요" (시안 L97)

### 승패만 적중 (`matchHit === 'outcome'`)
- **A. "승부는 적중, 스코어는 아쉬웠어요" (추천)** — "적중"과 "아쉬움"을 한 문장에 대비시켜 판정 근거(②번 비교 카드)로 자연스럽게 시선을 넘김
- B. "결과는 맞혔어요"
- C. "승패는 맞혔지만 스코어는 빗나갔어요"
- 서브라인 예: "Wolves전 2–1, 승리는 맞혔지만 스코어는 달랐어요"

### 빗나감 (`matchHit === 'miss'`)
- **A. "이번엔 예측이 빗나갔어요" (추천)** — 담백하게 사실만 전달, 과도한 위로/독려 톤 지양(현행 서비스 톤이 감탄사·이모지 없이 사실 위주인 것과 일관)
- B. "아쉽게 빗나갔어요"
- C. "예측이 어긋났어요"
- 서브라인 예: "Wolves전 0–2, 내 예측과는 달랐어요"

### 더블 매치위크 부분 적중 (2경기 중 1경기만 적중)
- **A. "2경기 중 1경기 적중!" (추천)** — intent.md L22에 이미 확정된 표현
- B. "이번 주 2경기 중 1승 적중"
- C. "절반은 맞혔어요"
- 서브라인 예: "Wolves전은 적중, Villa전은 빗나갔어요" (경기별로 어떤 게 맞았는지 명시가 판정 근거로서 더 유용함 — ②번 비교 카드가 2개 나열되므로 중복이지만, 헤드라인만 보고도 이해되게)

> 참고(요청 범위 밖, 참고용): 더블 매치위크 2/2 전적중·0/2 전빗나감은 위 "정확 적중"/"빗나감" 문구에 "두 경기 모두" 같은 수식만 얹으면 확장 가능해 보이나, 확정 요청 항목이 아니므로 후보를 만들지 않았다. 필요하면 별도로 요청 바람.

### 미참여
- **A. "이 기간에는 예측에 참여하지 않았어요" (추천)** — 현행 문구 그대로 재사용(`PredictionResult.tsx` L162). 새 카피를 만들 이유가 없고, 위 상태 매트릭스의 "참여+채점 전" 간극도 이 문구로 덮인다
- B. "이번 주는 예측하지 않았어요"
- C. "참여하지 않은 주차예요"

## 5. 인터랙션 — 전부 기존 패턴 재사용

새 인터랙션 패턴은 없다. 아래는 전부 기존 코드/토큰의 재사용이며, 신규 값을 발명하지 않는다.

- **픽 TOP3 아코디언**: `tailwind.config.ts` L165-177에 이미 정의된 `accordion-down`/`accordion-up` keyframe(0.2s ease-out)과, 이를 쓰는 `frontend/src/components/primitives/accordion.tsx`의 `Accordion`/`AccordionTrigger`/`AccordionContent`가 그대로 재사용 대상이다(intent.md L32, `accordion.tsx` L8-13 주석 — Radix `--radix-accordion-content-height` 기반 높이 애니메이션). **주의**: 시안-v9.html의 `.top3-toggle`/`.top3`는 `onclick` + `display:none/flex` 토글로 만든 정적 데모(L140-147 등)이며 실제 구현 컴포넌트가 아니다. 개발자는 레이아웃만 시안에서 가져오고 동작은 기존 `Accordion` 프리미티브를 붙인다.
- **총점 카운트업**: `PredictionResult.tsx` L199-215의 `useCountUp` 그대로 재사용(intent.md L31). 0에서 600ms 안에 목표값까지 올라가며, 서버 렌더/첫 페인트가 0이라 하이드레이션 불일치가 없다는 기존 설계 이유도 그대로 유지된다.
- **주차 랭킹 더보기 펼침**: `WeekRankCard.tsx`의 capped 로직(L30-40, L70-78 "전체보기 · N명" 버튼) 재사용. 자세한 내용은 6번 열린 질문 참고 — 현재 모바일과 데스크탑의 자르는 방식이 다르므로(아래 6-2) 그대로 재사용할지 통일할지가 열린 질문이다.

## 7. 열린 질문 — intent.md의 "근거 미확인" 3건 (결정은 사람이 한다)

intent.md L40-44를 그대로 옮기고, 각각에 디자이너 관점 추천을 덧붙인다.

### 7-1. 포지션별 평점 TOP3 데이터
> 모든 후보 선수의 경기 평점 데이터가 필요한데, 현재 확인된 건 내가 픽한 선수의 평점뿐(`scored.picks[position].rating`). 전체 선수 평점을 조회할 수 있는지(테이블/뷰/RLS) 미확인 → **별도 이슈로 격리** (사용자 확정)

**디자이너 추천**: 이미 별도 이슈로 격리하기로 확정됐으므로(intent.md L49) 이 결과 화면 개편 이슈에서는 TOP3 아코디언을 UI 껍데기(레이아웃·인터랙션)만 구현하고, 데이터가 없는 동안은 해당 아코디언 자체를 노출하지 않는 편을 추천한다 — 근거: `PredictionResult.tsx`의 기존 관례가 "값이 없으면 배지를 아예 안 그린다"는 방식이다(L339 `RatingBadge`가 `rating === null`이면 `null` 반환). 다만 이건 디자인 판단이 아니라 순서 조율에 가까우므로, 개발자 에이전트가 두 이슈의 순서를 어떻게 잡을지 결정할 문제로 넘긴다.

### 7-2. 랭킹 "더보기" 기본 노출 인원 수(N)
> 랭킹 "더보기" 기본 노출 인원 수(N) 미정 — 기존 `WeekRankCard`의 capped(10명) 로직 재사용 가능

**디자이너 추천**: 기존 `DESKTOP_CAP = 10`(`WeekRankCard.tsx` L9)을 그대로 재사용하는 걸 추천한다. 근거: 새 피날레는 데스크탑/모바일 레이아웃이 동일한 단일 컨테이너이므로(2번 UX 흐름 참고), 지금처럼 "데스크탑만 10명 캡+버튼, 모바일은 CSS 페이드"로 화면 폭에 따라 다른 방식을 쓸 이유가 사라졌다. 시안-v9.html도 모바일·데스크탑 둘 다 명시적 "더보기 ▾" 버튼을 쓴다(L216, L323) — CSS 페이드가 아니다. 즉 `WeekRankCard`의 `capped` prop 방식(버튼 노출)을 모바일에도 적용해 10명 캡으로 통일하는 게 시안과 일치한다. 단, 10이라는 숫자 자체를 바꿀지는 디자인 판단이 아니라 사람이 정할 정책 값이라 이 브리프에서 확정하지 않는다.

### 7-3. 다크 면 위 파란 강조색 토큰
> 다크 면 위 파란 강조 숫자(blue-400 직접 참조)는 semantic 토큰 부재 → 치환/신규 토큰/컴포넌트 예외 중 미정

**디자이너 추천**: 시안-v9.html의 `--blue-400: #6ab4ff`(L12)는 실제로 `globals.css` L53의 팔레트 토큰 `--p-blue-400: #6ab4ff`와 정확히 같은 값이다 — 즉 "새 색"이 아니라 이미 있는 팔레트 단계다. 다만 이걸 다크 면 위에서 쓰는 **semantic 토큰**(예: `fg-brand-on-solid` 같은)은 아직 없다(`--sem-fg-brand: var(--p-blue-700)`, L128 — 이건 라이트 면 전제).

같은 문제를 이미 겪은 선례가 코드에 있다: `globals.css` L206-222의 `.spotlight-glow-brand-strong`(다크 카드 배경에 `--p-blue-700`/`--p-blue-600`을 직접 참조)과 `.award-gold`(다크 카드 위 트로피 카드에 `--p-orange-*`를 직접 참조)가 "다크 면 전용 semantic 토큰이 없을 때 팔레트 값을 컴포넌트 레벨에서 직접 참조하는 예외"로 이미 명시적으로 허용돼 있다(L221-222 주석: "같은 선례"). 따라서 이번에도 새 semantic 토큰을 만들기보다 **같은 예외 패턴으로 `--p-blue-400`을 컴포넌트 레벨에서 직접 참조**하는 걸 추천한다 — 새 패턴을 발명하는 게 아니라 이미 두 번 쓰인 관례를 세 번째로 따르는 것이기 때문이다.

다만 이게 "semantic 토큰을 새로 만들지 말지"라는 디자인 시스템 판단이라 임의로 확정하지 않는다 — 아래 8번 에스컬레이션 참고.
