# 노란 팔레트 제안 — `--p-yellow-*` 11단계

작성: 2026-09-05 · 작성자: designer 에이전트
승인: 2026-09-05 · 11단계 값·색상각·대비 검증 전부 사용자 승인 완료 (`시안.html`에서 실제 적용해 비교한 뒤 확정 — 배지/다크 글로우에서 이 값을 정확히 어떻게 쓸지는 `design-brief.md` 2-3번·4번·6-2번 참고).

## 0. 영향 범위 고지 (반드시 먼저 읽을 것)

이 문서가 제안하는 `--p-yellow-50` ~ `--p-yellow-950`는 **"친선경기 색" 기능 하나를 위한 임시값이 아니라, 이 리포 디자인시스템의 8번째 팔레트 계열로 추가되는 것**이다.

- 지금 이 리포의 팔레트는 `blue/red/green/orange/cyan/violet/neutral` 7계열뿐이고(`frontend/src/app/globals.css` L53-59), 그중 순수 노란색 계열은 없다. 원래 "대회별로 색상 다르게" 프로젝트의 `design-brief.md`는 이 공백을 이유로 "친선경기=`--p-orange-*`로 대체, 별도 노란 팔레트 신설은 하지 않는다"로 확정했었다(`design-brief.md` §6-1).
- 이후 사람이 스코프를 넓혀 **정식 노란 팔레트를 신설하기로 결정**했다 — 이 문서는 그 신설 요청에 대한 답이다.
- 따라서 이 문서에서 나온 값이 승인되면, `globals.css`의 Palette 블록에 8번째 계열이 영구히 추가된다. **친선경기 배지 하나가 아니라, 앞으로 이 리포 어디서든 "노란색이 필요한 모든 곳"(예: 경고/주의 강조, 새 배지 등)이 이 계열을 재사용할 수 있게 된다는 뜻이다.** 승인 시 이 영향 범위를 인지하고 승인해야 한다.
- 이 문서는 값 계산만 한다. 이 팔레트를 실제로 어디에 어떻게 적용할지(예: 친선경기 배지에 700단계를 쓸지, weak 배경을 쓸지)는 `design-brief.md`가 이미 다룬 3-1~3-4번의 재검토 대상이며, 이 문서의 범위가 아니다.

## 1. 색상각(hue) 선정 — 근거

### 1-1. 기존 7계열 700단계(대표값)의 OKLCH 색상각

`globals.css`의 실제 hex를 sRGB → OKLab → OKLCH로 역산했다(계산 방법은 부록 참고).

| 계열 | 700단계 hex | OKLCH 색상각(H) |
|---|---|---|
| red | `#cf231a` | 29.07° |
| **orange** | `#a65e00` | **61.80°** |
| **green** | `#008728` | **145.81°** |
| cyan | `#007f9f` | 223.54° |
| neutral | `#6e7277` | 253.90° (채도 0.009로 매우 낮아 색상각 자체가 불안정 — 참고용) |
| blue | `#115aff` | 263.02° |
| violet | `#9130e7` | 302.46° |

색상각 순서로 보면 red(29°) → **[빈 구간]** → green(146°) → cyan(224°) → blue(263°) → violet(302°) → (한 바퀴 돌아) red(389°) 순이다. 노란색이 색상 원환에서 자연스럽게 들어가는 자리는 red/orange와 green 사이 — 즉 orange-700(61.80°)과 green-700(145.81°) 사이의 84.01° 구간뿐이다(다른 모든 계열은 이보다 훨씬 멀다 — 1-3번 표 참고).

### 1-2. 색상각 결정

이 84.01° 구간 안에서, orange-700과 green-700 양쪽으로부터 가장 멀리 떨어진 지점은 **정확히 그 구간의 이등분점**이다(하나가 가까워지면 반대쪽이 그만큼 가까워지는 제로섬 구조이므로, 이등분이 수학적으로 최적).

```
H_yellow = (61.80° + 145.81°) / 2 = 103.805°
```

- orange-700과의 거리: **42.01°**
- green-700과의 거리: **42.00°**

**§3.6 red↔orange 사례(24.3°→75°)와 정직하게 비교하면**: 이번엔 75° 수준까지는 못 간다. red↔orange는 색상 원환에서 색상각을 자유롭게 돌릴 수 있는 열린 공간이 있었지만, 노란색은 이미 자리 잡은 두 이웃(orange·green) *사이*에 끼워 넣어야 해서 가용 공간이 84.01°로 애초에 제한돼 있다 — 양쪽으로 최대한 벌려도 42°가 수학적 상한이다.

그래도 이 42°는:
- §3.6이 "위험하다"고 판단한 24.3°의 **1.7배 이상**이고,
- 참고로 순수 노란색(`#ffff00`)의 OKLCH 색상각은 109.77°, 금색(`#ffd700`)은 95.33°로, 103.805°는 이 둘 사이에 정확히 들어와 "노란색"으로 읽히는 범위와도 일치한다.

**1-3. 나머지 5계열과의 거리(참고, 문제 없음 확인)**

| 계열 | 700단계 H | 노랑(103.805°)과의 거리 |
|---|---|---|
| red | 29.07° | 74.74° |
| cyan | 223.54° | 119.73° |
| neutral | 253.90° | 150.09° |
| blue | 263.02° | 159.21° |
| violet | 302.46° | 161.35° |

전부 orange·green보다 훨씬 멀어 문제 없음.

**결론: `H_yellow = 103.8°`로 고정한다.**

## 2. 11단계(50~950) 생성

### 2-1. 밝기(L) 곡선 — 기존 6계열 실측 평균을 그대로 따름

기존 6개 유채색 계열(blue/red/green/orange/cyan/violet, neutral 제외)의 각 단계 hex를 OKLCH로 역산해 L값을 뽑으면, **계열이 달라도 같은 단계면 L이 거의 같다**(예: 700단계는 0.542~0.554 사이로 전 계열이 몰려 있음) — 이는 이 팔레트가 "단계별 고정 밝기 사다리 + 계열별로 다른 색상각·채도"로 설계됐다는 뜻이다(§3.5의 "OKLCH 11단계 생성 원리"와 일치). 새 곡선을 임의로 만들지 않고, **이 6계열의 단계별 L 평균을 그대로 밝기 사다리로 재사용**했다.

| 단계 | L 평균(6계열) | 개별 값 범위 |
|---|---|---|
| 50 | 0.9801 | 0.9724 ~ 0.9843 |
| 100 | 0.9574 | 0.9452 ~ 0.9660 |
| 200 | 0.9218 | 0.9011 ~ 0.9345 |
| 300 | 0.8666 | 0.8365 ~ 0.8854 |
| 400 | 0.7799 | 0.7529 ~ 0.8009 |
| 500 | 0.7049 | 0.6727 ~ 0.7211 |
| 600 | 0.6345 | 0.6096 ~ 0.6421 |
| 700 | 0.5489 | 0.5423 ~ 0.5539 |
| 800 | 0.4409 | 0.4394 ~ 0.4432 |
| 900 | 0.3211 | 0.3191 ~ 0.3239 |
| 950 | 0.2217 | 0.2203 ~ 0.2233 |

### 2-2. 채도(C) — sRGB 색 영역 한계까지 최대화 (채도 캡 불필요, 계산으로 확인)

같은 방식으로 기존 6계열의 "실제 채도 / 같은 밝기·색상각에서 sRGB가 허용하는 최대 채도" 비율을 계산해보면, **green을 제외한 5계열(blue/red/orange/cyan/violet)은 거의 모든 단계에서 이 비율이 1.00(=색 영역 한계까지 이미 채도를 최대로 쓰고 있음)**이다. 오직 green만 계열 전체에서 의도적으로 채도를 낮춰 쓰고 있다(0.48~0.85 수준) — §3.6이 기록한 "green 700단계 채도 1.176배 예외"는 이 계열 전체 패턴의 일부였다.

새 노랑 계열도 같은 계산을 해봤다 — H=103.8°에서 sRGB가 허용하는 최대 채도는 green의 최대 채도(예: L=0.55에서 0.177)보다 낮다(같은 L에서 0.116). 즉 **채도를 최대치까지 써도 green처럼 "네온/탁해 보이는" 과잉 채도 문제가 계산상 나타나지 않는다** — 그래서 green과 같은 인위적 채도 감쇠(캡)를 새로 만들지 않고, **다른 5계열과 동일하게 "각 단계에서 sRGB가 허용하는 최대 채도"를 그대로 썼다**. 이건 "계산상 필요성이 실제로 보일 때만 예외를 둔다"는 지시를 그대로 따른 것이다 — 필요성이 안 보였으므로 예외를 만들지 않았다.

(L/C/H는 hex를 8bit로 반올림한 뒤 다시 역산한 실측값 — 목표값과 소수점 셋째 자리 이내로 일치, 재현성 확인됨. 부록 스크립트로 재현 가능.)

**시각적 특성 — 미리 알아둘 것**: 노란색은 원래 700단계처럼 어두운 단계로 가면 순수한 "노랑"이 아니라 **올리브/카키색**에 가깝게 보인다(`#7d7400`). 이건 이 계산의 오류가 아니라 노란색 자체의 물리적 특성이다(sRGB에서 어두운 고채도 노랑은 항상 이렇게 보인다) — `orange-700`(`#a65e00`)도 이미 "갈색"에 가깝게 보이는 것과 같은 종류의 현상이다. 50~300단계는 눈에 익은 밝은 노랑(`#fcea00` 등)이고, 700단계 이후로 갈수록 올리브 방향으로 이동한다는 점을 승인 전에 감안해야 한다.

## 3. 대비 검증 (두 가지 모두)

### 검증 스크립트 자체 검산

`contrast('#000000', '#ffffff')` = **21.000** (WCAG 정의상 최댓값과 정확히 일치) → 계산 함수 정상 확인.
추가로 WCAG 공식 예시 `#767676` vs `#ffffff` = 4.542(공식 문서와 일치)로 재검산.

### 검증 1 — 700단계 vs 흰색(#ffffff)

| 비교 | 대비 | 기준(AA 4.5:1) |
|---|---|---|
| `yellow-700`(`#7d7400`) vs `#ffffff` | **4.805** | **PASS** |
| (참고) `green-700` vs `#ffffff` | 4.671 | PASS |
| (참고) `orange-700` vs `#ffffff` | 4.973 | PASS |

### 검증 2 — 700단계 텍스트 vs "그 색 자신의 weak 배경"

기존 6계열의 `--sem-bg-{intent}-weak`은 팔레트 100/200단계를 그대로 쓰는 게 아니라, **"`text-{intent}`(700단계, 고정)를 얹었을 때 대비 4.55(여유 포함 AA)를 만족하는 최소 밝기를 OKLCH에서 역산한 값"**이다(`globals.css` L76-98 주석, §3.16). 새 노랑도 같은 방법을 그대로 재현했다:

1. 색상각을 103.8°로 고정.
2. L을 0.999(거의 흰색)부터 낮춰가며 `contrast(yellow-700, 해당 L의 노랑빛 배경)`이 4.55 밑으로 떨어지는 지점을 이분탐색.
3. 채도는 기존 5계열(green·cyan 제외)과 동일하게 감쇠 없이(chromaMult 1.0) 그 L에서 sRGB가 허용하는 최대치를 그대로 사용 — green·cyan처럼 채도를 절반으로 낮추는 예외가 노랑에는 **필요하지 않았다**(아래 이유 참고).

| 목표 대비 | 결과 L | 결과 hex | 실제 대비 |
|---|---|---|---|
| 4.50 | 0.9746 | `#fffabe` | 4.501 |
| **4.55** | **0.9785** | **`#fffbc8`** | **4.550** |
| 4.57(참고, 기존 6계열이 실제로 쓴 여유값) | 0.9810 | `#fffcce` | 4.592 |

**`yellow-700`(`#7d7400`) vs `weak 배경`(`#fffbc8`) = 4.550 → PASS.**

**왜 green·cyan과 달리 채도 감쇠가 필요 없었나**: green·cyan은 순도 100%로는 L을 0.999까지 올려도 대비 4.55에 못 미쳐 채도를 강제로 절반까지 낮춰야 했다(§3.16). 노랑은 채도 100%인 채로 L=0.978 근처에서 이미 목표 대비를 만족한다 — 그래서 감쇠가 필요 없다는 걸 스캔(부록 참고)으로 확인했다. 결과적으로 노랑의 weak 배경(`#fffbc8`)은 기존 6계열의 weak 배경들(대부분 거의 흰색, 예: `#f4fff5`, `#f5ffff`)과 달리 **여전히 눈에 보이는 옅은 노란빛**을 유지한다 — 계산상의 우연이 아니라 노랑의 채도가 밝은 단계에서도 잘 유지되는 특성 때문이다.

**부수 확인**: 위에서 역산한 weak 배경(`#fffbc8`)은 2-3번 표의 `--p-yellow-50`(`#fffbcc`)과 거의 동일하다(OKLCH 상 L 차이 0.0009, C 차이 0.005) — 두 값이 서로 다른 계산 경로(하나는 "밝기 사다리 50단계", 하나는 "대비 4.55 역산")로 나왔는데도 사실상 같은 지점에 수렴했다. 이는 이 팔레트가 일관된 구조를 갖고 있다는 교차 검증이다.

승인되면 `globals.css`의 Palette 블록(L53-59)에 8번째 줄로 추가하는 것을 developer 에이전트에게 근거로 넘긴다. 이 문서는 팔레트 원시값만 제안하며, `--sem-*` semantic 토큰 신설 여부·"친선경기" 기능에서의 실제 적용 방식은 별도 승인 대상이다(0번 고지 참고).

## 부록 — 계산 스크립트 (재현 가능, 순수 JS, 외부 패키지 없음)

sRGB↔OKLab↔OKLCH 변환은 Björn Ottosson의 공개 OKLab 공식을 그대로 구현했다. 실행: `node <파일명>.mjs` (Node 18+, ESM).

```js
// oklch.mjs — sRGB <-> OKLab <-> OKLCH, WCAG contrast helpers
function srgbToLinear(c) {
  c = c / 255;
  return c <= 0.04045 ? c / 12.92 : Math.pow((c + 0.055) / 1.055, 2.4);
}
function linearToSrgb(c) {
  return c <= 0.0031308 ? c * 12.92 : 1.055 * Math.pow(c, 1 / 2.4) - 0.055;
}
function hexToRgb(hex) {
  hex = hex.replace('#', '');
  return [0, 2, 4].map(i => parseInt(hex.slice(i, i + 2), 16));
}
function rgbToHex([r, g, b]) {
  const c = (v) => Math.round(Math.max(0, Math.min(255, v))).toString(16).padStart(2, '0');
  return '#' + c(r) + c(g) + c(b);
}
function linearRgbToOklab(r, g, b) {
  const l = 0.4122214708*r + 0.5363325363*g + 0.0514459929*b;
  const m = 0.2119034982*r + 0.6806995451*g + 0.1073969566*b;
  const s = 0.0883024619*r + 0.2817188376*g + 0.6299787005*b;
  const l_ = Math.cbrt(l), m_ = Math.cbrt(m), s_ = Math.cbrt(s);
  return [
    0.2104542553*l_ + 0.7936177850*m_ - 0.0040720468*s_,
    1.9779984951*l_ - 2.4285922050*m_ + 0.4505937099*s_,
    0.0259040371*l_ + 0.7827717662*m_ - 0.8086757660*s_,
  ];
}
function oklabToLinearRgb(L, a, b) {
  const l_ = L + 0.3963377774*a + 0.2158037573*b;
  const m_ = L - 0.1055613458*a - 0.0638541728*b;
  const s_ = L - 0.0894841775*a - 1.2914855480*b;
  const l = l_**3, m = m_**3, s = s_**3;
  return [
    +4.0767416621*l - 3.3077115913*m + 0.2309699292*s,
    -1.2684380046*l + 2.6097574011*m - 0.3413193965*s,
    -0.0041960863*l - 0.7034186147*m + 1.7076147010*s,
  ];
}
function hexToOklch(hex) {
  const [r, g, b] = hexToRgb(hex).map(srgbToLinear);
  const [L, a, bb] = linearRgbToOklab(r, g, b);
  const C = Math.sqrt(a*a + bb*bb);
  let H = Math.atan2(bb, a) * 180 / Math.PI;
  if (H < 0) H += 360;
  return { L, C, H };
}
function oklchToRgbLinear(L, C, H) {
  const hRad = H * Math.PI / 180;
  return oklabToLinearRgb(L, Math.cos(hRad)*C, Math.sin(hRad)*C);
}
function inGamut(r, g, b) {
  return r >= -1e-6 && r <= 1+1e-6 && g >= -1e-6 && g <= 1+1e-6 && b >= -1e-6 && b <= 1+1e-6;
}
function maxChroma(L, H, precision = 0.0001) {
  let lo = 0, hi = 0.5;
  while (inGamut(...oklchToRgbLinear(L, hi, H)) && hi < 1) hi += 0.05;
  for (let i = 0; i < 60; i++) {
    const mid = (lo + hi) / 2;
    if (inGamut(...oklchToRgbLinear(L, mid, H))) lo = mid; else hi = mid;
    if (hi - lo < precision) break;
  }
  return lo;
}
function oklchToHex(L, C, H) {
  const rgb = oklchToRgbLinear(L, C, H).map(linearToSrgb).map(v => v * 255);
  return rgbToHex(rgb);
}
function relLuminance(hex) {
  const [r, g, b] = hexToRgb(hex).map(srgbToLinear);
  return 0.2126*r + 0.7152*g + 0.0722*b;
}
function contrast(hex1, hex2) {
  const L1 = relLuminance(hex1), L2 = relLuminance(hex2);
  const [hi, lo] = [Math.max(L1, L2), Math.min(L1, L2)];
  return (hi + 0.05) / (lo + 0.05);
}

// --- 3. L 사다리(6계열 평균, 본문 2-1 표) + 최대 채도로 11단계 생성 ---

  500:0.7049,600:0.6345,700:0.5489,800:0.4409,900:0.3211,950:0.2217 };

function weakBgAtL(L, chromaMult = 1.0) {
  return oklchToHex(L, maxChroma(L, H_YELLOW) * chromaMult, H_YELLOW);
}
function bisectMinL(target, chromaMult = 1.0) {

  for (let i = 0; i < 100; i++) {
    const mid = (lo + hi) / 2;
    if (contrast(palette[700], weakBgAtL(mid, chromaMult)) < target) lo = mid; else hi = mid;
  }
  return hi;
}
```
